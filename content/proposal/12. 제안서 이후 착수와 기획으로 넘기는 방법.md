# 12장 제안서 이후 착수와 기획으로 넘기는 방법

11장에서 제안서 제출 이후 발표라는 별도의 설득 구조를 다뤘다면, 이제 남는 과제는 그 제안 내용을 실제 착수 입력으로 다시 바꾸는 일이다.  
이 책이 제안서 작성법으로만 끝나면 중요한 절반을 놓치게 된다.  
제안서는 제출로 끝나는 문서가 아니라, 수주형 프로젝트의 앞단에서 만들어진 첫 기획 산출물이다.  
그래서 좋은 제안서는 잘 제출되는 것만으로는 충분하지 않다.  
그 이후 착수와 기획 단계로 안정적으로 넘어갈 수 있어야 한다.

이 장의 초점은 `제안서 이후의 해석과 입력 재구성`이다.  
제안서 자체를 잘 쓰는 방법이 아니라, 제안 내용을 착수와 기획으로 넘기는 방법을 다룬다.

실무에서는 이 연결이 자주 끊긴다.  
제안 단계에서 약속한 내용과 착수 단계에서 이해한 내용이 다르고, 제안서에 담긴 범위와 실제 기획 입력이 다르게 해석되며, 고객과 내부 팀이 보고 있는 기준 문서도 달라진다.  
이때부터 프로젝트는 시작부터 흔들린다.

그래서 제안서 이후 가장 중요한 질문은 이것이다.

- 무엇을 착수 입력으로 넘길 것인가
- 무엇을 다시 질문해야 하는가
- 무엇을 범위 확정 대상으로 남겨야 하는가
- 무엇이 다음 기획 산출물의 핵심 입력이 되는가

즉 제안서 이후 단계는 `문서를 넘기는 일`이 아니라 `입력을 재구성하는 일`이다.

## 1. 제안서와 착수 사이에는 해석 단계가 있다

많은 팀이 제안서가 확정되면 바로 착수한다고 생각한다.  
하지만 실제로는 그 사이에 반드시 해석 단계가 있어야 한다.

이 해석 단계에서 해야 할 일은 다음과 같다.

- 제안서의 약속 문구를 실제 수행 단위로 다시 읽기
- 범위가 확정된 항목과 협의가 필요한 항목을 구분하기
- 고객 확인이 필요한 질문을 정리하기
- 내부 전달용 입력 구조로 바꾸기

제안서의 문장은 설득을 위해 쓰였지만, 착수 입력은 실행을 위해 정리되어야 한다.  
따라서 같은 문서를 그대로 넘기는 것으로는 충분하지 않다.  
제안 내용을 착수 가능 형태로 번역하는 과정이 필요하다.

## 2. 착수 입력으로 다시 정리해야 하는 항목

제안서 이후 착수 단계에서 다시 정리해야 하는 대표 항목은 비교적 분명하다.

### 2-1. 문제 정의

제안서는 고객의 문제를 넓게 설명할 수 있다.  
하지만 착수 입력에서는 실제로 우리가 풀 문제를 더 명확히 적어야 한다.

- 어떤 문제를 우선 해결하는가
- 어떤 문제는 이번 범위 밖인가
- 성공 조건은 무엇인가

### 2-2. 범위와 제외 범위

제안 단계에서는 넓게 표현했던 범위가 착수 단계에서는 좁혀져야 한다.

- 이번 프로젝트에 반드시 포함되는 것
- 추가 협의가 필요한 것
- 명시적으로 제외해야 하는 것

### 2-3. 입력 자료

실제 기획과 설계를 하려면 제안서보다 더 구체적인 입력이 필요하다.

- 기존 시스템 자료
- 업무 흐름 자료
- 운영 정책
- 사용자 유형과 데이터 구조
- 고객 내부 승인 구조

### 2-4. 질문 리스트

제안서만으로 확정할 수 없는 내용은 반드시 질문 리스트로 남겨야 한다.  
질문을 남기지 않으면 모호함은 나중에 요구 변경과 책임 충돌로 돌아온다.

## 3. 제안서에서 RIB로 넘어간다

이 책이 `제안서 자동화`를 넘어 `기획 방법론`과 연결되는 지점이 바로 여기다.  
제안서 이후 단계에서 만들어야 하는 핵심은 결국 다음 기획 산출물의 입력 세트다.

그 대표가 `RIB`다.

RIB 관점으로 보면 제안서 이후에 다시 정리해야 하는 것은 다음과 같다.

- 왜 이 프로젝트를 하는가
- 어떤 사용자와 어떤 문제를 다루는가
- 성공 기준은 무엇인가
- 범위와 제약은 무엇인가
- 어떤 입력이 이미 있고 무엇이 빠져 있는가

즉 제안서를 그대로 기획 문서로 쓰는 것이 아니라, 제안서 안의 약속과 해석을 다시 정리해 `RIB 입력 후보`로 바꾸는 것이다.

> **[도식: fig-제안-착수-입력전환]** — 제안서 문장 → 확정/협의/질문 필요 항목 분리 → 착수 입력 세트 정리 → RIB 입력 후보 전환으로 이어지는 흐름도. 제안 단계 산출물이 다음 기획 입력으로 어떻게 번역되는지 보여주는 도식 후보.

## 4. AI는 이 연결 구간에서 무엇을 도울 수 있는가

제안서 이후 연결 구간은 사람이 많이 놓치는 영역이지만, AI가 유용하게 들어갈 수 있는 구간이기도 하다.

AI는 다음을 빠르게 도울 수 있다.

- 제안서에서 범위 관련 문장 추출
- 확정/협의/질문 필요 항목 분리
- 착수용 질문 리스트 초안 생성
- 킥오프 안건 초안 생성
- RIB 입력 후보 정리

이 단계에서 AI는 `재정리 도구`로 보는 것이 맞다.  
앞에서 만든 문서를 다시 읽고, 다음 단계 입력으로 바꾸는 일에 강하다.

반면 사람은 다음을 판단해야 한다.

- 제안서의 어떤 문장을 실제 약속으로 볼 것인가
- 고객과 다시 확인할 포인트가 무엇인가
- 무엇을 범위 확정 대상으로 남길 것인가
- 어떤 위험을 착수 단계에서 먼저 드러낼 것인가

즉 AI는 연결을 빠르게 만들 수 있지만, 연결의 기준은 사람이 정한다.

## 5. 착수와 킥오프는 제안의 연장선이어야 한다

좋은 프로젝트는 제안과 착수가 단절되지 않는다.  
제안 단계에서 정리한 메시지, 범위, 리스크, 질문이 착수와 킥오프 안건으로 이어진다.

그래서 착수 단계에서 확인해야 할 것은 다음과 같다.

- 제안서의 핵심 메시지가 킥오프에서도 유지되는가
- 고객이 기대한 범위와 내부가 이해한 범위가 같은가
- 질문 리스트가 실제 회의 안건으로 살아 있는가
- 범위 확정과 기획 입력 확정이 같은 흐름으로 이어지는가

착수는 새로운 시작이지만, 동시에 제안의 연장선이기도 하다.

## 6. 제안서 품질은 착수 품질로 증명된다

좋은 제안서인지 아닌지는 제출 직후에는 잘 드러나지 않을 수 있다.  
하지만 착수 단계에 들어가면 바로 드러난다.

좋은 제안서는:

- 범위 해석이 비교적 안정적이고
- 질문 리스트가 명확하며
- 다음 기획 입력으로 이어질 수 있고
- 내부 전달이 쉽다

반대로 약한 제안서는:

- 제안 문구와 실제 수행 범위가 충돌하고
- 고객 기대와 내부 이해가 어긋나며
- 질문이 뒤늦게 터지고
- 착수 후 다시 처음부터 정리해야 한다

그래서 제안서 품질은 문장력보다 착수 연결성으로 증명된다.

## 7. 이 장의 핵심

이 장에서 정리할 수 있는 원칙은 다음과 같다.

- 제안서는 제출로 끝나지 않는다
- 제안서 이후에는 해석과 재구성 단계가 필요하다
- 착수 입력은 제안서를 그대로 넘기는 것이 아니라 다시 정리한 입력이다
- 제안서 안의 약속은 RIB 입력 후보로 변환되어야 한다
- AI는 이 연결 구간에서 재정리와 질문 초안 생성에 강하다
- 사람은 범위, 위험, 약속, 질문의 우선순위를 판단해야 한다

이 책이 결국 말하고 싶은 것은 이것이다.  
좋은 제안서는 잘 써진 문서가 아니라, 다음 단계로 잘 넘어가는 문서다.

마지막 장에서는 지금까지의 흐름을 한 번 묶어, 이 책이 무엇을 하고 무엇을 하지 않는지 방법론의 입장으로 정리한다. 13장의 주제다.

## AI 협업 포인트

**이 단계의 핵심:** 제안서 전문을 AI에 넣어 착수 입력 세트를 빠르게 추출하고, 범위 해석과 약속 확정은 사람이 직접 판단한다.

### 협업 워크플로우

1. 최종 제안서 전문(또는 핵심 섹션)을 AI 입력으로 준비한다
2. AI에게 착수 단계에 필요한 입력 항목을 추출하도록 요청한다
3. AI가 범위 문장, 약속 항목, 질문 리스트, 킥오프 안건 초안을 생성한다
4. 사람이 각 항목을 확정 / 협의 필요 / 질문 필요로 직접 분류하고 판단을 추가한다
5. 정리된 착수 입력 세트를 RIB 또는 킥오프 문서의 입력으로 전환한다

### 프롬프트 예시

```
다음 제안서를 기반으로 착수 단계 입력 세트를 만들어줘.

[추출 요청 항목]
① 수행 범위 관련 문장: 범위를 명시하거나 암시하는 문장 목록
② 확정된 약속 항목: 일정, 인력, 산출물, 수준 등 명확하게 약속된 것
③ 협의가 필요한 항목: 조건부 표현이나 범위가 모호한 것
④ 착수 전 고객 확인이 필요한 질문 목록
⑤ 킥오프 안건 후보 (범위 → 일정 → 역할 → 리스크 순)

각 항목은 표로 정리하고, 제안서 원문 위치(섹션명)를 함께 표시해줘.

[제안서 전문 붙여넣기]
```

### 입출력 예시

**입력**
제안서 수행 범위·운영 방안 섹션

**AI 출력 초안**

| 유형 | 항목 | 원문 위치 | 확인 필요 사항 |
|---|---|---|---|
| 확정 약속 | PM 1인, 개발자 3인 배치 | 수행 조직 섹션 | 실제 인력 확정 시점 필요 |
| 협의 필요 | "요청 시 운영 지원 제공" | 운영 방안 섹션 | 요청 기준과 지원 범위 불명확 |
| 고객 질문 | 고객사 담당자 협조 범위 | 수행 방법 섹션 | 제안서에 명시 안 됨 |
| 킥오프 안건 | 범위 확정 회의 일정 | — | 수주 후 1주 내 개최 필요 |

**사람이 추가할 판단**
- "요청 시 운영 지원" → 계약서 조항으로 어떻게 처리할지 법무 확인 필요
- 인력 확정은 수주 후 2주 내 내부 프로세스로 진행

### 사람이 확인해야 하는 판단 체크리스트

- [ ] AI가 추출한 범위 문장이 실제 제안서 원문과 일치하는가
- [ ] 확정 / 협의 필요 / 질문 필요 분류를 사람이 직접 완료했는가
- [ ] 고객 확인 질문 목록이 킥오프 안건에 반영되었는가
- [ ] 이 착수 입력 세트가 RIB 또는 기획 문서 입력과 실제로 연결되는가
