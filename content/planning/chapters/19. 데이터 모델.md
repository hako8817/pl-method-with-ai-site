# 19장. 데이터 모델: ERD와 데이터 사전

> 이 장은 데이터베이스 설계를 위한 ERD(엔티티-관계 다이어그램)와, 각 필드·속성의 정의를 명세하는 데이터 사전(Data Dictionary)을 다룬다. 정책서와 BPMN·DMN에서 결정된 규칙이 실제 데이터 구조로 어떻게 전환되는지를 보여주는 핵심 산출물이다.

---

## 이 장의 목적

18장에서 콘텐츠 모델이 "어떤 데이터가 있어야 하는가"를 기획 관점에서 정의했다면, 이 장은 그 정의를 실제 DB 설계에 가까운 형태로 전환한다. ERD는 엔티티 간 관계를 구조화하고, 데이터 사전은 각 필드의 의미와 제약을 문서화한다.

이 장을 읽고 나면 다음을 할 수 있어야 한다.

- ERD가 정책서·BPMN·DMN과 어떻게 연결되는지 설명할 수 있다.
- 기획자 관점에서 ERD를 검토하는 기준이 무엇인지 파악한다.
- 데이터 사전의 구조와 작성 기준을 이해한다.
- AI와 함께 초안 ERD를 만들고 무엇을 확인해야 하는지 판단할 수 있다.

---

## 1. 이 산출물이 왜 존재하는가

콘텐츠 모델은 기획과 디자인이 공유하는 기준이다. 하지만 실제 DB를 설계하는 개발자는 더 구체적인 기준이 필요하다. 어떤 테이블에 어떤 컬럼이 있고, 컬럼의 데이터 타입과 제약 조건은 무엇인지, 다른 테이블과의 관계는 어떻게 설정되는지가 명확해야 한다.

ERD가 없으면 개발자마다 다른 DB 설계를 만들게 된다. 데이터 사전이 없으면 같은 컬럼이 팀마다 다른 의미로 사용된다. "user_status"가 어떤 팀에서는 로그인 상태를, 다른 팀에서는 계정 활성 여부를 의미하는 상황이 만들어진다.

기획자가 ERD를 설계하는 것이 아니다. 하지만 정책서에서 정의한 규칙이 ERD에 올바르게 반영됐는지는 기획자가 확인해야 한다.

---

## 2. 입력과 출력

**입력:**
- 콘텐츠 모델 (20장): 주요 엔티티와 속성 목록
- 정책서 (18장): 상태 값, 데이터 보존 기간, 예외 규칙
- DMN (19장): 상태 전이 판단 기준
- BPMN (19장): 프로세스에서 생성·변경·삭제되는 데이터

**출력:**
- ERD: 엔티티와 관계 다이어그램
- 상태 모델: 주요 엔티티의 상태 값과 전이 조건
- 데이터 사전: 각 엔티티의 속성별 정의·유형·제약

이 산출물들은 사양서(23장)와 API 명세서(24장)의 직접 입력이 된다.

---

## 3. 세 산출물의 구조와 역할

### 3-1. ERD (Entity-Relationship Diagram)

ERD는 데이터베이스 설계를 위한 엔티티와 관계를 정의하는 다이어그램이다. 기획자가 ERD를 직접 설계하지 않아도, PRD와 정책서를 기반으로 AI가 초안 ERD를 생성할 수 있고 기획자는 이를 검토해 개발자와 합의점을 찾는다.

| 항목 | 내용 |
|------|------|
| 목적 | 저장해야 하는 데이터의 구조와 관계를 정의 |
| 형식 | 엔티티-관계 다이어그램 (Crow's Foot 또는 논리 ERD) |
| 주요 내용 | 엔티티, 속성, 관계(1:N, M:N 등), 식별자 |
| 기준 문서 | PRD 기능 목록, 정책서의 데이터 보존 규칙, BPMN |

기획자가 ERD에서 확인해야 할 것은 기술 상세보다 **정책 반영 여부**다.

- 정책서에서 정의한 상태 값이 컬럼으로 반영됐는가
- 데이터 보존 기간 규칙이 설계에 포함됐는가
- 프로세스에서 생성·변경·삭제되는 데이터가 모두 커버됐는가

### 3-2. 상태 모델 (State Model)

상태 모델은 서비스 내 주요 엔티티가 어떤 상태를 가지며, 어떤 조건에서 상태가 바뀌는지를 정의하는 산출물이다.

예를 들어 회원 계정은 다음 상태를 가질 수 있다.

```
활성(Active) → 휴면(Dormant) → 탈퇴(Withdrawn) → 만료(Expired)
```

각 전이에는 조건이 있다.

| 전이 | 조건 |
|------|------|
| 활성 → 휴면 | 1년 이상 미접속 |
| 휴면 → 활성 | 본인 인증 후 복귀 |
| 활성 → 탈퇴 | 회원 탈퇴 요청 |
| 탈퇴 → 만료 | 탈퇴 후 90일 경과 |

상태 모델은 DMN과 밀접하게 연결된다. DMN이 "이 조건에서 어떤 결정을 내리는가"를 정의한다면, 상태 모델은 "어떤 상태에서 어떤 전이가 가능한가"를 정의한다.

---


### 3-3. 데이터 사전 (Data Dictionary)

데이터 사전은 DB의 각 테이블·컬럼에 대한 정의를 문서화한 명세다. ERD가 구조와 관계를 보여준다면, 데이터 사전은 각 필드가 무엇을 의미하는지, 어떤 값이 들어올 수 있는지, 어떤 제약 조건이 있는지를 기록한다.

이커머스 플랫폼 예시: 주문·반품 관련 주요 테이블 데이터 사전

**orders 테이블**

| 컬럼명 | 데이터 타입 | 필수 | 기본값 | 설명 |
|--------|------------|------|--------|------|
| order_id | UUID | 필수 | auto | 주문 고유 식별자 |
| buyer_id | UUID | 필수 | - | 구매자 ID (외래키) |
| status | ENUM | 필수 | 'PENDING_PAYMENT' | 주문상태: 결제대기/결제완료/배송준비/배송중/배송완료/구매확정 (정책 P-01~P-03 참조) |
| payment_completed_at | TIMESTAMP | 선택 | NULL | 결제 완료 시점 (취소 가능 기준) |
| shipped_at | TIMESTAMP | 선택 | NULL | 배송 출고 시점 (취소 불가 기준) |
| delivered_at | TIMESTAMP | 선택 | NULL | 배송 완료 시점 (반품 허용 기간 계산 기준) |
| confirmed_at | TIMESTAMP | 선택 | NULL | 구매확정 시점 (반품 불가 기준) |
| created_at | TIMESTAMP | 필수 | now() | 주문 생성 일시 |

**returns 테이블**

| 컬럼명 | 데이터 타입 | 필수 | 기본값 | 설명 |
|--------|------------|------|--------|------|
| return_id | UUID | 필수 | auto | 반품 고유 식별자 |
| order_id | UUID | 필수 | - | 주문 ID (외래키, 정책 P-02 배송완료 7일 이내 확인) |
| seller_responsible | BOOLEAN | 필수 | - | 판매자 귀책 여부 (정책 P-05 배송비 부담 기준) |
| status | ENUM | 필수 | 'PENDING' | 반품상태: 신청/수거중/수거완료/반품확인/환불완료 (정책 P-01~P-06 참조) |
| requested_at | TIMESTAMP | 필수 | now() | 반품 신청 일시 (배송완료로부터 7일 초과 체크) |
| approved_at | TIMESTAMP | 선택 | NULL | 반품 승인 일시 |
| refund_id | UUID | 선택 | NULL | 환불 ID (외래키, 환불 처리 완료 기준) |

데이터 사전은 팀 안에서 "이 컬럼이 뭐야?"라는 질문이 반복될 때 참조하는 단일 기준이 된다. 특히 AI에게 쿼리 작성이나 API 명세 생성을 요청할 때, 데이터 사전을 컨텍스트로 제공하면 필드명과 의미가 일치하는 결과물을 얻을 수 있다.

## 4. AI와 함께 만드는 법

### 단계 1: 입력 준비

AI에게 제공할 컨텍스트를 정리한다.

- 승인된 PRD의 주요 기능 목록
- 정책서의 엔티티별 규칙 (보존 기간, 상태 전이 조건)
- BPMN에서 각 단계별 생성·변경 데이터

### 단계 2: AI 초안 생성

**Step 2-1: 정책 → ERD 초안 생성**

```
아래 정책서와 DMN 조건을 기반으로 반품·환불 도메인의 논리 ERD를 작성해줘.

[정책 조건]
- 반품 상태: PENDING / RETURN_REQUESTED / RETURN_COLLECTING / RETURN_COLLECTED / RETURN_APPROVED / REFUND_PROCESSING / COMPLETED / REJECTED
- 반품 허용 기간: 배송 완료일로부터 7일 이내 (P-02)
- 구매확정 이후 반품 불가 (P-03)
- 판매자 귀책 반품 시 배송비 판매자 부담 (P-05)
- 환불은 원결제 수단으로 처리 (P-06)

[ERD 요청 항목]
1. Return 엔티티 + 핵심 속성 목록 (타입·제약조건 포함)
2. 상태값 컬럼과 상태 전이에 필요한 보조 컬럼 (예: requestedAt, approvedAt, refundedAt)
3. Order·Buyer·Seller 엔티티와의 관계 (FK 방향, 선택적/필수 여부)
4. 정책 조건(허용 기간, 귀책 기준)을 지원하는 컬럼 구조

표 형식(엔티티명 / 속성 / 타입 / 설명)으로 작성해줘.
```

**Step 2-2: 상태 전이 조건 → ERD 검증**

ERD 초안이 나오면 상태 전이 조건이 컬럼 구조에 반영됐는지 AI와 함께 점검한다.

```
아래 ERD 초안과 상태 전이 조건을 비교해서 누락된 컬럼이나 관계를 찾아줘.

[상태 전이 조건]
- PENDING → RETURN_REQUESTED: 반품 신청 접수 시 / requestedAt = 현재 시각 저장
- RETURN_REQUESTED → RETURN_COLLECTING: 판매자 수락 시 / 수거 요청 처리
- RETURN_COLLECTING → RETURN_COLLECTED: 수거 완료 시 / 배송사 콜백 기준
- RETURN_COLLECTED → REFUND_PROCESSING: 반품 확인 완료 시
- REFUND_PROCESSING → COMPLETED: 환불 처리 완료 시 / refundedAt 저장
- RETURN_REQUESTED → REJECTED: 판매자 거부 또는 정책 위반 (P-02/P-03)

[ERD 초안]
(AI가 생성한 내용 붙여넣기)

누락된 속성, 상태 전이를 지원하지 못하는 구조, 정책서 조건과 불일치하는 항목을
구체적으로 지적해줘.
```

### 단계 3: PM 검토 기준

AI가 생성한 초안에서 PM이 확인해야 할 것:

- 정책서와 DMN의 조건이 상태 모델에 모두 반영됐는가
- 상태 전이 조건이 DMN 판단 기준과 일치하는가
- 엔티티 관계가 BPMN 흐름과 정합하는가
- 데이터 보존 규칙이 컬럼이나 별도 테이블로 반영됐는가
- 다음 단계 사양서와 API 명세 작성에 충분한 정보가 포함됐는가

## 5. 품질 기준 / 체크리스트

| 항목 | 확인 기준 |
|------|-----------|
| 정책 반영 | 정책서의 모든 상태 값이 ERD와 상태 모델에 포함됐는가 |
| 전이 조건 | 상태 전이 조건이 DMN과 일치하는가 |
| 데이터 흐름 | BPMN의 각 태스크에서 생성·변경되는 데이터가 ERD에 존재하는가 |
| 기준 문서 연결 | 각 엔티티와 속성이 어떤 기준 문서에서 비롯됐는지 추적 가능한가 |
| 미정 항목 표시 | 확정되지 않은 부분이 명확히 표시됐는가 |
| 승인 상태 | Draft / Review / Approved 상태가 문서 헤더에 표시됐는가 |

## 6. 다음 단계 연결 규칙

이 장에서 만든 산출물은 다음으로 이어진다.

- **사양서(Spec)**: ERD의 엔티티와 속성이 기능별 상세 조건으로 전개됨
- **API 명세서**: ERD의 관계와 상태 모델이 API 요청/응답 스키마로 전환됨
- **테스트케이스**: 상태 전이 조건이 경계값과 예외 케이스 기준이 됨
- **RTM**: 정책서 → ERD → 사양서 → 테스트케이스 추적 경로 완성

---

## 7. 이 장의 핵심 메시지

> 정책은 규칙을 정의하고, 데이터 모델은 그 규칙이 실제로 저장되고 조회될 수 있는 구조를 정의한다.

BPMN과 DMN까지 완성됐더라도 데이터 구조가 정의되지 않으면 개발과 QA는 각자 해석한 구조로 작업한다. 정보 구조도, ERD, 상태 모델은 그 해석의 불일치를 산출물 단계에서 미리 해소한다.

---

## 8. 다음 장으로의 연결

데이터 모델이 완성되면 "이 구조를 어떤 시스템 아키텍처 위에 올릴 것인가"를 결정할 차례다. ERD의 엔티티 구조가 SAD의 데이터 레이어 컴포넌트가 되고, 상태 모델이 이벤트 흐름의 기반이 된다.

### 데이터 모델에서 SAD로 이동하는 항목

| 데이터 모델 항목 | 이동 형태 | SAD에서의 역할 |
|---|---|---|
| ERD 주요 엔티티 | 엔티티 목록 + 관계 구조 | SAD 데이터 레이어 컴포넌트 정의 |
| 상태 모델 | 상태-전환 다이어그램 | SAD 이벤트·상태 관리 구조 |
| 데이터 접근 패턴 | 읽기/쓰기 빈도 추정 | 캐시 레이어, DB 분리(Read Replica) 근거 |
| 외부 데이터 연동 요건 | 연동 대상·방식 | SAD 외부 시스템 인터페이스 정의 |
| 민감 데이터 필드 | 마스킹·암호화 대상 목록 | SAD 보안 경계 및 데이터 암호화 레이어 |

### 체인 전환 기준 (데이터 모델 → SAD)

| 확인 항목 | 기준 |
|---|---|
| ERD 핵심 엔티티 확정 | 주요 비즈니스 엔티티와 관계가 그려져 있는가 |
| 상태 모델 존재 | 핵심 객체(회원, 주문 등)의 상태 전환 다이어그램이 있는가 |
| 접근 패턴 파악 | 조회 빈도가 높은 엔티티가 식별되어 있는가 |
