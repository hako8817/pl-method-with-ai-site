# 27장. RTM, Decision Log, Changelog

> 이 장은 산출물 체인의 추적·거버넌스 문서 세 가지를 다룬다. RTM(요구사항 추적 매트릭스)은 요구사항이 설계·구현·검증으로 이어지는지를 추적한다. Decision Log는 왜 그렇게 결정했는가의 판단 근거를 보존한다. Changelog는 무엇이 언제 어떻게 바뀌었는지를 기록한다. 세 문서는 함께 산출물 체인의 투명성과 연속성을 보장한다.

---

## 제1절. RTM: 요구사항 추적 매트릭스

> **이 장에서 다루는 것**
> - RTM의 역할과 설계 기준
> - 산출물 체인에서 RTM이 담당하는 연결
> - AI와 함께 RTM을 운영하는 실무 패턴

> 의사결정 이력은 27장 제2절(Decision Log), 변경 이력은 27장 제3절(Changelog)에서 다룬다.

> **전제 지식**: 25장(산출물 체인 설계), 11장(PRD) — RTM은 PRD의 요구사항이 설계·구현·검증 단계로 이어지는지를 추적한다.

## 이 장의 목적

이 장은 RTM(Requirements Traceability Matrix)이 산출물 체인에서 어떤 역할을 하는지, 어떻게 설계하고 운영하는지를 설명한다. RTM은 요구사항이 어떤 정책, 설계, 테스트, 구현 항목과 연결되는지를 추적하는 문서다.

이 장을 읽고 나면 다음을 할 수 있어야 한다.

- RTM이 Decision Log, Changelog와 어떻게 다른지 설명할 수 있다.
- 최소 RTM 구조를 설계할 수 있다.
- RTM을 어떤 시점에 갱신해야 하는지 판단할 수 있다.

---

## 1. 이 산출물이 왜 존재하는가

AI를 쓰면 PRD에서 BPMN 초안, 사양서 초안, 테스트케이스 초안까지 빠르게 만들 수 있다. 문제는 속도가 빨라질수록 이런 질문이 더 중요해진다는 점이다.

- 이 요구사항은 어떤 설계 항목으로 내려갔는가
- 이 요구사항은 어떤 테스트케이스로 검증되는가
- 설계가 바뀌었을 때 어느 TC가 영향받는가
- 릴리즈 범위에서 어떤 요구사항이 빠졌는가

RTM이 없으면 이 질문에 답하려고 모든 문서를 직접 뒤져야 한다. RTM은 이 연결을 한 곳에서 볼 수 있게 만든다.

---

## 2. 무엇을 입력으로 받고 무엇을 넘기는가

### RTM이 받는 입력

| 입력 소스 | 내용 |
|---|---|
| PRD / RIB | 요구사항 항목과 ID |
| 정책서 / BPMN / DMN | 요구사항이 내려간 설계 항목 |
| 사양서 | 구현 조건 참조 |
| 테스트케이스 | 검증 항목과 실행 결과 |
| 구현 태스크 | 개발 작업 연결 참조 |

### RTM이 넘겨주는 출력

| 출력 | 내용 |
|---|---|
| 연결 지도 | 요구사항 → 설계 → 검증 전체 추적 |
| 누락 항목 목록 | 연결되지 않은 요구사항 또는 TC |
| 릴리즈 범위 점검 | 검증 완료 여부 확인 기준 |
| 다음 기획 입력 | 미연결 항목 → RIB/PRD 갱신 근거 |

## 3. RTM은 무엇을 추적해야 하는가

RTM은 거대한 표가 되어야 하는 것이 아니다. 핵심 연결 고리가 끊기지 않는 것이 중요하다.

최소한 아래 연결이 보여야 한다.

| 컬럼 | 내용 |
|---|---|
| Req ID | 요구사항 식별자 |
| 요구사항 요약 | 한 줄 설명 |
| 정책 참조 | 연결된 정책서 항목 |
| BPMN/DMN 참조 | 연결된 흐름/판단 구조 |
| 사양서 참조 | 연결된 구현 조건 |
| 테스트 참조 | 연결된 TC ID |
| 구현 참조 | 연결된 개발 태스크 |
| 상태 | 설계중 / 구현중 / 검증완료 / 릴리즈 |

### 최소 템플릿

```md
| Req ID | 요구사항 요약 | 정책 참조 | BPMN/DMN | 사양 참조 | TC 참조 | 구현 참조 | 상태 |
|---|---|---|---|---|---|---|---|
```

## 4. 언제 갱신해야 하는가

| 갱신 트리거 | 내용 |
|---|---|
| 요구사항 확정 시 | 새 Req ID 등록 |
| 정책/설계로 내려갈 때 | 연결 항목 추가 |
| TC 실행 결과 확정 시 | 검증 상태 갱신 |
| 릴리즈 직전 | 전체 연결 완전성 점검 |
| 요구사항 변경 시 | 영향 항목 연결 재확인 |

주 책임: PM/PO 또는 BA가 기본 구조 관리, QA와 개발이 TC/구현 연결 보강.

---

## 5. RTM이 특히 유용한 순간

- 정책 변경이 생겼을 때 영향 범위를 즉시 파악해야 할 때
- 테스트 누락을 찾을 때
- 특정 기능의 구현/검증 상태를 점검할 때
- 릴리즈 범위를 확인할 때

RTM은 요구사항이 문장으로 끝나지 않고 설계와 검증까지 살아 있는지 보여주는 문서다.


## 7. AI와 함께 RTM을 운영하는 실무 패턴

### AI에게 맡기기 좋은 일
- RTM 누락 연결 후보 탐지
- TC와 요구사항 연결 누락 질문 생성
- 릴리즈 범위 내 미검증 항목 목록 생성

### 사람이 직접 보증해야 하는 일
- 최종 연결 관계 확정
- 릴리즈 범위 책임 판단
- 영향 범위 확정

## 8. 품질 기준 / 체크리스트

- 요구사항이 설계와 테스트까지 연결되는가
- 미연결 항목이 식별되고 추적되는가
- TC 실행 결과가 RTM에 반영되는가
- 릴리즈 전 전체 연결 완전성이 확인됐는가

| 검증완료 상태 확정 | 릴리즈 판단 입력 |
| 릴리즈 완료 | Changelog 배포 이력 추가 |

> 의사결정 이력은 **27장 제2절(Decision Log)**, 변경 이력은 **27장 제3절(Changelog)**에서 이어진다.

## 제2절. Decision Log: 의사결정 이력

> **이 장에서 다루는 것**
> - Decision Log의 역할과 회의록과의 차이
> - 어떤 결정을 언제 기록해야 하는가
> - AI와 함께 Decision Log를 운영하는 실무 패턴

> 요구사항 추적은 27장 제1절(RTM), 변경 이력은 27장 제3절(Changelog)에서 다룬다.

> **전제 지식**: 25장(산출물 체인 설계) — Decision Log는 산출물 체인 위에서 내려진 판단의 근거를 보존하는 문서다.

## 이 장의 목적

이 장은 Decision Log가 무엇인지, 회의록이나 메모와 어떻게 다른지, 어떤 결정을 어떻게 남겨야 하는지를 설명한다. Decision Log는 왜 그렇게 결정했는가를 나중에도 확인할 수 있도록 남기는 판단 책임 기록이다.

이 장을 읽고 나면 다음을 할 수 있어야 한다.

- Decision Log가 RTM, Changelog와 어떻게 다른지 설명할 수 있다.
- 어떤 결정을 Decision Log에 남겨야 하는지 판단할 수 있다.
- 최소 Decision Log 구조를 작성할 수 있다.

---

## 1. 이 산출물이 왜 존재하는가

실무에서 결정은 빠르게 내려지고 빠르게 잊힌다. 회의에서 정한 정책 해석, 범위 제외, 예외 허용은 구두로 합의되거나 메신저로 오가다 문서에 남지 않는 경우가 많다.

나중에 이런 상황이 생긴다.

- "왜 재가입 제한이 30일이었지?"
- "이 예외는 누가 승인한 거야?"
- "이번 릴리즈에서 왜 이 기능을 뺐지?"

Decision Log가 없으면 같은 결정을 다시 논의하거나, 책임 소재가 불분명해지거나, 잘못된 기억으로 정책이 바뀐다. AI 시대에는 문서가 빠르게 생성되기 때문에 결정 근거가 더 쉽게 사라진다.

Decision Log는 이 공백을 채우는 최소한의 판단 책임 기록이다.

---

## 2. 무엇을 입력으로 받고 무엇을 넘기는가

### Decision Log가 받는 입력

| 입력 소스 | 내용 |
|---|---|
| 정책 해석 결정 | 기본 규칙·예외·우선순위 판단 |
| 범위 변경 결정 | In Scope / Out of Scope 조정 |
| 운영 예외 승인 | 특수 케이스 처리 방침 |
| 보안/법무/운영 기준 결정 | 외부 기준 적용 판단 |

### Decision Log가 넘겨주는 출력

| 출력 | 내용 |
|---|---|
| 결정 근거 기록 | 왜 그렇게 결정했는가 — 재논의 방지 |
| 책임 소재 | 누가 결정했고 누가 승인했는가 |
| 관련 문서 연결 | 결정이 반영된 산출물 목록 |
| 영향 범위 | 어떤 후속 작업에 영향을 미치는가 |

---

## 3. Decision Log는 회의록과 무엇이 다른가

| 항목 | 회의록 | Decision Log |
|---|---|---|
| 기록 대상 | 논의 전반 | 최종 결정과 근거만 |
| 분량 | 상세 | 짧고 명확하게 |
| 목적 | 회의 내용 보존 | 결정 책임 추적 |
| 참조 시점 | 회의 직후 | 분쟁 발생 시, 정책 변경 시 |

Decision Log는 논의 과정이 아니라 **결론과 그 이유**만 남긴다.

---

## 4. 어떤 결정을 남겨야 하는가

모든 결정을 남길 필요는 없다. 아래 기준에 해당하는 결정은 반드시 남긴다.

- 정책 해석이 바뀐 경우
- 범위를 제외하거나 추가한 경우
- 운영 예외를 허용한 경우
- 보안/법무/운영 기준으로 중요한 판단을 내린 경우
- 나중에 "왜 이렇게 됐지?"라는 질문이 생길 만한 결정

## 5. 최소 항목과 템플릿

### 최소 항목

| 항목 | 내용 |
|---|---|
| 결정 ID | DEC-001 형태 |
| 결정 제목 | 한 줄 요약 |
| 결정 내용 | 무엇을 결정했는가 |
| 결정 이유 | 왜 그렇게 결정했는가 |
| 결정 일자 | YYYY-MM-DD |
| 결정자 / 승인자 | 역할 기준 |
| 관련 문서 | 결정이 반영된 산출물 |
| 영향 범위 | 후속 영향 항목 |

### 최소 템플릿

```md
## DEC-001 재가입 제한 기간 유지
- 결정 내용: 탈퇴 후 재가입 제한 기간은 30일로 유지한다.
- 결정 이유: 보안/운영 기준과 기존 정책 정합성 유지
- 일자: 2026-03-15
- 결정자: PO, 운영 책임자
- 관련 문서: 프로젝트 정책서, DMN, 사양서, 테스트케이스
- 영향 범위: 재가입 플로우, FAQ, 고객센터 응대 문구
```

## 6. 언제 갱신해야 하는가

| 갱신 트리거 | 내용 |
|---|---|
| 정책 해석이 바뀔 때 | 기존 결정 업데이트 또는 신규 등록 |
| 범위 제외/추가를 결정할 때 | 즉시 등록 |
| 운영 예외를 허용할 때 | 승인자 포함하여 등록 |
| 보안/법무 기준으로 결정할 때 | 근거 출처와 함께 등록 |

주 책임: PM/PO가 기록 책임, 승인권자가 최종 책임.

---

## 7. 이커머스 반품·환불 케이스에 적용하면

```md
## DEC-003 반품 허용 기간 7일은 정책서 Approved 후 변경 불가
- 결정 내용: 배송 완료 후 반품 허용 기간을 7일로 확정, 운영팀 예외 승인 없이 단독 변경 불가
- 결정 이유: 전자상거래법 최소 기준 준수 + CS 과부하 방지 분석 기반, 임의 변경 시 연쇄 산출물 불일치 발생
- 일자: 2026-03-20
- 결정자: PM, 법무 담당
- 관련 문서: 정책서 P-02, DMN 반품허용판단표, 사양서 F-05, 운영 FAQ
- 영향 범위: 반품 신청 판단 로직, 운영자 예외 처리 화면, 고객센터 응대 가이드
```

## 8. AI와 함께 Decision Log를 운영하는 실무 패턴

### AI에게 맡기기 좋은 일
- 회의 메모에서 결정 후보 항목 추출
- Decision Log 미반영 문서 후보 탐지
- 영향 범위 후보 생성

### 사람이 직접 보증해야 하는 일
- 결정 내용과 이유 최종 확정
- 승인 여부 확인
- 영향 범위 확정 및 관련 담당자 동기화

---

## 9. 품질 기준 / 체크리스트

- 논의가 아니라 결정이 남아 있는가
- 결정 이유가 한 줄 이상 남아 있는가
- 관련 문서와 영향 범위가 연결되는가
- 승인 주체가 명시되는가

---

## 10. 다음 단계 연결 규칙

| 상황 | 연결 |
|---|---|
| 결정이 정책서/사양서에 반영될 때 | Changelog에 변경 이력 추가 |
| 결정 관련 요구사항 확정 시 | RTM 해당 항목에 Decision Log 참조 추가 |
| 결정 번복 시 | 기존 결정 업데이트 + 신규 결정 등록 |

> 변경 이력은 **27장 제3절(Changelog)**에서 이어진다.

## 제3절. Changelog: 변경 이력

> **이 장에서 다루는 것**
> - Changelog의 역할과 릴리즈 노트와의 차이
> - 어떤 변경을 언제 기록해야 하는가
> - AI와 함께 Changelog를 운영하는 실무 패턴

> 요구사항 추적은 27장 제1절(RTM), 의사결정 이력은 27장 제2절(Decision Log)에서 다룬다.

> **전제 지식**: 27장 제2절(Decision Log) — 결정이 내려지면 그 결정이 산출물에 반영될 때 Changelog에 기록한다.

## 이 장의 목적

이 장은 Changelog가 무엇인지, 릴리즈 노트와 어떻게 다른지, 어떤 변경을 어떻게 남겨야 하는지를 설명한다. Changelog는 무엇이 언제 어떻게 바뀌었는지, 그리고 어떤 문서가 영향을 받았는지를 추적하는 변경 이력 문서다.

이 장을 읽고 나면 다음을 할 수 있어야 한다.

- Changelog가 RTM, Decision Log와 어떻게 다른지 설명할 수 있다.
- 어떤 변경을 Changelog에 남겨야 하는지 판단할 수 있다.
- 최소 Changelog 구조를 작성할 수 있다.

---

## 1. 이 산출물이 왜 존재하는가

산출물 체인이 길어질수록 변경 하나가 여러 문서에 파급된다. 정책서가 바뀌면 DMN이 바뀌고, DMN이 바뀌면 사양서가 바뀌고, 사양서가 바뀌면 테스트케이스가 바뀐다.

Changelog가 없으면 이런 상황이 생긴다.

- "이 사양서, 언제 바뀐 거야?"
- "이 TC가 현재 정책을 반영하고 있는 건가?"
- "정책이 바뀌었는데 어떤 문서를 업데이트해야 하지?"

AI 시대에는 문서 수정이 더 빠르고 잦아진다. Changelog는 이 변경의 투명성을 보장하고, 관련 문서 동기화 누락을 방지하는 기록이다.

---

## 2. Changelog는 릴리즈 노트와 무엇이 다른가

| 항목 | 릴리즈 노트 | Changelog (이 책 기준) |
|---|---|---|
| 대상 독자 | 사용자, 고객 | PM·개발·QA·설계 팀 내부 |
| 기록 범위 | 배포된 기능 변경 | 산출물과 기준 문서의 변경 |
| 작성 시점 | 배포 직전 | 문서 변경 발생 시 즉시 |
| 목적 | 사용자 안내 | 문서 동기화와 변경 추적 |

이 책에서 Changelog는 개발 릴리즈 노트가 아니라 **산출물과 기준의 변경을 추적하는 내부 문서**다.

---

## 3. 무엇을 입력으로 받고 무엇을 넘기는가

### Changelog가 받는 입력

| 입력 소스 | 내용 |
|---|---|
| 문서 버전 변경 | 정책서·사양서·BPMN·DMN·TC 등 수정 |
| Decision Log | 결정이 산출물에 반영될 때 |
| 운영 반영 이슈 | 운영 이슈가 설계 변경으로 이어질 때 |
| 릴리즈 배포 | 배포 완료 시점 기록 |

### Changelog가 넘겨주는 출력

| 출력 | 내용 |
|---|---|
| 변경 이력 | 버전·날짜·변경 내용·영향 문서 |
| 동기화 기준 | 어느 문서가 어느 버전 기준인지 |
| 다음 기획 입력 | 운영 반영 패턴 → RIB/PRD 갱신 근거 |

---

## 4. 어떤 변경을 남겨야 하는가

모든 오탈자 수정을 남길 필요는 없다. 아래 기준에 해당하는 변경은 반드시 남긴다.

- 문서 버전이 올라갈 때
- 주요 정책/규칙/조건이 수정될 때
- 릴리즈 기준이 바뀔 때
- 운영 반영이 설계 변경으로 이어질 때
- 영향 문서가 2개 이상인 변경이 발생할 때

---

## 5. 최소 항목과 템플릿

### 최소 항목

| 항목 | 내용 |
|---|---|
| 변경 일자 | YYYY-MM-DD |
| 변경 대상 문서 | 문서명 + 버전 |
| 변경 내용 요약 | 무엇이 바뀌었는가 |
| 변경 이유 | 왜 바뀌었는가 (Decision Log 참조 가능) |
| 영향 문서 | 함께 업데이트가 필요한 문서 목록 |

### 최소 템플릿

```md
## 2026-03-15 / 정책서 v1.1
- 변경 내용: 탈퇴 후 재가입 제한 기간 관련 예외 계정 규칙 추가
- 변경 이유: 운영 승인 예외 처리 요구 반영 (→ DEC-003 참조)
- 영향 문서: DMN v1.1, 사양서 v1.2, 테스트케이스 v1.1, FAQ
```

## 6. 언제 갱신해야 하는가

| 갱신 트리거 | 담당 |
|---|---|
| 문서 버전 올라갈 때 | 각 문서 오너가 1차 기록 |
| 주요 정책/사양 수정 시 | PM/PO 또는 BA가 영향 범위 정렬 |
| 릴리즈 완료 시 | PM이 배포 이력 추가 |
| 운영 이슈 설계 반영 시 | PM이 변경 근거와 함께 기록 |

---

## 7. 이커머스 반품·환불 케이스에 적용하면

```md
## 2026-03-20 / 정책서 v1.2
- 변경 내용: 운영자 예외 승인에 의한 구매확정 이후 반품 허용 조건 추가
- 변경 이유: CS 현장에서 불가피한 케이스 발생 → PO·법무 합의로 예외 경로 명문화 (→ DEC-003)
- 영향 문서: DMN v1.2 (반품허용판단표), 사양서 v1.3 (운영자 예외 승인 상태 전이), TC v1.1 (예외 승인 케이스), 고객센터 응대 가이드

## 2026-03-28 / 사양서 v1.3
- 변경 내용: 환불 처리 완료 후 반품 상태 COMPLETED 자동 전이 조건 명시
- 변경 이유: 개발팀 구현 과정에서 상태 전이 트리거 누락 발견
- 영향 문서: TC v1.2 (COMPLETED 전이 케이스 추가)
```

## 8. AI와 함께 Changelog를 운영하는 실무 패턴

### AI에게 맡기기 좋은 일
- 변경된 문서의 영향 문서 후보 목록 생성
- 두 버전 간 차이점 요약 초안 작성
- Changelog 미반영 문서 탐지

### 사람이 직접 보증해야 하는 일
- 영향 범위 확정
- 영향 문서 담당자 동기화 결정
- 릴리즈 이력 최종 확정

---

## 9. 품질 기준 / 체크리스트

- 무엇이 바뀌었는지 한눈에 보이는가
- 왜 바뀌었는지 설명이 있는가 (또는 Decision Log 참조가 있는가)
- 영향 문서 목록이 연결되는가
- 버전과 날짜가 남아 있는가

---

## 10. 다음 단계 연결 규칙

| 상황 | 연결 |
|---|---|
| Changelog에 영향 문서 기록 시 | 해당 문서 담당자 동기화 요청 |
| 운영 이슈가 반복될 때 | 패턴 분석 후 다음 RIB/PRD 입력 |
| 릴리즈 완료 기록 시 | RTM 배포 상태 갱신 입력 |

> RTM / Decision Log / Changelog 세 문서는 함께 있어야 산출물 체인이 흔들리지 않는다.
> - RTM은 연결을 추적한다 — "이 요구사항이 어디까지 구현됐는가"
> - Decision Log는 판단 근거를 기록한다 — "왜 이렇게 결정했는가"
> - Changelog는 변경 이력을 남긴다 — "무엇이 언제 왜 바뀌었는가"

세 문서가 순환한다. 정책이 바뀌면 Changelog에 기록되고, 그 변경 근거는 Decision Log에 남으며, 영향받은 요구사항 상태가 RTM에 반영된다. 어느 하나가 빠지면 나머지 두 문서도 신뢰할 수 없게 된다.

## 11. 세 문서의 역할 요약

| 문서 | 역할 | 핵심 질문 | 주요 독자 |
|---|---|---|---|
| **RTM** | 요구사항-구현-검증 연결 추적 | "이 요구사항이 구현·검증됐는가?" | QA, PM, 감리 |
| **Decision Log** | 결정 근거와 배경 기록 | "왜 이렇게 결정했는가?" | PM, 기획자, 신규 합류자 |
| **Changelog** | 산출물 변경 이력 | "무엇이 언제 어떤 이유로 바뀌었는가?" | 팀 전체, AI 컨텍스트 공급 |�
