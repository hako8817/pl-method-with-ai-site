# 12장. NFR (Non-Functional Requirements)

> **전제 지식**: 11장(PRD) — NFR은 PRD가 정의한 기능 목표가 "어떤 품질 수준으로 동작해야 하는가"를 정의한다. PRD의 기능 요구사항을 먼저 이해해야 성능·가용성·보안 기준의 맥락을 설정할 수 있다.

## 이 장의 목적

이 장은 PRD가 "무엇을 만드는가"를 정의한 뒤, 그것이 "어떤 수준으로 동작해야 하는가"를 정의하는 NFR(Non-Functional Requirements)을 다룬다.

NFR은 기능이 아니라 품질을 정의하는 문서다. 응답 속도가 얼마나 빨라야 하는가, 얼마나 많은 동시 접속을 감당해야 하는가, 어떤 보안 수준을 충족해야 하는가 — 이 질문들은 기능 명세에 들어가기 어렵지만 빠지면 개발과 운영 단계에서 뒤늦게 큰 문제로 나타난다.

이 장을 읽고 나면 독자는 다음을 할 수 있어야 한다.

- NFR이 왜 PRD와 분리되어 별도 문서로 관리되어야 하는지 설명할 수 있다.
- NFR의 주요 항목(성능·가용성·보안·유지보수성·규제 준수)을 구조화할 수 있다.
- AI와 함께 NFR 초안을 만들고 PM이 무엇을 확정해야 하는지 판단할 수 있다.
- NFR이 사양서·테스트케이스·SAD와 어떻게 연결되는지 이해한다.

---

## 1. 이 산출물이 왜 존재하는가

기능 요구사항만으로는 시스템이 얼마나 잘 동작해야 하는지를 알 수 없다. 결제 기능이 만들어졌어도 응답에 10초가 걸린다면 서비스가 될 수 없고, 주문 데이터를 다루는데 암호화 기준이 없다면 출시할 수 없다.

실무에서 NFR이 빠지는 데는 이유가 있다. 기능 요구사항은 눈에 보이는 결과물이 있지만 비기능 요구사항은 "당연히 해야 하는 것"으로 전제되어 문서화되지 않는 경우가 많다. 그 결과:

- 성능 목표 없이 개발이 완료된 뒤 성능 테스트에서 처음 기준이 나온다.
- 보안 요건을 뒤늦게 추가하면서 설계를 바꿔야 한다.
- SLA(서비스 수준 협약)와 실제 구현 목표가 처음부터 다른 방향을 본다.
- 규제 준수 요건이 출시 직전에 발견된다.

NFR은 이 상황을 막기 위해 PRD와 함께 초기에 정의되어야 한다. 기능 개발과 NFR은 동시에 설계되고 테스트케이스에서 함께 검증되어야 한다.

## 2. 무엇을 입력으로 받고 무엇을 넘기는가

**입력:**

| 입력 소스 | 내용 |
|----------|------|
| PRD | 서비스 범위, 대상 사용자 규모, 핵심 시나리오 |
| RIB | 제약 조건(규제·인프라·예산), 이해관계자 요건 |
| As-is 분석 | 현재 시스템 성능 현황, 알려진 병목, 운영 이슈 |
| 법규·컴플라이언스 | GDPR, 개인정보보호법, 금융 규제 등 외부 의무 |
| 인프라 제약 | 클라우드 환경, 예산, SLA 약정 |

**출력:**

| 다음 산출물 | NFR에서 넘겨주는 것 |
|------------|-------------------|
| **SAD** | 아키텍처 결정 기준 (성능·가용성 달성을 위한 구조 선택) |
| **사양서** | 기능별 성능 조건, 입력 검증 규칙, 에러 처리 기준 |
| **테스트케이스** | 성능 테스트 기준값, 부하 테스트 시나리오, 보안 테스트 체크포인트 |
| **운영 정책서(OPD)** | 운영 중 유지해야 할 성능·가용성 기준 |

## 3. NFR 구조와 주요 항목

NFR은 다음 다섯 카테고리로 구성한다. 모든 항목이 모든 프로젝트에 해당하지는 않는다. 해당 없는 항목은 "해당 없음 / 이유" 형태로 명시한다.

### 3-1. 성능 (Performance)

| 항목 | 기준 | 측정 조건 |
|------|------|-----------|
| 응답 시간 | 예: 95%ile 응답 3초 이내 | 일반 트래픽 기준 |
| 처리량 | 예: 분당 최대 1,000 TPS | 피크 트래픽 기준 |
| 동시 접속 | 예: 동시 사용자 10,000명 이상 | 서버 다운 없이 처리 |
| 페이지 로드 | 예: LCP 2.5초 이내 | Core Web Vitals 기준 |

### 3-2. 가용성 (Availability)

| 항목 | 기준 |
|------|------|
| SLA | 예: 99.9% uptime (월 약 43분 허용 다운타임) |
| 계획된 점검 | 예: 월 1회, 새벽 2~4시 허용 |
| 장애 복구 목표 | RTO: 1시간 이내, RPO: 4시간 이내 |

### 3-3. 보안 (Security)

| 항목 | 기준 |
|------|------|
| 인증 방식 | 예: OAuth 2.0 + JWT, MFA 지원 |
| 데이터 암호화 | 전송 중: TLS 1.2 이상 / 저장 중: AES-256 |
| 취약점 관리 | OWASP Top 10 기준 연 1회 이상 점검 |
| 접근 제어 | 최소 권한 원칙(Least Privilege), RBAC 기반 |
| 개인정보 처리 | 법정 보존 기간 준수, 탈퇴 후 익명화 처리 |

### 3-4. 유지보수성 (Maintainability)

| 항목 | 기준 |
|------|------|
| 배포 주기 | 예: 무중단 배포 가능, 롤백 10분 이내 |
| 로그 보존 | 예: 90일 이상 |
| 모니터링 | 핵심 지표 실시간 알림 |
| 테스트 커버리지 | 핵심 비즈니스 로직 단위 테스트 70% 이상 |

### 3-5. 규제 준수 (Compliance)

| 항목 | 해당 규제 | 준수 기준 |
|------|----------|-----------|
| 개인정보보호법 | 국내 정보통신망법 | 수집·보존·파기 규정 준수 |
| 접근성 | WCAG 2.1 AA | 장애인 사용자 접근성 |
| 결제 | PCI-DSS (해당 시) | 카드정보 처리 보안 기준 |

## 4. AI와 함께 만드는 법

### 4-1. 흐름 개요

```
PM 입력 준비 → AI 초안 생성 → PM 수치 확정 → AI 보완 → PM 최종 승인
```

### 4-2. AI에게 맡기는 단계

**단계 1: 입력 준비 및 초안 요청**

AI에게 다음 정보를 제공한다.
- PRD의 서비스 범위와 목표 사용자 규모
- RIB의 제약 조건(규제·인프라·예산)
- 현재 시스템 성능 현황(있는 경우)

```
아래 PRD 범위와 조건을 기반으로 NFR 초안을 작성해줘.
- 서비스: 중형 이커머스 플랫폼의 주문·결제·반품·환불 시스템
- 목표 규모: MAU 100만, 피크 동시접속 10,000명
- 규제: 국내 개인정보보호법, PCI-DSS 결제 보안 기준
- 인프라: AWS 기반
- 알려진 이슈: 주문 생성 API 응답 지연, 결제 처리 장애 빈번

NFR 항목: 성능·가용성·보안·유지보수성·규제 준수
각 항목별 정량 기준을 포함해줘.
측정 조건(피크/일반 트래픽 구분)도 명시해줘.
```

**AI가 잘하는 작업**: 업계 표준 기준값 제안, 항목 구조화, 누락 항목 후보 질문 생성, OWASP·WCAG 등 표준 체크리스트 초안 작성

**단계 2: 누락 항목 보완 요청**

```
위 NFR 초안에서 다음을 점검해줘.
1. 해당 없음으로 처리할 수 있는 항목과 이유
2. 규제 준수 항목 중 국내 서비스에서 추가 확인이 필요한 항목
3. 성능 기준 중 측정 조건이 빠진 항목
```

### 4-3. PM이 직접 판단·확정해야 하는 것

| 항목 | 이유 |
|------|------|
| 성능 수치 확정 | 인프라 비용·아키텍처 결정에 직접 영향 |
| SLA 수준 | 사업·계약 약정과 연결됨 |
| 규제 준수 범위 | 법무·컴플라이언스 담당자 검토 필요 |
| 보안 기준 | 보안 담당자 또는 외부 감사 기준 반영 필요 |
| 해당 없음 처리 | 어떤 항목을 적용 제외할지는 조직 맥락에서 결정 |

> **원칙**: AI는 업계 표준 기준값 초안을 빠르게 제안할 수 있다. 그러나 **우리 서비스의 SLA·비용·규제 범위 확정**은 사람이 한다.

## 5. 품질 기준 / 체크리스트

### 5-1. 필수 확인 (이것이 없으면 Feature 정의를 시작하면 안 된다)

- [ ] 모든 성능·가용성 기준이 측정 가능한 수치로 정의됐는가 ("빠르게" 대신 "95%ile 응답 3초 이내")
- [ ] 성능 기준에 측정 조건이 명시됐는가 (피크/일반 트래픽 구분)
- [ ] 보안 항목(인증 방식·암호화 적용 범위)이 명시됐는가
- [ ] 해당 법규·규제가 확인됐는가
- [ ] NFR 상태가 Approved 또는 팀 합의 완료 상태인가

### 5-2. 품질 향상 항목

- [ ] 각 NFR 항목이 어떻게 검증될지 방향이 있는가
- [ ] 성능·가용성 기준이 SAD(아키텍처) 결정에 반영됐는가
- [ ] 해당 없는 항목에 이유가 명시됐는가
- [ ] 컴플라이언스 항목이 법무·보안 담당자 검토를 거쳤는가

### 5-3. 자주 발생하는 오류

| 오류 유형 | 현상 | 수정 방향 |
|---|---|---|
| 정성 기준 | "빠르게", "안정적으로" 등 수치 없는 표현 | 측정 가능한 수치로 교체 (예: "95%ile 응답 3초 이내") |
| 측정 조건 누락 | 기준값은 있지만 어떤 조건에서인지 없음 | 피크/일반 트래픽 등 측정 조건 명시 |
| NFR 후주입 | 개발 완료 후 성능 기준을 처음 정함 | PRD와 동시에 초기 작성, 테스트케이스와 함께 검증 |
| 규제 항목 공백 | 컴플라이언스 섹션이 비어 있음 | 해당 없으면 "해당 없음 / 이유" 명시 필수 |

## 6. 다음 단계 연결 규칙

### 6-1. NFR → Feature/Scenario/AC 전환 조건

다음 조건이 충족되어야 Feature 정의를 시작한다.

- 성능 기준(응답시간·TPS)이 측정 가능한 수치로 확정되었다
- 보안 항목(인증 방식·암호화 적용 범위)이 명시되었다
- SLA 수치가 사업팀 합의 기반으로 확정되었다
- 해당 법규·규제가 확인되었다
- NFR 상태가 Approved 또는 팀 합의 완료 상태다

### 6-2. NFR이 열어주는 병렬 작업

NFR이 확정되면 다음 산출물을 병렬로 시작할 수 있다.

| 병렬 가능 산출물 | NFR에서 받는 것 |
|---|---|
| Feature/Scenario/AC | 성능·보안 조건을 AC에 반영할 기준값 |
| SAD | 아키텍처 결정의 근거 기준 (성능·가용성 목표) |
| 테스트케이스(성능·보안) | 부하 테스트·보안 테스트 시나리오 기준값 |

### 6-3. NFR에서 해결하지 않는 것

NFR은 다음을 결정하지 않는다.

- 기능 범위와 구현 우선순위 (→ PRD·Feature 정의에서)
- 구체적인 API 설계나 에러 코드 (→ 사양서에서)
- 아키텍처 패턴 선택 (→ SAD에서)
- 배포 절차와 롤백 방법 (→ 운영 정책서에서)

NFR에 구현 조건이 섞이면 SAD·사양서와 역할이 중복된다.

---

## 7. 이 장의 핵심 메시지

> NFR은 시스템이 "무엇을 하는가"가 아니라 "얼마나 잘 해야 하는가"를 정의한다.

기능 개발과 NFR은 함께 설계되어야 한다. NFR이 뒤늦게 추가되면 아키텍처 재설계, 개발 재작업, 출시 지연으로 이어진다. PRD가 방향을 정했다면 NFR은 그 방향의 품질 기준을 정한다.

---

## 8. 다음 장으로의 연결

NFR이 완성되면 Feature 정의가 시작될 준비가 된다. NFR 없이 Feature·AC를 쓰면 성능·보안 조건이 AC에서 누락되고 나중에 사양서에서 억지로 채워야 한다.

### NFR에서 Feature/Scenario/AC로 이동하는 항목

| NFR 항목 | 이동 형태 | Feature/AC에서의 역할 |
|---|---|---|
| 성능 기준 (응답시간, TPS) | 수치 기준 (예: "2초 이내") | AC의 성능 조건절로 직접 삽입 |
| 보안 기준 (인증 방식, 암호화) | 적용 조건과 예외 | AC의 보안 조건절 |
| 가용성 기준 (SLA, RTO) | 수치 기준 | 운영 복구 관련 시나리오 AC |
| 규제 요건 (개인정보 처리) | 적용 대상 데이터 범위 | 개인정보 관련 시나리오 AC |
| 유지보수 기준 (배포 빈도) | 최대 허용 다운타임 | 배포 관련 운영 시나리오 AC |

### 체인 전환 기준 (NFR → Feature/Scenario/AC)

| 확인 항목 | 기준 |
|---|---|
| 성능 기준 수치화 | 응답시간·TPS 기준이 측정 가능한 숫자로 확정되어 있는가 |
| 보안 항목 완성 | 인증 방식과 암호화 적용 범위가 명시되어 있는가 |
| SLA 수치 확정 | 가용성 목표값이 사업팀 합의 기반으로 확정되어 있는가 |
| NFR 상태 | `Approved` 또는 팀 합의 완료 상태인가 |

- **이 장이 결정한 것**: 성능·가용성·보안·유지보수·컴플라이언스 기준값
- **다음 장이 시작하는 것**: Feature 정의, 시나리오 흐름, AC 작성 — NFR 조건이 AC에 반영된 상태로 시작
