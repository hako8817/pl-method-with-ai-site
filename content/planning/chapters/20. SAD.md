# 20장. SAD (System Architecture Document)

> **전제 지식**: 11장(PRD), 12장(NFR), 16장(프로젝트 정책서) — SAD는 PRD의 방향과 NFR의 품질 기준, 정책서의 제약 조건을 아키텍처 구조로 연결한다. 세 산출물의 내용을 먼저 이해해야 SAD 검토 기준을 잡을 수 있다.

## 이 장의 목적

이 장은 시스템이 어떤 구성 요소로 이루어지고 그 요소들이 어떻게 연결되는지를 정의하는 **SAD(System Architecture Document)**를 다룬다.

기획자가 아키텍처를 직접 설계하지는 않는다. 그러나 SAD는 기획자가 검토하고 승인에 관여해야 할 문서다. 이유는 하나다. NFR에서 정한 성능·가용성·보안 기준이 실제 아키텍처에서 달성 가능한지를 기획자가 확인하지 않으면, 나중에 "설계대로 구현했지만 요건을 충족하지 못한다"는 상황이 생긴다.

이 장을 읽고 나면 독자는 다음을 할 수 있어야 한다.

- SAD가 왜 기획자의 검토 대상이 되어야 하는지 설명할 수 있다.
- C4 Model 기반 아키텍처 문서의 구성과 각 레벨의 역할을 이해한다.
- AI와 함께 SAD 초안을 만들고 PM이 무엇을 검토해야 하는지 판단할 수 있다.
- SAD가 사양서·API 명세서·운영 정책서와 어떻게 연결되는지 이해한다.

---

## 1. 이 산출물이 왜 존재하는가

요구사항이 명확하게 정의됐더라도 시스템 구조가 그것을 지탱하지 못하면 출시 후 문제가 생긴다. 가장 흔한 패턴은 이렇다.

- 성능 요건은 있지만, 아키텍처가 그것을 달성하기에 부적합하다는 것이 개발 완료 후 발견된다.
- 외부 서비스(본인인증, 결제 게이트웨이)와의 연동 방식이 기획 단계에서 전제됐는데, 실제 아키텍처와 달라 재설계가 필요해진다.
- 어떤 시스템이 어느 데이터에 접근하는지 정의하지 않아, 운영 중 데이터 유출 경로가 문서화되지 않은 채 남는다.
- 장애 복구 시나리오(RTO, RPO)가 아키텍처 결정과 연결되지 않는다.

SAD는 시스템 구성과 연결 방식을 명시화해서, **기획 단계의 요구사항이 구현 가능한 구조 위에 올라가 있는지를 검증하는 기준 문서**다.

기획자 관점에서 SAD를 검토하는 것은 기술적 상세를 이해하기 위해서가 아니라, 자신이 정의한 요건(NFR, 정책서, 권한 정책)이 아키텍처에 반영됐는지 확인하기 위해서다.

## 3. SAD 구조 (C4 Model 기반)

이 책에서는 C4 Model의 네 레벨을 기준으로 SAD를 구성한다. 기획자가 집중해야 하는 레벨은 Context와 Container다.

### 3-1. Level 1: System Context (시스템 컨텍스트)

시스템과 외부 요소(사용자, 외부 시스템) 간의 관계를 보여준다.

```
[구매자]      → [주문·결제 시스템] → [결제 PG사 (토스페이먼츠)]
                                  → [배송사 API]
                                  → [알림 시스템 (SMS/이메일)]
[판매자]      → [판매자 어드민]   → [주문·결제 시스템]
[운영자]      → [운영자 어드민]   → [주문·결제 시스템]
                                  → [정산 시스템]
```

기획자 검토 포인트: 모든 외부 시스템 연동이 포함됐는가? 데이터 흐름 방향이 정책과 일치하는가?

### 3-2. Level 2: Container (컨테이너)

시스템 내부의 주요 구성 단위와 그 역할을 보여준다.

| 컨테이너 | 역할 | 기술 스택(예시) |
|---------|------|----------------|
| Buyer App | 구매자 UI (웹/모바일) | React / React Native |
| Seller Portal | 판매자 어드민 | React |
| Admin Portal | 운영자 어드민 (CS/정산) | React |
| Order Service | 주문 생성·관리 API | Node.js / Spring Boot |
| Payment Service | 결제 처리·PG 연동 | Node.js / Spring Boot (PCI-DSS) |
| Shipping Service | 배송 추적·반품 처리 | Node.js |
| Refund Service | 환불 처리·정산 | Node.js |
| Order Database | 주문·반품·환불 데이터 | PostgreSQL |
| Cache | 주문 상태·결제 세션 | Redis |
| Message Queue | 비동기 이벤트 (주문→결제→배송) | Kafka / SQS |
| Notification Service | SMS/이메일 발송 | AWS SES / 써드파티 |

기획자 검토 포인트: NFR의 성능·가용성 요건을 이 구조가 달성할 수 있는가? 결제·반품 정책이 서비스 분리에 반영됐는가? 보안 경계(PCI-DSS)가 명확한가?

### 3-3. Level 3·4: Component / Code

개발팀이 주도하는 영역이다. 기획자는 컴포넌트 레벨에서 외부 연동 인터페이스와 보안 경계를 검토하는 데 집중한다.

## 4. AI와 함께 만드는 법

### 단계 1: 입력 준비

AI에게 다음을 제공한다.
- NFR의 성능·가용성·보안 기준
- PRD의 주요 기능과 외부 시스템 연동 목록
- 기존 인프라 환경(클라우드, DB, 인프라 제약)

### 단계 2: AI 초안 생성

**Step 2-1: NFR + 외부 연동 → 아키텍처 초안**

```
아래 요건을 기반으로 C4 Model Level 1~2 수준의 시스템 아키텍처 초안을 작성해줘.

서비스: 이커머스 플랫폼 주문·결제·반품·환불 시스템
NFR:
- 피크 동시접속 10,000명, 주문 생성 API 응답 2초 이내, 결제 처리 3초 이내
- 99.9% 가용성 (월간 다운타임 43분 이내)
- PCI-DSS 준수, 결제 정보 암호화, 개인정보 보호법 준수
외부 연동: 결제 PG사(토스페이먼츠), 배송사 API, 알림 서비스(SMS/이메일)
환경: AWS 기반, PostgreSQL, Redis, Kafka

포함 항목:
1. 주요 컨테이너(Container) 목록과 역할
2. 컨테이너 간 통신 방식과 프로토콜 (REST API, 메시지 큐)
3. 외부 시스템(PG사, 배송사) 연결 구조와 이중화
4. 가용성·보안 요건 달성을 위한 구조 선택 (Load Balancer, Multi-AZ, PCI-DSS 경계 등)
표와 구조 설명을 함께 작성해줘.
```

**Step 2-2: NFR 달성 가능성 점검**

초안이 나오면 NFR 요건이 구조적으로 지원되는지 확인한다.

```
아래 SAD 초안이 NFR 요건을 구조적으로 지원하는지 점검해줘.

[NFR 요건]
- 피크 동시접속 10,000명, 주문 생성 2초 이내, 결제 처리 3초 이내
- 99.9% 가용성
- 장애 복구 목표: RTO 1시간, RPO 4시간
- 보안: PCI-DSS 준수, TLS 1.2 이상, 개인정보 암호화(AES-256)
- 규제: 개인정보보호법 준수, 배송 추적 데이터 보존 정책

[SAD 초안]
(위에서 생성된 내용 붙여넣기)

점검 항목:
1. 응답시간 요건을 달성하기 위한 캐시·CDN·DB 구조가 있는가
2. 99.9% 가용성을 위한 이중화·페일오버 구조가 있는가
3. RTO/RPO 달성을 위한 백업·복구 전략이 포함됐는가
4. JWT 만료 정책이 아키텍처에 반영됐는가
5. 외부 연동(PASS, SES) 실패 시 처리 방식이 정의됐는가
```

### 단계 3: PM 검토 기준

기획자가 SAD에서 확인해야 할 것은 기술 상세가 아니라 다음이다.

| 확인 항목 | 이유 |
|----------|------|
| NFR 달성 가능성 | 성능·가용성 기준이 구조적으로 지원되는가 |
| 외부 연동 완결성 | 정책서·PRD에서 정의한 외부 연동이 모두 포함됐는가 |
| 보안 경계 | 역할별 접근 가능 영역이 권한 매트릭스와 일치하는가 |
| 데이터 흐름 | ERD의 엔티티가 올바른 컨테이너에서 관리되는가 |
| 장애 복구 | RTO/RPO 달성을 위한 구조적 장치가 있는가 |

## 5. 품질 기준 / 체크리스트

| 항목 | 확인 기준 |
|------|-----------|
| NFR 연결 | 성능·가용성·보안 요건이 아키텍처 결정에 반영됐는가 |
| 외부 시스템 | PRD와 정책서에서 정의한 모든 외부 연동이 포함됐는가 |
| 보안 경계 | 인증·인가 처리 위치가 명확한가 |
| 데이터 저장 | ERD의 주요 엔티티가 올바른 컨테이너에 배치됐는가 |
| 장애 복구 | RTO/RPO 달성 방안이 구조에 포함됐는가 |
| 미결정 사항 | 아직 결정되지 않은 기술 선택이 명시됐는가 |
| 승인 상태 | Draft / Review / Approved 상태가 표시됐는가 |

## 6. 다음 단계 연결 규칙

- **사양서**: SAD의 컴포넌트 인터페이스를 기능별 상세 조건으로 전개
- **API 명세서**: 컨테이너 간 통신 인터페이스를 API 스펙으로 전환
- **운영 정책서(OPD)**: 아키텍처 기반 장애 복구 절차, 인프라 운영 기준 정의
- **테스트케이스**: NFR 기준값을 바탕으로 성능·부하·장애 복구 테스트 시나리오 생성

---

## 7. 이 장의 핵심 메시지

> SAD는 개발팀이 만들고 기획자가 검토하는 문서다. 기획자가 확인해야 할 것은 기술 상세가 아니라, 자신이 정의한 요건이 이 구조에서 달성 가능한지다.

NFR과 정책서, 권한 매트릭스에서 정의한 내용이 아키텍처에 반영되지 않으면 개발 완료 후 재설계가 필요해진다. SAD 검토는 그 재설계 비용을 설계 단계에서 미리 줄이는 과정이다.

---

## 8. 다음 장으로의 연결

SAD가 확정되면 각 컴포넌트의 기능 단위로 내려가 "구현 가능한 조건"으로 상세화할 차례다. SAD의 컴포넌트 경계가 사양서의 기능 분류 기준이 된다.

### SAD에서 사양서로 이동하는 항목

| SAD 항목 | 이동 형태 | 사양서에서의 역할 |
|---|---|---|
| 컴포넌트 목록 | 서비스·모듈 단위 | 사양서의 기능 분류 단위 |
| 외부 시스템 인터페이스 | 인터페이스 목록 + 프로토콜 | 사양서의 인터페이스 정의 |
| 기술 스택 결정 | 언어·프레임워크·DB 목록 | 사양서의 구현 조건 제약 |
| 보안 경계 | 인증·암호화 적용 위치 | 사양서의 보안 구현 조건 |
| NFR 달성 구조 | 성능·가용성 달성 방식 | 사양서의 성능 조건 구현 방법 |
| 이벤트 흐름 | 비동기 처리 구조 | 사양서의 이벤트 처리 조건 |

### 체인 전환 기준 (SAD → 사양서)

| 확인 항목 | 기준 |
|---|---|
| 컴포넌트 경계 확정 | 각 컴포넌트의 책임 범위가 명시되어 있는가 |
| 인터페이스 정의 존재 | 외부 시스템과의 연동 방식이 기재되어 있는가 |
| 기술 스택 확정 | 개발팀과 합의된 기술 스택이 기재되어 있는가 |
| SAD 상태 | `Approved` 상태인가 |

- **이 장이 결정한 것**: 시스템 컴포넌트 구조, 외부 인터페이스, 기술 스택, 보안 경계
- **다음 장이 시작하는 것**: 컴포넌트 단위로 내려가 기능별 구현 조건을 작성하는 사양서
