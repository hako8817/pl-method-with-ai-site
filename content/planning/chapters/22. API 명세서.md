# 22장. API (Application Programming Interface) 명세서

> **전제 지식**: 21장(사양서), 20장(SAD), 16장(권한 정책 매트릭스) — API 명세서는 사양서의 기능별 구현 조건과 SAD의 컴포넌트 인터페이스 구조, 권한 매트릭스의 역할 정의를 API 스펙으로 전환한다. 세 산출물을 먼저 이해해야 엔드포인트 설계와 에러 코드 체계의 기준을 잡을 수 있다.

## 이 장의 목적

이 장은 서비스 컴포넌트 간, 또는 외부 시스템과의 인터페이스를 정의하는 **API 명세서(API Specification)**를 다룬다.

API 명세서는 개발자가 작성한다고 생각하기 쉽다. 그러나 API 명세서의 구조와 내용은 기획자가 정의한 사양서와 권한 정책을 직접 반영해야 한다. API 명세서가 없거나 부실하면 프론트엔드-백엔드 간 협의가 구두로만 이루어지고, 외부 연동 파트너와의 계약 조건이 모호해지며, QA가 응답값 기준을 잡지 못한다.

이 장을 읽고 나면 독자는 다음을 할 수 있어야 한다.

- API 명세서가 사양서·권한 정책·테스트케이스와 어떻게 연결되는지 설명할 수 있다.
- OpenAPI(Swagger) 기반 API 명세서의 주요 구성 항목을 이해한다.
- AI와 함께 API 명세서 초안을 만들고 PM이 무엇을 검토해야 하는지 판단할 수 있다.

---

## 1. 이 산출물이 왜 존재하는가

기능이 사양서에서 정의됐더라도 실제 구현 단계에서 다음 문제가 반복된다.

- 프론트엔드와 백엔드가 요청/응답 포맷을 각자 다르게 이해하고 구현한다.
- 에러 코드 정의가 없어서 클라이언트가 "서버 에러"와 "비즈니스 에러"를 구분하지 못한다.
- 외부 연동(본인인증, 결제) API의 응답 처리 방식이 문서 없이 코드에만 남는다.
- 권한 체크 로직이 API마다 달리 구현된다.

API 명세서는 **시스템 간 인터페이스를 계약 수준으로 명시화**한다. "어떤 요청을 보내면 어떤 응답이 돌아오는가"가 문서로 정의되어 있을 때, 개발팀은 서로 독립적으로 작업하고 QA는 명확한 기준으로 검증할 수 있다.

## 2. 무엇을 입력으로 받고 무엇을 넘기는가

**입력:**

| 입력 소스 | 내용 |
|----------|------|
| 사양서 | 기능별 상세 조건, 상태값, 에러 케이스 |
| 권한 정책 매트릭스 | API별 허용 역할, 인증 방식 |
| SAD | 컴포넌트 간 인터페이스 구조 |
| 데이터 모델(ERD) | 요청/응답에 포함되는 엔티티 구조 |

**출력:**

| 다음 산출물 | API 명세서에서 넘겨주는 것 |
|------------|---------------------------|
| **테스트케이스** | API 응답 기준값, 에러 케이스, 권한 케이스 |
| **운영 정책서(OPD)** | API 버전 관리 정책, Deprecation 절차 |
| **프로토타입** | 실제 API 응답 기반 화면 데이터 구조 |

## 3. API 명세서 구조

### 3-1. 엔드포인트 정의 기본 항목

각 API 엔드포인트는 다음 항목을 포함한다.

| 항목 | 내용 |
|------|------|
| Method | GET / POST / PUT / DELETE / PATCH |
| Path | `/api/v1/members/{memberId}` |
| Summary | 한 줄 설명: "회원 정보 조회" |
| 인증 방식 | Bearer Token (JWT) / API Key / 없음 |
| 허용 역할 | OPERATOR, ADMIN (권한 매트릭스 참조) |
| Request | Path Params / Query Params / Request Body |
| Response | 200 성공 응답 / 에러 응답 목록 |

### 3-2. 요청/응답 예시 (반품 신청)

**요청:**
```
POST /api/v1/orders/{orderId}/returns
Authorization: Bearer {access_token}
Content-Type: application/json

{
  "reason": "상품 불량",
  "reasonType": "DEFECT",
  "items": [
    {
      "orderItemId": "oi-5678",
      "quantity": 1
    }
  ]
}
```

**성공 응답 (200/201):**
```json
{
  "returnId": "ret-1234",
  "orderId": "ord-5678",
  "status": "PENDING",
  "createdAt": "2026-03-31T10:00:00Z",
  "estimatedPickupDate": "2026-04-02T00:00:00Z",
  "refundAmount": 25000
}
```

**에러 응답 목록:**

| HTTP 코드 | 에러 코드 | 설명 |
|-----------|-----------|------|
| 400 | ORDER_001 | 잘못된 주문 ID 형식 |
| 401 | AUTH_001 | 인증 토큰 없음 또는 만료 |
| 404 | ORDER_002 | 존재하지 않는 주문 |
| 422 | RETURN_001 | 반품 가능 기간 초과 |
| 422 | RETURN_002 | 반품 불가 상태 (구매확정, 배송 미완료 등) |

### 3-3. 에러 코드 체계

API 명세서는 에러 코드를 **HTTP 상태코드 + 비즈니스 에러코드**로 이중 정의한다.

| HTTP 상태코드 | 용도 |
|--------------|------|
| 400 | 클라이언트 입력 오류 (유효성 검사 실패) |
| 401 | 인증 실패 (토큰 없음·만료) |
| 403 | 권한 없음 (인증은 됐지만 접근 불가) |
| 404 | 리소스 없음 |
| 409 | 충돌 (중복 데이터) |
| 422 | 비즈니스 규칙 위반 (정책서 기반 거부) |
| 500 | 서버 내부 오류 |

비즈니스 에러코드는 `{도메인}_{순번}` 형태로 정의한다. 예: `MEMBER_001`, `AUTH_002`

### 3-4. API 버전 관리 원칙

| 항목 | 기준 |
|------|------|
| 버전 표기 | URL Path 기반: `/api/v1/`, `/api/v2/` |
| 하위 호환성 | Minor 변경은 기존 버전에 추가, Breaking 변경은 새 버전 발행 |
| Deprecation | 구 버전 지원 종료 최소 3개월 전 공지 |

## 4. AI와 함께 만드는 법

### 단계 1: 입력 준비

AI에게 다음을 제공한다.
- 사양서의 기능별 상세 조건
- 권한 정책 매트릭스
- ERD의 관련 엔티티 구조

### 단계 2: AI 초안 생성

**Step 2-1: 엔드포인트 + 요청/응답 스키마 초안**

```
아래 사양 기준으로 반품·환불 관련 REST API 명세 초안을 작성해줘.

[기능]
- 반품 신청 조회: 본인(BUYER 역할) / 판매자(SELLER) / 운영자(OPERATOR 이상)
- 반품 상태 변경 (판매자 수락·거부): SELLER 이상만 가능
- 반품 예외 승인 (정책 외 케이스 수동 처리): OPERATOR 이상만 가능

[공통 조건]
- 인증: JWT Bearer Token
- 응답 포맷: JSON
- 에러 코드 체계: RETURN_XXX, ORDER_XXX 형식

각 API별 다음 항목을 포함해줘:
1. Method + Path
2. 인증 방식과 허용 역할
3. Request 파라미터 또는 Body (필드명·타입·필수여부)
4. Response 200 성공 예시 (JSON)
5. 에러 응답 목록 (HTTP 코드 + 에러 코드 + 설명)
```

**Step 2-2: 에러 코드 완결성 점검**

초안이 나오면 정책서의 거부 케이스가 모두 API 에러로 정의됐는지 점검한다.

```
아래 정책서의 거부 케이스와 API 명세서 초안을 비교해서 누락된 에러 코드를 찾아줘.

[정책서 거부 케이스]
- 구매확정 이후 반품 신청 → 거부 (RETURN_001)
- 반품 허용 기간(7일) 초과 → 거부 (RETURN_002)
- 판매자 미수락 상태에서 수거 요청 → 거부 (RETURN_003)
- SELLER 미만 역할 → 반품 상태 변경 거부 (RETURN_004)
- 존재하지 않는 주문 ID → 조회 거부 (ORDER_001)
- 환불 API 연동 실패 → 환불 처리 불가 (RETURN_005)

[API 명세서 초안]
(위에서 생성된 내용 붙여넣기)

1. 정책서 거부 케이스 중 API 에러로 정의되지 않은 것
2. HTTP 상태코드와 비즈니스 에러코드가 함께 정의되지 않은 것
3. 역할별 거부 케이스가 누락된 엔드포인트
를 각각 목록으로 알려줘.
```

AI가 잘 하는 작업: 엔드포인트 구조화, 요청/응답 스키마 생성, 에러 케이스 목록화, 정책-에러코드 정합성 점검

### 단계 3: PM 검토 기준

| 항목 | 이유 |
|------|------|
| 권한 체크 반영 | 권한 매트릭스와 API별 허용 역할 일치 확인 |
| 에러 코드 완결성 | 정책서의 거부 케이스가 422 에러로 모두 정의됐는가 |
| 응답 데이터 범위 | 역할별 마스킹 항목이 응답 스키마에 반영됐는가 |
| 외부 연동 API | 본인인증·결제 연동 API 응답 처리가 포함됐는가 |

## 5. 품질 기준 / 체크리스트

| 항목 | 확인 기준 |
|------|-----------|
| 엔드포인트 완결성 | 사양서의 모든 기능이 API로 정의됐는가 |
| 인증·권한 | 모든 API에 인증 방식과 허용 역할이 명시됐는가 |
| 에러 코드 | HTTP 상태코드와 비즈니스 에러코드가 모두 정의됐는가 |
| 응답 스키마 | 성공 응답의 모든 필드가 ERD와 정합하는가 |
| 정책 반영 | 정책서의 거부 케이스가 422 에러로 커버됐는가 |
| 버전 관리 | API 버전 규칙이 명시됐는가 |
| 승인 상태 | Draft / Review / Approved 상태가 표시됐는가 |

## 6. 다음 단계 연결 규칙

- **테스트케이스**: API 응답 기준값과 에러 코드가 TC의 검증 기준이 됨
- **프로토타입**: 실제 API 응답 구조 기반으로 UI 데이터 바인딩 설계 가능
- **운영 정책서(OPD)**: API 버전 Deprecation 절차, 장애 대응 시 API 롤백 기준
- **RTM**: 요구사항 → 사양서 → API → TC 추적 경로 완성

## 7. 이 장의 핵심 메시지

> API 명세서는 개발자 간 구두 협의를 계약으로 바꾸는 문서다.

API 명세서가 있으면 프론트엔드·백엔드·QA·운영이 같은 인터페이스 기준으로 작업한다. API 명세서가 없으면 그 기준이 코드 안에 숨는다. AI 시대에 API 명세서는 AI가 테스트케이스를 생성하고 통합 검증을 자동화할 때의 핵심 입력이기도 하다.

## 8. 다음 장으로의 연결

API가 확정되면 사용자가 실제로 경험하는 화면 흐름을 검토할 차례다. API의 Response 구조가 화면 레이아웃의 데이터 기반이 되고, 에러 응답이 에러 화면 설계의 기준이 된다.

### API 명세서에서 프로토타입으로 이동하는 항목

| API 항목 | 이동 형태 | 프로토타입에서의 역할 |
|---|---|---|
| Response 데이터 구조 | JSON 필드·타입 목록 | 화면에 표시되는 데이터 레이아웃 설계 기준 |
| 에러 응답 코드·메시지 | 에러 코드-사용자 메시지 매핑 | 에러 화면 / Toast / Alert 설계 |
| Endpoint 목록 | URL + HTTP 메서드 | 화면 전환 시 API 연결 지점 표시 |
| Pagination 구조 | 페이지·커서 파라미터 | 목록 화면의 더보기·무한스크롤 설계 |
| 인증 실패 응답 | 401/403 처리 흐름 | 권한 없음 안내·반품 불가 안내 화면 |

### 체인 전환 기준 (API → 프로토타입)

| 확인 항목 | 기준 |
|---|---|
| 주요 Endpoint 확정 | 핵심 화면과 연결되는 API Endpoint가 정의되어 있는가 |
| 에러 응답 목록 존재 | 사용자에게 표시될 에러 케이스가 정의되어 있는가 |
| Response 스키마 완성 | 화면에 표시할 데이터 필드가 Response에 포함되어 있는가 |
| API 명세서 상태 | `Approved` 또는 개발팀 합의 완료 상태인가 |

- **이 장이 결정한 것**: Endpoint 구조, Request/Response 스키마, 에러 코드 체계
- **다음 장이 시작하는 것**: API 응답 구조를 기반으로 사용자 경험 흐름을 프로토타입으로 검토
