# 14장. Scenario와 Acceptance Criteria: 동작과 완료 기준

> **이 장에서 다루는 것**
> - Scenario: Feature가 어떤 상황에서 어떻게 동작해야 하는가
> - Acceptance Criteria: 완료를 판단하는 합의 기준 (Given/When/Then)
> - Scenario → AC → TC로 이어지는 1:1 연결 구조

---

## 제1절. Scenario: 동작 시나리오

> **이 장에서 다루는 것**
> - Scenario의 정의, 구조, 유형 (정상·예외·경계)
> - 상태 기반 시나리오 설계 원칙
> - AI와 함께 Scenario 초안을 만드는 법
> - 샘플: F-02 이메일 로그인 Scenario 전체 (8개)

> **전제 지식**: 13장(Feature Spec) — Scenario는 Feature 단위로 작성된다. Feature가 확정되어야 Scenario를 시작할 수 있다.
> **다음 연결**: 14장 제2절(AC) — Scenario의 기대 결과가 AC의 Then 조건이 된다.

---

## 1. 이 산출물이 왜 존재하는가

Feature가 "무엇을 만드는가"를 정의한다면, Scenario는 "그것이 어떤 상황에서 어떻게 동작해야 하는가"를 정의한다.

Feature 하나는 여러 상황에서 작동한다. 이메일 로그인이라는 Feature 하나만 해도 다음 상황이 모두 다르게 처리되어야 한다.

- 정상: 올바른 이메일·비밀번호로 로그인
- 실패: 비밀번호 1~2회 틀림
- 잠금: 3회 실패 후 AUTO_LOCKED 전환
- 잠금 재시도: 잠금 상태에서 다시 시도
- 관리자 잠금: ADMIN_LOCKED 상태
- 휴면: DORMANT 상태 계정
- 만료: 세션이 만료된 상태에서 재접근
- 탈퇴: WITHDRAWN 계정 로그인 시도

이 여덟 개는 모두 "이메일 로그인"이라는 같은 Feature이지만 동작이 다르다. Scenario가 없으면 이 차이가 개발자 재량으로 결정된다.

**Scenario가 없을 때 생기는 일**

| 상황 | 결과 |
|---|---|
| 정상 흐름만 정의 | 예외 처리를 개발자가 임의로 구현 |
| 예외를 열거하지 않음 | 테스트가 정상 흐름만 검증 |
| 상태 기준 없이 시나리오 작성 | 같은 상황을 두 사람이 다르게 이해 |
| Scenario 없이 AC 작성 | AC의 Given이 막연해짐 |

## 2. 무엇을 입력으로 받고 무엇을 넘기는가

### 2-1. Scenario가 받는 입력

| 입력 소스 | 내용 |
|---|---|
| Feature 목록 | 어떤 기능의 시나리오인지 — Feature ID와 책임 범위 |
| PRD | 핵심 시나리오·성공 기준 — 정상 흐름의 출발점 |
| 상태 모델 | 엔티티 상태 목록 — 상태별 시나리오 분기 기준 |
| 정책서 초안 | 허용·차단·예외 규칙 — 예외 시나리오 도출 근거 |
| As-is 분석 | 현재 발생하는 예외 케이스 — 놓치기 쉬운 엣지케이스 발굴 |

### 2-2. Scenario가 넘겨주는 출력

| 다음 산출물 | 받는 것 |
|---|---|
| **AC** | 각 Scenario의 전제 상태 + 기대 결과 → Given / Then 조건 |
| **BPMN** | Scenario 흐름 → 노드·게이트웨이 검증 기준 |
| **DMN** | 판단이 필요한 분기 → 의사결정 테이블 후보 |
| **사양서** | Scenario의 전제 상태 + 기대 결과 → 상태·메시지·API 항목 |
| **테스트케이스** | Scenario 하나 = TC 그룹 하나 (AC 기준으로 세분화) |

## 3. Scenario의 구조

Scenario 하나는 아래 항목으로 구성된다.

| 항목 | 설명 | 작성 기준 |
|---|---|---|
| **Scenario ID** | 고유 식별자 | Feature ID + 순번. 예: F02-SC-01 |
| **Scenario명** | 한 줄 설명 | "정상 로그인", "3회 실패 → 잠금 전환" |
| **유형** | 정상 / 예외 / 경계 | 아래 유형 분류 참조 |
| **관련 Feature** | Feature ID | F-02 |
| **전제 상태** | 이 Scenario가 시작되는 조건 | "회원 상태: ACTIVE, 실패 횟수: 0" |
| **행동** | 사용자 또는 시스템이 하는 것 | "이메일·비밀번호를 입력하고 [로그인] 클릭" |
| **기대 결과** | 화면 결과 + 상태 결과 | "세션 발급, 메인 페이지 이동, 실패 횟수 초기화" |
| **예외 조건** | 이 Scenario에서 발생 가능한 추가 예외 | "네트워크 오류, 동시 요청 중복 등" |

## 4. Scenario의 세 가지 유형

모든 Feature는 세 가지 유형의 Scenario를 포함해야 한다.

### 정상 시나리오 (Happy Path)

기능이 의도한 대로 완료되는 경로. 보통 1~2개.

```
예: 이메일·비밀번호를 올바르게 입력하고 로그인 성공
```

### 예외 시나리오 (Exception Path)

정상 경로가 아닌 모든 분기. 대부분의 기능에서 예외가 정상보다 많다.

```
예: 비밀번호 불일치 / 잠금 계정 / 휴면 계정 / 탈퇴 계정 / 서버 오류
```

### 경계 시나리오 (Edge Case)

상태나 수치의 경계에서 발생하는 케이스. 자주 놓친다.

```
예: 실패 횟수가 정확히 3회째일 때 / 잠금 해제 카운트다운이 0이 됐을 때 /
    두 기기에서 동시에 로그인할 때 / 비밀번호 변경 직후 기존 세션으로 API 호출
```

## 5. 상태 기반 시나리오 설계

Scenario를 설계할 때 가장 효과적인 방법은 **상태 모델에서 시작하는 것**이다.

엔티티의 상태값이 n개이면, 그 상태에서 이 Feature가 동작할 때 어떤 결과가 나와야 하는지 표로 먼저 정리한다.

**회원 상태 × 로그인 시도 매트릭스 (F-02)**

| 회원 상태 | 로그인 시도 결과 | Scenario |
|---|---|---|
| `PENDING_VERIFY` | 거부 (AUTH_001 반환, 인증 미완료 미노출) | F02-SC-06 |
| `ACTIVE` (실패 0~2회) | 실패 횟수 증가, AUTH_001 반환 | F02-SC-02, 03 |
| `ACTIVE` (실패 3회) | AUTO_LOCKED 전환, AUTH_002 반환 | F02-SC-04 |
| `AUTO_LOCKED` | 거부, AUTH_003 + 카운트다운 | F02-SC-05 |
| `ADMIN_LOCKED` | 거부, AUTH_004 + 고객센터 안내 | F02-SC-07 |
| `DORMANT` | 거부, AUTH_007 + 고객센터 안내 | F02-SC-08 |
| `WITHDRAWN` | 거부, MEMBER_002 | F02-SC-09 |
| `ACTIVE` (정상) | 성공, 세션 발급 | F02-SC-01 |

이 매트릭스를 먼저 그리면 Scenario 목록이 자연스럽게 도출된다.

## 6. AI와 함께 Scenario를 만드는 법

### Step 1: 상태 매트릭스 → Scenario 목록 도출

**프롬프트**

```
아래 Feature와 상태 모델을 보고 Scenario 목록을 도출해줘.

규칙:
- 각 상태에서 이 Feature가 동작할 때 어떤 결과가 나와야 하는지 하나씩 Scenario로 만들 것
- 정상 시나리오 / 예외 시나리오 / 경계 시나리오로 분류할 것
- 상태 매트릭스(상태 × Feature 행동 = 결과)를 먼저 표로 정리하고, 그 다음 Scenario 목록 출력

[Feature]
Feature ID: F-05
Feature명: 반품 신청 및 처리
책임: 배송 완료 후 7일 이내 반품을 신청하고 수거·환불을 처리한다.

[상태 모델]
주문 상태: 배송완료 / 구매확정
반품 상태: (신청 전) / RETURN_REQUESTED / RETURN_COLLECTING / RETURN_COLLECTED / RETURN_APPROVED / RETURN_REJECTED / REFUND_PROCESSING

[정책]
- P-02: 배송 완료 후 7일 이내만 반품 신청 가능
- P-03: 구매확정 후 반품 불가
- P-05: 판매자 귀책 반품 시 배송비 판매자 부담
- P-06: 반품 환불은 원결제 수단으로 처리 (운영 예외 승인 시 대체 가능)
```

### Step 2: 각 Scenario 상세 작성

**프롬프트**

```
아래 Scenario 목록의 각 항목을 다음 형식으로 상세화해줘.

형식:
- Scenario ID / 명
- 유형 (정상 / 예외 / 경계)
- 전제 상태 (회원 상태, 실패 횟수, 세션 상태 등)
- 행동 (사용자가 무엇을 하는가)
- 기대 결과 (화면 + 상태 변화 + 오류 코드)
- 추가 예외 조건

[Scenario 목록]
(붙여넣기)
```

**PM 검토 기준**

| 확인 항목 | 기준 |
|---|---|
| 상태 커버 완전성 | 엔티티의 모든 상태에서 이 Feature의 동작이 정의됐는가 |
| 예외 실재성 | AI가 만든 예외 케이스가 실제 운영에서 발생하는 상황인가 |
| 경계값 포함 | "딱 3회째", "15분 정확히 경과 직후" 같은 경계 케이스가 있는가 |
| 정책 연결 | 각 Scenario의 결과가 정책서 규칙에서 나왔는가 |

## 7. 샘플: F-05 반품 신청 및 처리 — Scenario 전체 (8개)

### F05-SC-01: 정상 반품 신청 (정상)

```
유형     : 정상
전제 상태 : 주문 상태 구매확정 / 배송 완료일로부터 3일 경과
행동     : 구매자가 반품 사유를 선택하고 [반품 신청] 클릭
기대 결과 :
  - 화면: 반품 신청 완료 안내 페이지로 이동 (신청 번호 표시)
  - 상태: 반품 상태 → RETURN_REQUESTED / requestedAt = 현재 시각 저장
  - 상태: 주문 상태는 유지 (구매확정)
  - 로그: 반품 신청 이벤트 기록
```

### F05-SC-02: 반품 기한 내 신청 — 남은 기한 표시 (예외)

```
유형     : 예외
전제 상태 : 주문 상태 구매확정 / 배송 완료일로부터 1일 경과
행동     : 구매자가 반품 사유를 선택하고 [반품 신청] 클릭
기대 결과 :
  - 화면: 반품 신청 완료 안내 + "반품 가능 기간: 앞으로 N일 남음"
  - 상태: 반품 상태 → RETURN_REQUESTED
  - 상태: deadlineAt = 배송 완료 + 7일 서버 기준 저장
  - 로그: 반품 신청 이벤트 + 남은 기한 기록
```

### F05-SC-03: 반품 기한 초과 시도 (예외)

```
유형     : 예외
전제 상태 : 주문 상태 구매확정 / 배송 완료일로부터 8일 경과
행동     : 구매자가 반품을 시도할 때 반품 버튼 클릭
기대 결과 :
  - 화면: RETURN_001 오류 — "반품 가능 기간이 지났습니다. 배송 완료 후 7일 이내에만 신청 가능합니다."
  - 상태: 변화 없음
  - 버튼: [반품 신청] 버튼 비활성화 + 회색으로 표시
```

### F05-SC-04: 판매자 귀책 반품 신청 (예외)

```
유형     : 예외
전제 상태 : 주문 상태 구매확정 / 배송 완료일로부터 3일 경과 / 반품 사유: "상품 결함"
행동     : 구매자가 반품 사유를 "상품 결함"으로 선택하고 [반품 신청] 클릭
기대 결과 :
  - 화면: 반품 신청 완료 + "배송비 전액 환불 예정" 안내 표시
  - 상태: 반품 상태 → RETURN_REQUESTED / reasonType = SELLER_FAULT
  - 상태: refundType = FULL (배송비 포함 환불) 마킹
  - 노트: 운영팀 검토 없이 자동 승인 (P-05 정책)
```

### F05-SC-05: 수거 진행 중 (예외)

```
유형     : 예외
전제 상태 : 반품 상태 RETURN_REQUESTED / 반품 신청 후 1일 경과
행동     : 배송사 연동으로 수거 상태가 자동 업데이트될 때
기대 결과 :
  - 화면: 구매자의 반품 조회 페이지에 "수거 예정" → "수거 중" 상태 변경 표시
  - 상태: 반품 상태 → RETURN_COLLECTING / collectorTrackingNo = 배송사 API에서 수신한 추적번호
  - 상태: collectionDeadlineAt = 수거사 예정 도착일 저장
  - 로그: 배송사 API 응답 및 상태 전환 기록
```

### F05-SC-06: 수거 완료 후 상품 검사 (경계)

```
유형     : 경계
전제 상태 : 반품 상태 RETURN_COLLECTING / 수거 완료 상태 API 수신
행동     : 배송사에서 수거 완료 이벤트 발생, 반품 물품 반입
기대 결과 :
  - 상태: 반품 상태 → RETURN_COLLECTED / collectedAt = 수거 완료 시각 저장
  - 화면: 구매자 UI에 "상품 검수 중" 상태 표시
  - 로그: 수거 완료 이벤트 + 예상 환불 일정 기록
  - 운영: 운영팀 큐에 자동 할당 (검수 필요)
```

### F05-SC-07: 운영팀 반품 거부 (예외)

```
유형     : 예외
전제 상태 : 반품 상태 RETURN_COLLECTED / 운영팀이 반품 사유를 검수 (예: 구매자 귀책 확인)
행동     : 운영팀이 [반품 거부] 버튼 클릭 후 거부 사유 입력
기대 결과 :
  - 화면: 운영팀 어드민에서 "반품 거부 완료" 확인 메시지
  - 상태: 반품 상태 → RETURN_REJECTED / rejectedAt = 현재 시각 저장
  - 화면: 구매자에게 "반품 신청이 거부되었습니다. [거부 사유 보기]" 안내 표시
  - 로그: 거부 결정 + 거부 사유 + 운영자 ID 기록
주의    : 구매자 귀책으로 거부할 경우, 반품/왕복 배송비 공제 후 환불 결정
```

### F05-SC-08: 환불 처리 (예외)

```
유형     : 예외
전제 상태 : 반품 상태 RETURN_APPROVED / 환불 대기 (3시간 이내 환불 처리)
행동     : 시스템 자동 또는 운영팀 수동 환불 버튼 클릭
기대 결과 :
  - 상태: 반품 상태 → REFUND_PROCESSING / refundRequestedAt = 현재 시각 저장
  - 상태: 결제 PG사에 환불 API 호출, 응답 반영
  - 화면: 구매자에게 "환불이 처리 중입니다. 2~3일 소요됩니다" 안내 표시
  - 로그: 환불 요청 API 호출 + 응답 코드 기록
```

### 엣지케이스 별도 목록

| 케이스 | 예상 동작 | 비고 |
|---|---|---|
| 배송 완료 정확히 7일 후 신청 | RETURN_REQUESTED 허용 | 데드라인 7일 포함 (RETURN-P-01) |
| 반품 신청 후 배송사 수거 연동 실패 | 운영팀 수동 개입 | 2시간 이내 재시도, 실패 시 고객센터 연락 |
| 배송사가 수거 불가 응답 (접근 불가) | 반품 신청 상태 유지 + 구매자에게 배송사 문의 안내 | RETURN-P-02 |
| 반품 수거 중 구매자 취소 요청 | 배송사 수거 취소 API 호출 (가능 시) | 운영팀 판단 필요 |
| 동일 상품 복수 반품 신청 | 각각 독립 반품 신청으로 처리 | 상품별 추적 번호 별도 발급 |

## 8. 품질 기준 / 체크리스트

**구조 기준**
- [ ] 각 Scenario에 전제 상태 / 행동 / 기대 결과 (화면+상태) 가 있는가
- [ ] 정상 / 예외 / 경계 유형이 모두 포함됐는가
- [ ] 상태 모델의 모든 상태가 Scenario에서 커버됐는가

**내용 기준**
- [ ] 기대 결과에 화면 결과와 상태 변화가 모두 있는가
- [ ] 예외 Scenario에 오류 코드와 사용자 메시지가 연결됐는가
- [ ] 경계 케이스 (딱 n회, 정확히 만료 시점 등)가 포함됐는가

**연결 기준**
- [ ] 각 Scenario의 결과가 정책서 규칙에 근거하는가
- [ ] 상태 매트릭스 (상태 × Feature = 결과)를 작성하고 Scenario를 도출했는가
- [ ] AI가 생성한 Scenario를 PM이 실제 운영 관점에서 검증했는가

## 9. 다음 단계 연결 규칙 — Scenario → AC 변환 규칙

Scenario가 완성되면 각 Scenario의 기대 결과를 검증 가능한 기준(AC)으로 변환한다.

### 항목별 매핑 규칙

각 Scenario의 구성 항목은 다음 규칙으로 AC의 구성 항목에 매핑된다.

| Scenario 항목 | AC 항목 | 변환 기준 |
|---|---|---|
| **전제 상태** | **Given** | 상태값·수치를 명시적 조건으로 기술. "ACTIVE, 실패 횟수 2" |
| **행동** | **When** | 주체(사용자·시스템) + 행동을 그대로 기술 |
| **기대 결과 — 화면** | **Then** 첫 항목 | 위치·문구·노출 방식까지 포함 |
| **기대 결과 — 상태 변화** | **And** (상태 항목) | 변경 전→후 명시. "AUTO_LOCKED로 전환" |
| **기대 결과 — 오류 코드** | **And** (코드 항목) | HTTP 상태 코드 + 비즈니스 에러 코드 모두 기술 |
| **예외 조건** | **And** 또는 별도 AC | 연쇄 동작이면 And, 독립 케이스이면 별도 AC로 분리 |

**변환 원칙:**
- Scenario 하나 = AC 하나 이상
- 기대 결과 항목 수 = Then + And 항목 수 (기대 결과가 4개이면 Then 1개 + And 3개)
- "화면 결과 + 상태 변화 + 오류 코드" 세 가지가 모두 Then/And에 포함되어야 강한 AC

### 변환 예시: F02-SC-04 → AC-03

**Scenario (F02-SC-04: 3회 실패 → AUTO_LOCKED)**

```
전제 상태 : 회원 상태 ACTIVE / 실패 횟수 2
행동      : 잘못된 비밀번호 입력 후 [로그인] 클릭
기대 결과 :
  - 화면:  AUTH_002 오류 + "계정이 잠겼습니다" 메시지 + [비밀번호 재설정] 링크
  - 상태:  회원 상태 → AUTO_LOCKED / unlockAt = 현재 시각 + 15분 저장
  - 코드:  AUTH_002 반환
```

↓ 항목별 매핑 규칙 적용

**AC (AC-03: 3회 실패 → AUTO_LOCKED 전환)**

```
Given  회원 상태가 ACTIVE이고 실패 횟수가 2인 상태에서       ← 전제 상태
When   잘못된 비밀번호를 입력하고 [로그인] 버튼을 클릭하면     ← 행동
Then   회원 상태가 AUTO_LOCKED로 전환되고                   ← 기대 결과 · 상태 변화
And    서버에 unlockAt = 현재 시각 + 15분이 저장되며          ← 기대 결과 · 상태 변화
And    AUTH_002 오류가 반환되고                             ← 기대 결과 · 오류 코드
And    화면에 "계정이 잠겼습니다. 15분 후 재시도하거나 비밀번호를 재설정하세요."
       메시지와 [비밀번호 재설정] 링크가 함께 표시된다         ← 기대 결과 · 화면
```

> **이 장이 결정한 것**: 각 Feature의 동작 흐름, 상태별 기대 결과, 예외·경계 케이스 목록
> **다음 장이 시작하는 것**: Scenario의 기대 결과를 Given/When/Then 구조의 AC로 변환

> **다음 연결**: 16장(정책서) — AC의 조건절·예외 케이스가 정책 규칙으로 전환된다. / 24장(테스트케이스) — AC 1개 = TC 1개.

## 1. 이 산출물이 왜 존재하는가

기능이 완료됐다는 것을 팀이 공통으로 판단할 수 있어야 한다. 개발자는 "구현했다"고 하고, QA는 "버그가 있다"고 하고, PM은 "이건 다르다"고 하는 상황이 반복되는 이유는 완료 기준이 없어서다.

Acceptance Criteria(AC)는 **"이 조건들이 모두 충족되면 이 기능이 완료됐다고 본다"는 합의 기준**이다.

AC가 있으면:
- 개발자가 "어디까지 만들어야 하는가"를 명확히 안다
- QA가 무엇을 어떻게 검증할지 AC 그대로 테스트케이스를 만든다
- PM이 "이 기능이 맞게 만들어졌는가"를 AC 기준으로 판단한다
- AI가 코드를 생성할 때 AC를 입력으로 받아 구현 범위를 제한한다

AC가 없으면:
- 각자 다른 기준으로 "완료"를 판단한다
- QA가 테스트 기준을 만들기 위해 기획자에게 계속 질문한다
- AI가 생성한 코드가 실제 요구와 다른지 확인하기 어렵다

## 3. AC의 구조: Given / When / Then

AC를 작성하는 가장 표준적이고 효과적인 구조는 세 파트로 구성된다.

| 파트 | 역할 | 내용 |
|---|---|---|
| **Given** | 전제 조건 | 이 AC가 적용되는 상태·환경 |
| **When** | 행동 | 사용자 또는 시스템이 취하는 행동 |
| **Then** | 기대 결과 | 그 행동의 결과 — 화면 / 상태 변화 / 오류 코드 |

Then은 하나로 끝나지 않는다. 대부분의 AC는 Then이 여러 항목으로 구성된다.

```
Given  회원 상태가 ACTIVE이고 실패 횟수가 2인 상태에서
When   잘못된 비밀번호를 입력하고 [로그인] 버튼을 클릭하면
Then   AUTH_002 오류가 반환되고
And    회원 상태가 AUTO_LOCKED으로 전환되며
And    unlockAt이 현재 시각 + 15분으로 서버에 저장되고
And    화면에 "[비밀번호 재설정]" 링크가 함께 표시된다
```

## 4. 약한 AC vs 강한 AC

AC를 작성할 때 가장 흔한 실수는 결과가 모호한 문장으로 끝내는 것이다.

### 비교: 약한 AC → 강한 AC

| 약한 AC (❌) | 강한 AC (✅) |
|---|---|
| 로그인이 안전하게 처리되어야 한다 | 실패 3회 시 AUTO_LOCKED로 전환되고 AUTH_002가 반환된다 |
| 잠긴 계정은 적절히 안내한다 | AUTH_003이 반환되고 서버 unlockAt 기준 카운트다운이 표시된다 |
| 비밀번호가 틀리면 오류를 보여준다 | "이메일 또는 비밀번호를 확인해주세요. (N/3회 실패)" 문구가 [로그인] 버튼 하단에 인라인으로 표시된다 |
| 로그인 성공 시 메인으로 이동한다 | 이전 접근 URL이 있으면 해당 URL로, 없으면 서비스 메인 페이지로 이동한다 |
| 관리자 계정은 보안 처리한다 | ADMIN 역할 계정의 첫 번째 실패 시 보안팀 Slack 채널에 알림이 발송된다 |

### 약한 AC를 강하게 만드는 방법

약한 AC가 나오는 패턴과 수정 방법:

| 패턴 | 예시 | 수정 방향 |
|---|---|---|
| **동사가 모호** | "적절히 처리한다", "안전하게 한다" | 구체적 동작으로 대체: "AUTH_003을 반환한다", "세션을 REVOKED로 전환한다" |
| **화면 결과 없음** | "오류가 발생한다" | 위치 + 문구 + 노출 방식 명시: "[로그인] 버튼 하단에 인라인으로 빨간색 텍스트로 표시" |
| **상태 변화 없음** | "로그인이 차단된다" | 상태 전환 명시: "회원 상태가 AUTO_LOCKED로 전환된다" |
| **조건이 불완전** | "비밀번호가 틀리면" | 전제 조건까지 명시: "실패 횟수가 2인 상태에서 비밀번호가 틀리면" |
| **결과가 하나뿐** | "오류 코드가 반환된다" | 연쇄 결과까지: "오류 코드 반환 + 상태 변경 + 화면 표시 + 로그 기록" |

## 5. AC → TC 1:1 연결 원칙

AC 하나는 TC 하나로 직접 변환된다.

```
AC:
Given  회원 상태가 AUTO_LOCKED이고 unlockAt이 현재 시각 이후인 상태에서
When   이메일·비밀번호를 입력하고 [로그인]을 클릭하면
Then   AUTH_003 오류가 반환되고
And    서버 unlockAt 기준 카운트다운이 화면에 표시되며
And    [로그인] 버튼이 비활성화 상태로 표시된다

↓ 변환

TC:
전제조건 : 회원 상태 = AUTO_LOCKED, unlockAt = 현재 시각 + 5분
입력     : 이메일·비밀번호 입력 후 [로그인] 클릭
기대결과 :
  1. 응답 코드: AUTH_003
  2. 화면: "계정이 잠겨있습니다. 자동 해제까지: 4분 XX초" 텍스트 표시
  3. [로그인] 버튼: disabled 상태
  4. 카운트다운: 서버 unlockAt 기준으로 감소 (클라이언트 시각 아님)
```

AC의 Then 항목이 TC의 기대결과 항목이 된다. Then이 4개이면 기대결과 검증 항목도 4개다.

## 6. AI와 함께 AC를 작성하는 법

### Step 1: Scenario → AC 변환

**프롬프트**

```
아래 Scenario를 Given / When / Then 구조의 Acceptance Criteria로 변환해줘.

규칙:
- Then에는 반드시 세 가지를 포함할 것:
  1. 화면에 무엇이 표시되는가 (문구·위치·방식)
  2. 시스템 상태가 어떻게 바뀌는가 (DB·세션·카운터)
  3. 오류가 있다면 어떤 오류 코드가 반환되는가
- "적절히", "안전하게", "잘" 같은 모호한 표현은 구체적 조건으로 바꿀 것
- 하나의 Scenario에서 Then 항목이 여러 개이면 And로 연결할 것

[Scenario]
(붙여넣기)
```

### Step 2: AC 누락 점검

**프롬프트**

```
아래 AC 목록을 검토하고 다음 관점에서 누락된 항목을 찾아줘.

1. 모든 상태 (ACTIVE / AUTO_LOCKED / ADMIN_LOCKED / DORMANT / WITHDRAWN)에 대한 AC가 있는가
2. 경계값 케이스 (정확히 N회째, 만료 시각 직전/직후)가 빠지지 않았는가
3. 화면 결과 / 상태 변화 / 오류 코드 세 가지가 모든 AC에 있는가
4. 비기능 조건 (응답 시간, 로그 기록 여부)이 누락됐는가

[AC 목록]
(붙여넣기)
```

**PM 검토 기준**

| 확인 항목 | 기준 |
|---|---|
| 테스트 가능성 | AC를 그대로 TC로 변환할 수 있는가 |
| 관찰 가능성 | Then이 화면·상태·로그로 확인 가능한 결과인가 |
| 완전성 | Scenario에서 정의한 모든 기대 결과가 AC에 담겼는가 |
| 모호함 제거 | "적절히", "잘" 같은 판단 기준 없는 표현이 없는가 |
| 정책 정합성 | AC 조건이 정책서 규칙과 충돌하지 않는가 |

## 7. 샘플: F-02 이메일 로그인 — AC 전체

### AC-01: 정상 로그인

```
Given  회원 상태가 ACTIVE이고
       올바른 이메일·비밀번호를 입력한 상태에서
When   [로그인] 버튼을 클릭하면
Then   세션이 발급되고 (유효기간 24시간, AUTH-P-01)
And    이전 접근 시도 URL이 있으면 해당 URL로, 없으면 서비스 메인 페이지로 이동하며 (LOGIN-P-03)
And    해당 계정의 실패 횟수가 0으로 초기화된다 (LOGIN-P-01)
```

### AC-02: 1~2회 실패 — 횟수 누적 안내

```
Given  회원 상태가 ACTIVE이고 실패 횟수가 0 또는 1인 상태에서
When   잘못된 비밀번호를 입력하고 [로그인] 버튼을 클릭하면
Then   AUTH_001 오류가 반환되고
And    [로그인] 버튼 하단에 "이메일 또는 비밀번호를 확인해주세요. (N/3회 실패)" 문구가 인라인으로 표시되며
And    실패 횟수가 1 증가하고
And    회원 상태는 ACTIVE를 유지한다
```

*2회차 추가 조건*:
```
And    "1회 더 실패 시 계정이 잠깁니다." 경고 문구가 추가로 표시된다
```

### AC-03: 3회 실패 → AUTO_LOCKED 전환

```
Given  회원 상태가 ACTIVE이고 실패 횟수가 2인 상태에서
When   잘못된 비밀번호를 입력하고 [로그인] 버튼을 클릭하면
Then   회원 상태가 AUTO_LOCKED로 전환되고
And    서버에 unlockAt = 현재 시각 + 15분이 저장되며 (서버 기준 시각, AUTH-P-02)
And    AUTH_002 오류가 반환되고
And    화면에 "로그인 실패 횟수 초과로 계정이 잠겼습니다. 15분 후 재시도하거나 비밀번호를 재설정하세요." 메시지와 [비밀번호 재설정] 링크가 함께 표시된다
```

### AC-04: AUTO_LOCKED 상태 재시도 — 카운트다운

```
Given  회원 상태가 AUTO_LOCKED이고 서버 unlockAt이 현재 시각 이후인 상태에서
When   이메일·비밀번호를 입력하고 [로그인] 버튼을 클릭하면
Then   AUTH_003 오류가 반환되고
And    서버 unlockAt을 기준으로 계산한 카운트다운 (N분 N초)이 화면에 표시되며 (클라이언트 시각 기준 아님, LOGIN-P-02)
And    [로그인] 버튼이 비활성화(disabled) 상태로 표시되고
And    [비밀번호 재설정] 링크가 제공되며
And    카운트다운이 0이 되면 [로그인] 버튼이 자동으로 활성화된다 (페이지 새로고침 없음)
```

### AC-05: 15분 경과 후 AUTO_LOCKED 자동 해제

```
Given  회원 상태가 AUTO_LOCKED이고 서버 unlockAt이 현재 시각 이전(만료)인 상태에서
When   올바른 이메일·비밀번호를 입력하고 [로그인] 버튼을 클릭하면
Then   로그인이 성공하고
And    회원 상태가 ACTIVE로 전환되며
And    세션이 발급된다
```

### AC-06: ADMIN_LOCKED 계정 로그인 시도

```
Given  회원 상태가 ADMIN_LOCKED인 상태에서
When   이메일·비밀번호를 입력하고 [로그인] 버튼을 클릭하면
Then   AUTH_004 오류가 반환되고
And    "계정이 관리자에 의해 잠겼습니다. 고객센터에 문의해주세요." 메시지가 표시되며
And    자동 해제 경로가 제공되지 않고
And    [비밀번호 재설정] 링크가 미표시된다
```

### AC-07: 관리자(ADMIN) 계정 첫 번째 실패 → Slack 알림

```
Given  role이 ADMIN인 계정의 이메일을 입력하고
When   잘못된 비밀번호를 입력하고 [로그인] 버튼을 클릭하면 (1회차부터)
Then   AUTH_001 오류가 화면에 표시되고 (일반 계정과 동일)
And    동시에 보안팀 Slack 채널에 알림이 발송된다 (AUTH-P-06)
And    실패 횟수가 1 증가한다
```

## 8. 품질 기준 / 체크리스트

**구조 기준**
- [ ] 모든 AC가 Given / When / Then 구조를 갖추고 있는가
- [ ] Then에 화면 결과 / 상태 변화 / 오류 코드가 모두 포함됐는가
- [ ] AC가 Scenario와 1:1 대응되는가

**내용 기준**
- [ ] "적절히", "잘", "안전하게" 같은 모호한 표현이 없는가
- [ ] Given 조건이 특정 상태값과 수치로 명시됐는가
- [ ] Then이 관찰 가능한 결과(화면·코드·상태)로 기술됐는가

**연결 기준**
- [ ] AC → TC로 직접 변환할 수 있는가 (TC 1개 = AC 1개)
- [ ] AC 조건이 정책서 규칙에서 나왔는가 (정책 ID 참조 표기 권장)
- [ ] 모든 엔티티 상태 (ACTIVE / LOCKED / DORMANT 등)에 대한 AC가 있는가
- [ ] 비기능 조건 (로그 기록, 응답 시간) 이 필요하면 포함됐는가

## 9. AC, Scenario, TC의 관계 정리

세 산출물은 같은 내용을 다른 관점으로 기술한다.

| 산출물 | 관점 | 기술 방식 |
|---|---|---|
| **Scenario** | "이 상황에서 무슨 일이 일어나는가" | 자연어 서술 (전제 상태 + 행동 + 기대 결과) |
| **AC** | "이 기능이 완료됐다고 볼 수 있는 기준은 무엇인가" | Given/When/Then 구조의 조건-결과 명세 |
| **TC** | "이것을 어떻게 검증할 것인가" | 전제조건 + 입력값 + 실행 단계 + 기대결과 |

```
Scenario: "AUTO_LOCKED 상태에서 로그인을 시도하면 카운트다운이 표시된다"
    ↓
AC: Given AUTO_LOCKED / When 로그인 클릭 / Then AUTH_003 + 카운트다운 + 버튼 비활성화
    ↓
TC: 전제: 상태=AUTO_LOCKED, unlockAt=현재+5분 / 입력: 이메일·비밀번호 입력 후 클릭 /
    기대: AUTH_003 응답 + "4분 XX초" 텍스트 노출 + 버튼 disabled
```

## 10. 다음 단계 연결 규칙

AC가 완성되면 두 방향으로 연결된다.

**정책서 방향**: AC의 Given 조건과 Then 결과에 담긴 규칙이 정책서로 이동한다.

| AC 항목 | 정책서 전환 형태 |
|---|---|
| Given의 상태 조건 | 정책 적용 대상 조건 |
| Then의 결과 규칙 | 조건-결과 정책 항목 |
| 경계값 (3회, 15분) | 정책서 수치 기준 |
| 예외 처리 방식 | 예외 처리 정책 |

**테스트케이스 방향**: AC 하나가 TC 하나로 전환된다.

| AC 파트 | TC 파트 |
|---|---|
| Given | 전제조건 (테스트 환경 준비 사항) |
| When | 테스트 입력 및 실행 단계 |
| Then | 기대결과 (검증 항목) |
| And | 추가 기대결과 (검증 항목 추가) |

> **이 장이 결정한 것**: 기능별 완료 기준 (AC), Given/When/Then 조건-결과 명세
> **다음 장이 시작하는 것**: AC의 조건절·예외 케이스를 정책 규칙으로 구조화
