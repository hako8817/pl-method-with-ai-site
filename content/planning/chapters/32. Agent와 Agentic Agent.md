# 32장. Agent와 Agentic Agent

> 이 장은 AI 실행 단위의 두 계층을 다룬다. Agent(에이전트)는 목표가 주어지면 스스로 판단하고 실행하는 단일 AI 실행 단위다. Agentic Agent(에이전틱 에이전트)는 여러 에이전트가 역할을 분담하여 협업하는 구조다. 단일 에이전트가 충분한 상황과 멀티 에이전트 구조가 필요한 상황을 구분하는 것이 이 장의 핵심이다.

> **전제 지식**: 31장(Skill, Harness Engineering, Harness Operating Environment) — 에이전트는 스킬과 하네스를 실행 단위로 묶어 자율적으로 동작하는 구조다. 스킬과 하네스 개념을 먼저 이해해야 에이전트와의 관계와 차이를 명확히 볼 수 있다.

---

## 제1절. Agent: 에이전트

## 이 장의 목적

이 장은 에이전트(Agent)의 개념과 기획 실무에서의 의미를 다룬다. 에이전트는 목표가 주어지면 스스로 판단하고, 장애물을 만나면 우회하고, 상황을 다시 평가하면서 목표까지 도달하는 AI 실행 단위다. 프롬프트나 스킬이 "이렇게 해라"라는 지시 기반이라면, 에이전트는 "목표는 이것이다, 나머지는 스스로 판단해서 해라"는 자율 기반이다.

이 장을 읽고 나면 다음을 이해해야 한다.

- 에이전트가 기존 AI 활용 방식과 어떻게 다른지
- 에이전트가 자율적으로 행동한다는 것이 실무에서 무엇을 의미하는지
- 에이전트를 쓸 수 있는 상황과 사람이 개입해야 하는 지점
- 에이전트의 한계와 위험 요소

---

## 1. 에이전트란 무엇인가

에이전트는 목표를 받고, 그 목표를 달성하기 위해 스스로 계획하고, 도구를 사용하고, 결과를 평가하고, 다음 행동을 결정하는 AI 실행 단위다.

비유로 표현하면 이렇다. 어떤 길을 걸어가는 사람에게 "저기 건물까지 가라"고 하면, 그 사람은 스스로 판단한다.

- 웅덩이를 만나면 피한다.
- 공사 구간을 만나면 우회한다.
- 막힌 골목을 만나면 다른 길을 찾는다.

목표는 건물이고, 어떻게 갈지는 그 사람이 판단한다. 에이전트가 하는 일이 이것과 같다.

기존 AI 활용 방식은 대부분 "이 작업을 해줘"라는 단발 요청이다. 에이전트는 다르다. "이 목표를 달성해줘"라고 하면 AI가 스스로 작업을 쪼개고, 도구를 쓰고, 진행 상태를 점검하고, 오류가 생기면 다른 방법을 시도하면서 결과까지 간다.

---

## 2. 에이전트의 작동 방식

에이전트는 일반적으로 다음 사이클로 작동한다.

**계획 수립**: 주어진 목표를 달성하기 위해 어떤 단계를 거쳐야 하는지 계획한다.

**실행**: 계획의 첫 단계를 실행한다. 도구(검색, 파일 접근, API 호출 등)를 사용한다.

**결과 평가**: 실행 결과가 기대와 맞는지 확인한다.

**다음 행동 결정**: 기대와 맞으면 다음 단계로, 맞지 않으면 다른 방법을 시도하거나 계획을 수정한다.

이 사이클이 반복되면서 에이전트는 목표를 향해 나아간다. 중간에 예상치 못한 상황이 생겨도 스스로 판단해서 대응한다.

---

## 3. 에이전트가 기획 실무에서 할 수 있는 것

### 에이전트 목표 설정 예시: 산출물 연쇄 검증

에이전트를 실제로 사용할 때는 목표·범위·중단 조건·출력 기준을 사전에 정의해야 한다. 아래는 "사양서 초안이 AC와 정합하는지 연쇄 검증"을 에이전트에게 맡기는 예시다.

---

**에이전트 목표**
사양서 초안의 각 Feature 항목이 AC 목록과 빠짐없이 연결되어 있는지 검증한다.

**접근 가능한 입력**
- 사양서 초안 (Spec_v1.md)
- AC 목록 (AC_F01~F08.md)
- 권한 정책 매트릭스 (permission-matrix.md)

**행동 지침**
1. 사양서의 Feature ID 목록을 먼저 추출한다
2. 각 Feature ID에 대응하는 AC가 AC 목록에 있는지 확인한다
3. AC가 없는 Feature ID를 "누락" 목록으로 기록한다
4. AC는 있지만 사양서에서 해당 Feature의 조건이 AC의 Given 조건과 불일치하는 항목을 "불일치" 목록으로 기록한다
5. 권한 정책 매트릭스에서 정의한 역할 조건이 사양서와 AC 모두에 반영됐는지 확인한다

**중단 조건**
- 사양서 파일이 손상됐거나 Feature ID 형식이 불일치: 중단하고 "형식 오류" 보고
- 확인 불가 항목이 전체의 30% 이상: 중단하고 중간 결과 보고

**출력 형식**
```
## 검증 결과 요약
- 총 Feature 수: N개
- AC 연결 완료: N개
- 누락: N개 → 목록
- 불일치: N개 → 목록 + 불일치 내용
- 권한 조건 미반영: N개 → 목록
```

**사람이 최종 판단할 것**
- 불일치 항목의 수정 방향 (사양서를 고칠지 AC를 고칠지)
- 누락 항목을 이번 릴리즈 범위에 포함할지 여부
- 검증 결과의 최종 승인

---

이 정의가 있으면 에이전트는 이 목표를 받아 단계별로 자율 실행한다. 목표 정의 없이 "사양서와 AC 비교해줘"라고 하면 에이전트가 무엇을 어디까지 확인해야 하는지 스스로 결정하게 되어 결과를 예측할 수 없다.

---

에이전트는 다음과 같은 작업에서 가치가 있다.

**멀티스텝 리서치**: "이 서비스의 경쟁사 3곳을 조사해서 기능 비교표를 만들어라"처럼 여러 단계를 거쳐야 하는 작업. 에이전트는 검색하고, 내용을 읽고, 정리하고, 비교표를 만드는 단계를 스스로 진행한다.

**산출물 연쇄 생성**: RIB가 주어지면 PRD 초안을 쓰고, PRD를 기반으로 핵심 정책 포인트를 추출하고, 그것을 BPMN 흐름 초안으로 변환하는 것처럼 이전 결과를 다음 입력으로 쓰는 작업.

**반복 검증**: 사양서 초안이 있을 때 AC 목록과 하나씩 대조해서 누락 항목을 찾는 작업. 항목이 많아도 에이전트가 순차적으로 처리한다.

**오류 감지와 수정**: 문서의 특정 기준(용어 일관성, 포맷 규칙 등)을 반복 점검하면서 오류를 찾는 작업.

---

## 4. 에이전트를 쓸 때 사람이 개입해야 하는 지점

에이전트가 자율적으로 행동한다고 해서 사람의 판단이 불필요해지는 것은 아니다. 다음 지점에서는 사람이 반드시 개입해야 한다.

**목표 정의**: 에이전트에게 무엇을 달성하라고 할지는 사람이 결정한다. 목표가 잘못 설정되면 에이전트가 아무리 잘 실행해도 틀린 방향으로 가게 된다.

**정책 결정**: 에이전트가 "이 경우 어떻게 처리할까"를 스스로 결정하게 두면 안 된다. 예외 처리 방식, 우선순위 기준, 정책 충돌 해소는 사람이 판단해야 한다.

**최종 승인**: 에이전트가 만든 결과물은 Draft로만 취급해야 한다. 공식 기준 문서나 팀 외부로 나가는 결과물은 사람이 검토하고 승인해야 한다.

**중단 판단**: 에이전트가 진행하다가 의도하지 않은 방향으로 가고 있을 때, 멈추고 재설정하는 것은 사람의 역할이다.

---

## 5. 에이전트의 한계와 위험 요소

에이전트가 강력할수록 위험 요소도 커진다.

**목표 오해**: 에이전트가 목표를 다르게 해석하면 의도하지 않은 방향으로 상당히 진행될 수 있다. 단발 요청보다 훨씬 많은 작업이 이미 실행된 뒤 문제가 드러날 수 있다.

**정보 오용**: 에이전트가 오래된 문서, 잘못된 버전을 기준으로 작업하면 전체 결과가 틀어진다. 이것은 컨텍스트 엔지니어링의 품질과 직결된다.

**오류 연쇄**: 한 단계의 오류가 다음 단계 입력이 되어 오류가 쌓인다. 단발 요청에서는 한 번 틀리고 끝이지만, 에이전트는 오류가 전파된다.

**범위 초과**: 에이전트가 목표 달성을 위해 의도하지 않은 범위까지 행동할 수 있다. 하네스 엔지니어링에서 이 범위를 명확히 설정해두는 이유가 여기에 있다.

이러한 위험 요소 때문에 에이전트를 안전하게 운영하려면 하네스 엔지니어링이 필요하다. 하네스는 에이전트에 범위, 게이트, 오류 복구 구조를 씌워 목적지까지 안전하게 도착하게 한다.

---

## 6. 에이전트 활용 체크리스트

- 목표가 명확하게 정의되어 있는가
- 에이전트가 접근할 수 있는 도구와 문서 범위가 제한되어 있는가
- 중간 결과를 사람이 확인하는 게이트가 있는가
- 최종 결과물을 사람이 승인하는 구조가 있는가
- 에이전트가 중단해야 할 조건이 정의되어 있는가
- 오류가 생겼을 때 어떻게 복구할지 정해져 있는가

---

## 7. 정리

에이전트는 목표를 향해 스스로 계획하고 실행하고 판단하는 AI 실행 단위다. 단발 요청과 달리 여러 단계를 자율적으로 처리하고, 장애물이 생기면 우회하며 목표까지 나아간다.

기획 실무에서 에이전트는 멀티스텝 리서치, 산출물 연쇄 생성, 반복 검증, 오류 감지 같은 작업에서 가치가 크다. 그러나 목표 정의, 정책 결정, 최종 승인, 중단 판단은 여전히 사람의 역할이다.

에이전트가 강력할수록 오류 연쇄, 정보 오용, 범위 초과 위험도 커진다. 이 위험을 관리하는 것이 하네스 엔지니어링이다.

그런데 단일 에이전트로는 처리하기 어려운 복잡한 작업도 있다. 여러 에이전트가 각자의 역할을 맡아 팀처럼 협업하고, 상황이 바뀌면 작전을 수정하는 구조 — 그것이 다음 장의 에이전틱 에이전트다.

---

## 다음 장으로의 연결

단일 에이전트가 잘 작동해도, 복잡한 문제는 혼자 감당하기 어렵다. 여러 에이전트가 역할을 나눠 협업하고, 전체 진행 상황에 따라 전략을 수정하는 것이 에이전틱 에이전트다. 32장 제2절에서는 그 팀 플레이 구조를 다룬다.

---

## 제2절. Agentic Agent: 에이전틱 에이전트

## 이 장의 목적

이 장은 단일 에이전트를 넘어선 에이전틱 에이전트(Agentic Agent) 구조를 다룬다. 에이전틱 에이전트는 여러 에이전트가 각자의 역할을 맡아 협업하고, 전체 상황이 바뀌면 작전을 수정하면서 복잡한 목표를 달성하는 구조다. 핵심은 분업과 적응이다.

이 장을 읽고 나면 다음을 이해해야 한다.

- 에이전틱 에이전트가 단일 에이전트와 어떻게 다른지
- 멀티 에이전트 협업 구조가 왜 필요한지
- 오케스트레이터와 서브 에이전트의 역할 분리
- 기획 실무에서 에이전틱 에이전트 구조가 적용될 수 있는 상황
- 에이전틱 에이전트의 운영 리스크와 사람의 역할

---

## 1. 에이전틱 에이전트란 무엇인가

에이전틱 에이전트는 단일 에이전트가 혼자 처리하는 것이 아니라, 여러 에이전트가 팀처럼 역할을 나눠 작동하는 구조다.

스포츠 팀 비유가 이해하기 쉽다. 축구에서 포워드, 미드필더, 수비수, 골키퍼는 각자 다른 역할을 하지만 공통 목표(골 넣기, 실점 막기)를 향해 협력한다. 상대 팀의 작전이 바뀌면 감독이 선수 배치와 전술을 바꾼다. 에이전틱 에이전트가 하는 일이 이것과 같다.

단일 에이전트는 한 명이 모든 포지션을 뛰는 것이다. 작은 작업에서는 충분하지만, 복잡하고 병렬 처리가 필요한 작업에서는 한계가 있다. 에이전틱 에이전트는 역할을 분리하고, 각 에이전트가 자기 역할에 집중하고, 오케스트레이터가 전체를 조율하는 구조다.

---

## 2. 오케스트레이터와 서브 에이전트의 역할

에이전틱 에이전트 구조는 크게 두 계층으로 나뉜다.

### 2-1. 오케스트레이터(Orchestrator)

오케스트레이터는 전체 목표를 이해하고, 작업을 분해하고, 각 서브 에이전트에게 역할을 배분하고, 진행 상황을 점검하고, 상황이 바뀌면 작전을 수정하는 에이전트다.

오케스트레이터의 역할은 다음과 같다.

- 목표를 서브 작업으로 분해
- 어떤 에이전트가 어떤 작업을 맡을지 결정
- 서브 에이전트 결과를 수집하고 통합
- 예상치 못한 상황에서 계획 수정
- 전체 진행 상태 모니터링

### 2-2. 서브 에이전트(Sub-Agent)

서브 에이전트는 오케스트레이터로부터 특정 역할을 받아 그 범위 안에서 실행하는 에이전트다. 각 서브 에이전트는 자기 전문 영역에 집중한다.

예를 들어 기획 실무의 대규모 리서치 작업에서는 다음처럼 나뉠 수 있다.

- 검색 에이전트: 관련 자료와 경쟁사 정보를 수집
- 분석 에이전트: 수집된 내용을 분류하고 패턴을 찾음
- 문서화 에이전트: 분석 결과를 지정된 산출물 형식으로 정리
- 검증 에이전트: 결과물이 기준 문서와 일치하는지 교차 확인

각 에이전트는 자기 역할만 한다. 오케스트레이터가 전체 흐름을 관리한다.

---

## 3. 적응형 작전 수정이 핵심인 이유

에이전틱 에이전트에서 "상황이 바뀌면 작전을 수정한다"는 것이 왜 중요한가.

실제 복잡한 작업은 처음 계획대로만 흘러가지 않는다. 수집한 자료가 예상보다 적을 수도 있고, 특정 경로가 막혀서 다른 방법이 필요할 수도 있고, 중간 결과가 초기 가정과 달라서 목표 자체를 재검토해야 할 수도 있다.

단일 에이전트는 이런 상황에서 멈추거나 이미 설정된 규칙으로만 대응한다. 에이전틱 에이전트의 오케스트레이터는 중간 결과를 평가하고, 현재 상황에 맞게 이후 단계를 다시 설계한다. 이것이 적응형 작전 수정이다.

이 능력이 있어야 복잡한 실무 과제에서 에이전트가 유용해진다. 처음부터 완벽한 계획을 세우는 것이 아니라, 진행하면서 상황을 반영해 계획을 개선하는 것이다.

---

## 4. 단일 에이전트에서 에이전틱 구조로 전환하는 기준

모든 작업에 에이전틱 에이전트가 필요한 것은 아니다. 복잡한 구조는 관리 비용이 크기 때문에, 단일 에이전트로 충분한 상황에서 굳이 멀티 에이전트를 도입하면 오히려 리스크만 늘어난다. 다음 기준으로 전환을 판단한다.

| 전환 신호 | 단일 에이전트로 충분 | 에이전틱 구조로 전환 |
|---|---|---|
| **작업 범위** | 목표가 하나의 흐름으로 처리 가능 | 병렬 처리가 가능하거나 필요한 다수의 하위 작업 |
| **전문성 요구** | 한 가지 능력으로 전체 처리 가능 | 다른 종류의 전문성이 동시에 필요 |
| **작업 규모** | 수십 개 항목 이내 | 수백 개 이상 또는 여러 도메인에 걸친 대규모 |
| **오류 민감도** | 중간 오류가 전체에 미치는 영향 작음 | 단계 오류가 이후 전체에 전파되는 연쇄 구조 |
| **진행 적응** | 계획이 거의 고정 | 중간 결과에 따라 다음 단계를 재설계해야 함 |

에이전틱 구조는 병렬성, 전문화, 적응이 동시에 필요할 때 도입하는 것이 적절하다. 단순히 "작업이 많다"는 이유만으로 도입하면 조율 비용만 증가한다.

---

## 5. 기획 실무에서 에이전틱 에이전트가 적용될 수 있는 상황

현재 기획 실무에서 에이전틱 에이전트 구조가 실질적으로 적용될 수 있는 상황은 제한적이다. 그러나 다음 유형의 작업에서 가능성이 있다.

**대규모 As-is 분석**: 레거시 서비스의 기존 기능, 정책, 흐름을 파악하는 작업. 수집 에이전트, 분류 에이전트, 정리 에이전트로 나눠 병렬 처리할 수 있다.

**멀티 도메인 요구사항 통합**: 여러 팀 또는 여러 소스에서 나온 요구사항을 하나의 구조로 통합하는 작업. 각 소스를 담당하는 서브 에이전트와 통합을 담당하는 에이전트로 나눌 수 있다.

**반복 검토 사이클**: 산출물 초안에 대해 여러 관점(정책 일치, 흐름 완결성, 용어 일관성 등)을 각각 전문화된 에이전트로 병렬 검토하는 작업.

**릴리즈 문서 세트 생성**: 릴리즈 노트, FAQ 갱신, 운영 가이드 반영을 각 에이전트가 맡아 동시에 진행하는 구조.

---

## 6. 에이전틱 에이전트의 운영 리스크

에이전틱 에이전트는 단일 에이전트보다 훨씬 복잡한 만큼 리스크도 크다.

**조율 실패**: 오케스트레이터가 잘못 판단하면 서브 에이전트들이 엉뚱한 방향으로 각자 열심히 작동한다. 팀원들이 각자 열심히 하는데 결과가 따로 놀게 되는 것과 같다.

**오류 전파 가중**: 한 서브 에이전트의 오류가 다음 에이전트의 입력이 되면서 오류가 쌓이고 전파된다. 여러 에이전트를 거칠수록 초기 오류의 영향이 커진다.

**투명성 감소**: 에이전트가 많아질수록 중간 과정을 사람이 전부 파악하기 어렵다. 무슨 결정이 어디서 어떻게 이루어졌는지 추적하기 힘들어진다.

**범위 충돌**: 서브 에이전트들의 역할 경계가 불분명하면 같은 작업을 중복으로 하거나, 아무도 담당하지 않는 공백이 생긴다.

이 리스크들을 관리하기 위해 하네스 엔지니어링은 에이전틱 에이전트 구조에서도 필수다. 각 에이전트의 범위 제한, 오케스트레이터의 게이트 확인, 오류 복구 메커니즘이 갖춰져야 에이전틱 구조가 안전하게 작동한다.

---

## 7. 사람이 끝까지 붙들어야 할 것

에이전틱 에이전트 구조가 아무리 정교해도 사람이 책임져야 할 것은 바뀌지 않는다.

- **목표 정의**: 무엇을 달성해야 하는지는 사람이 결정한다.
- **역할 설계**: 어떤 에이전트가 어떤 역할을 맡는지 처음 설계는 사람이 한다.
- **최종 승인**: 에이전틱 에이전트가 만든 결과는 Draft다. 공식 기준으로 올리려면 사람의 검토와 승인이 필요하다.
- **중단 기준**: 에이전트들이 잘못된 방향으로 가고 있을 때 전체를 멈추는 판단은 사람이 한다.
- **정책과 예외 결정**: 에이전트가 판단하기 어려운 정책 충돌, 예외 처리 기준은 사람이 정한다.

AI가 팀처럼 협업할 수 있게 됐다고 해서, 그 팀을 운영하고 책임지는 사람이 필요 없어지는 것은 아니다. 오히려 에이전트 팀의 결과에 대한 책임은 더 명확하게 사람에게 귀속되어야 한다.

---

## 8. 에이전틱 에이전트 설계 체크리스트

- 오케스트레이터와 서브 에이전트의 역할이 명확히 분리되어 있는가
- 각 서브 에이전트의 범위와 경계가 정의되어 있는가
- 에이전트 간 결과 전달 방식과 형식이 정해져 있는가
- 중간 결과를 사람이 확인하는 체크포인트가 있는가
- 오케스트레이터가 계획을 수정할 수 있는 조건이 정의되어 있는가
- 오류 발생 시 전체 또는 일부를 멈추는 기준이 있는가
- 최종 결과물에 대한 사람의 승인 구조가 있는가

---

## 9. 정리

에이전틱 에이전트는 단일 에이전트가 혼자 처리하는 한계를 넘어, 여러 에이전트가 역할을 분담하고 오케스트레이터가 전체를 조율하는 팀 플레이 구조다. 상황이 바뀌면 오케스트레이터가 작전을 수정한다는 것이 핵심이다.

이 구조는 대규모 리서치, 멀티 도메인 통합, 병렬 검토처럼 단일 에이전트로는 효율적으로 처리하기 어려운 복잡한 작업에서 가치가 있다. 그러나 조율 실패, 오류 전파, 투명성 감소 같은 리스크가 더 크기 때문에 하네스 엔지니어링과 사람의 승인 구조가 반드시 함께 있어야 한다.

파트 5에서 다룬 여섯 계층 — 프롬프트 엔지니어링, 컨텍스트 엔지니어링, 스킬, 하네스 엔지니어링, 에이전트, 에이전틱 에이전트 — 은 각각 독립적이면서 순서대로 쌓인다. 명령을 잘 내리는 것에서 시작해, 환경을 설계하고, 행동을 규칙화하고, 안전 구조를 씌우고, 자율 실행을 허용하고, 팀 협업까지 나아가는 계층이다. 이 계층 위에서 기획 산출물이 AI 작업 인터페이스가 된다.

---

## 에필로그로의 연결

기획자는 이제 문서를 쓰는 사람이기 이전에, AI가 읽을 수 있는 구조를 설계하는 사람이다. 프롬프트 하나로 시작했지만, 컨텍스트를 설계하고, 스킬을 만들고, 하네스를 씌우고, 에이전트를 운영하고, 에이전틱 팀을 조율하는 것까지 — 결국 모든 계층에서 기준과 구조와 판단을 붙들고 있는 것은 사람이다.

AI 시대에도 끝까지 남는 것은 AI를 작동시키는 기술이 아니라, AI가 일할 수 있는 구조를 설계하고 그 결과에 책임지는 사람의 역할이다.
