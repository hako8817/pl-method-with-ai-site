# 13장. Feature Spec: 기능 명세

## 이 장의 목적

PRD가 제품의 목표와 범위를 정의한다면 Feature Spec은 그 범위 안의 각 기능을 구현 가능한 단위로 나누는 문서다. "회원가입 기능을 만든다"는 PRD의 기능 항목이고 "이메일 회원가입", "소셜 로그인", "비밀번호 재설정"은 각각 독립된 Feature다.

Feature가 잘 정의되면 AI가 기능 단위로 구현 작업을 나눌 수 있다. 반대로 Feature 경계가 흐릿하면 AI는 하나의 큰 덩어리를 처리하다가 중간에 방향을 잃는다.

이 장을 읽고 나면 다음을 할 수 있어야 한다.
- Feature의 적절한 크기를 판단할 수 있다.
- Feature Spec의 구조를 작성할 수 있다.
- AI와 함께 Feature를 도출하는 방법을 이해한다.

---

> **이 장에서 다루는 것**
> - Feature의 정의, 크기 기준, 구조
> - 좋은 Feature와 나쁜 Feature의 차이
> - AI와 함께 PRD에서 Feature를 도출하는 법
> - 샘플: 회원/인증 서비스 Feature 목록 완전 예시

> **전제 지식**: 11장(PRD) — Feature는 PRD가 정한 방향을 구현 단위로 내리는 작업이다.
> **다음 연결**: 14장(Scenario와 AC) → 각 Feature의 동작 흐름을 시나리오로 풀어낸다.

---

## 1. 이 산출물이 왜 존재하는가

PRD는 "무엇을 왜 만드는가"를 정의한다. 그러나 PRD의 목표 문장만으로는 팀이 실제로 무엇을 만들어야 하는지 공통으로 이해하기 어렵다.

예를 들어 PRD에 "사용자가 안전하게 로그인할 수 있어야 한다"고 쓰여 있어도 이것이 몇 개의 기능인지, 각 기능의 경계가 어디인지, 어떤 것이 이번 릴리즈 범위인지는 PRD만으로 알 수 없다.

Feature는 그 간격을 채운다.

- PRD가 방향이라면 Feature는 **구현 책임 단위**다.
- Feature 하나는 팀이 "이것을 만들었다"고 말할 수 있는 최소 묶음이다.
- Feature 목록이 확정되면 개발 태스크 분해, Jira 등록, 인력 배분, 테스트 범위 설계가 시작된다.

## 2. 무엇을 입력으로 받고 무엇을 넘기는가

### 2-1. Feature가 받는 입력

| 입력 소스 | 내용 |
|---|---|
| PRD | 핵심 시나리오·기능 범위·성공 기준·Out of Scope — Feature 후보 추출 기준 |
| RIB | 이해관계자 요구·제약 조건 — Feature 우선순위 판단 근거 |
| NFR | 성능·보안·가용성 조건 — Feature AC에 반영할 비기능 기준 |
| As-is 분석 | 현재 기능 동작과 예외 케이스 — 누락 Feature 방지 |
| 정책서 초안 | 허용·차단·예외 규칙 후보 — Feature 경계 확정 근거 |

### 2-2. Feature가 넘겨주는 출력

| 다음 산출물 | 받는 것 |
|---|---|
| **Scenario** | Feature 하나당 정상·예외·경계 시나리오 |
| **정책서** | Feature의 조건 분기·예외 처리 → 정책 규칙 항목 |
| **BPMN** | Feature 단위 → 레인 구성 기준, 게이트웨이 후보 |
| **DMN** | 판단이 필요한 Feature → 의사결정 테이블 후보 |
| **사양서** | Feature 범위 → Spec 섹션 단위 |
| **RTM** | Feature ID → 요구사항 추적 시작점 |
| **DoD** | Feature 완료 = AC 전체 통과 |

## 3. Feature의 구조

Feature 하나는 아래 항목으로 구성된다.

| 항목 | 설명 | 예시 |
|---|---|---|
| **Feature ID** | 고유 식별자 | F-02 |
| **Feature명** | 한 줄 책임 정의 | 이메일 로그인 |
| **책임 범위** | 이 Feature가 처리하는 것 | 이메일·비밀번호 인증 및 세션 발급 |
| **In Scope** | 이번 릴리즈에 포함되는 것 | 로그인 시도, 실패 횟수 추적, 잠금 처리, 세션 발급, 로그아웃 |
| **Out Scope** | 이번 릴리즈에 포함되지 않는 것 | 자동 로그인, 2차 인증, 기기별 세션 관리 |
| **의존 Feature** | 이 Feature가 전제하는 Feature | F-01(이메일 회원가입) — ACTIVE 상태 계정이 있어야 로그인 가능 |
| **대표 시나리오 수** | 이 Feature에서 파생될 시나리오 수 | 정상 1 + 예외 6 = 7개 |

---

## 4. Feature의 적절한 크기

Feature는 너무 크면 관리가 어렵고, 너무 작으면 의미 있는 단위가 되지 않는다.

### 적절한 Feature의 기준

- 한 줄로 책임이 설명된다: "이메일 로그인 — 이메일·비밀번호로 인증하고 세션을 발급한다"
- 2~10개의 시나리오로 커버된다
- 한 팀 또는 한 역할이 담당 가능하다
- 완료 여부를 AC로 판단할 수 있다

### 너무 큰 Feature (분리 필요)

```
❌ "회원 관리 전반"
→ 회원가입 / 로그인 / 소셜 로그인 / 비밀번호 재설정 / 마이페이지 / 탈퇴로 분리
```

```
❌ "인증 보안 강화"
→ 로그인 실패 잠금 / 관리자 계정 알림 / 세션 관리 / 휴면 처리로 분리
```

### 너무 작은 Feature (병합 필요)

```
❌ "로그인 버튼 UI 수정"
→ 이것은 Feature가 아니라 UI Task다. 상위 Feature에 포함시킨다.
```

```
❌ "비밀번호 필드에 눈 아이콘 추가"
→ "이메일 로그인" Feature의 UI 구현 항목이다.
```

### Feature 크기 판단 기준표

| 신호 | 판단 |
|---|---|
| 시나리오가 10개 이상 나온다 | 분리 검토 |
| 두 역할 이상이 병행 개발해야 한다 | 분리 검토 |
| "~와 ~" 형태로 책임이 두 개 이상이다 | 분리 검토 |
| 시나리오가 0~1개다 | 병합 검토 |
| 화면 1개 안에서 끝난다 | 병합 또는 Task로 처리 |

## 5. AI와 함께 Feature를 도출하는 법

### Step 1: PRD 시나리오 → Feature 분해

**입력**: PRD 핵심 시나리오 + In/Out Scope

**프롬프트**

```
아래 PRD 내용을 읽고 구현 책임 단위(Feature)로 분해해줘.

규칙:
- Feature 하나는 한 줄로 "이 기능이 무엇을 책임지는가"를 설명할 수 있어야 함
- PRD의 Out of Scope는 Feature로 만들지 말 것
- 너무 넓은 것은 분리, 너무 좁은 것은 병합 제안도 함께
- 각 Feature에 의존 관계가 있으면 표시

출력 형식:
| Feature ID | Feature명 | 책임 한 줄 | 의존 Feature |

[PRD 핵심 시나리오]
(붙여넣기)

[In Scope / Out Scope]
(붙여넣기)
```

**PM 검토 기준**

| 확인 항목 | 기준 |
|---|---|
| 책임 명확성 | Feature 하나가 하나의 기능 책임인가 |
| 범위 준수 | PRD의 Scope 안에 있는가 |
| 크기 적절성 | 2~10개 시나리오로 커버 가능한가 |
| 의존 관계 | 선행 Feature가 누락되지 않았는가 |
| Out Scope 준수 | 이번 릴리즈 범위 밖의 내용이 포함됐는가 |

## 6. 샘플: 이커머스 플랫폼 주문·결제·반품 처리 Feature 목록

PRD에 "주문·결제·배송·반품·환불의 완전한 자동화"가 정의된 상황에서 도출한 Feature 목록이다.

### Feature 목록

| Feature ID | Feature명 | 책임 범위 (한 줄) | 의존 Feature |
|---|---|---|---|
| **F-01** | 장바구니 관리 | 구매자가 상품을 장바구니에 추가·제거하고 수량을 수정한다 | 없음 |
| **F-02** | 주문 생성 및 결제 | 장바구니에서 주문을 생성하고 PG사를 통해 결제를 처리한다. 결제 완료 후 배송 상태 전환 | F-01 |
| **F-03** | 배송 추적 | 구매자가 주문 번호로 배송 상태(준비·배송중·배송완료)를 조회하고 배송사 정보를 확인한다 | F-02 |
| **F-04** | 주문 취소 | 결제 완료 후 배송 출고 전까지만 주문을 취소하고 환불을 처리한다 | F-02 |
| **F-05** | 반품 신청 및 처리 | 배송 완료 후 7일 이내 반품을 신청하고 수거·환불을 처리한다 | F-03 |
| **F-06** | 환불 처리 | 환불액을 원결제 수단으로 반환하거나 운영 예외 승인 시 대체 수단으로 처리한다 | F-04, F-05 |
| **F-07** | 판매자 어드민 — 주문 관리 | 판매자가 주문 목록을 조회하고 배송 정보를 입력·관리한다 | F-02 |

### 이번 릴리즈 Out Scope (Feature로 만들지 않는 것)

| 항목 | 이유 |
|---|---|
| 소셜 커머스 통합 (라이브 커머스) | 별도 릴리즈 |
| 판매자 마진율·수수료 자동 정산 | 별도 릴리즈 |
| 멤버십 할인·포인트 적립 | 별도 릴리즈 |
| 배송사 추가 선택지 제공 | 별도 릴리즈 |
| 구독 상품 반복 구매 | 별도 릴리즈 |

### F-05 반품 신청 및 처리 — Feature 상세 카드

```
Feature ID : F-05
Feature명  : 반품 신청 및 처리
책임       : 배송 완료 후 7일 이내 반품을 신청하고 수거·환불을 처리한다.
             판매자 귀책 반품 시 배송비 판매자 부담. 구매자 귀책 시 배송비 차감 환불.
의존       : F-03 (배송 완료 상태여야 함)
In Scope   : 반품 신청 / 신청 기한 자동 검증 / 수거사 호출 /
             수거 상태 추적 / 반품 확인 / 환불 처리 기준 판단
Out Scope  : 반품 거부 사유 제시 AI / 고객 분쟁 중재 / 재판매 검사
예상 시나리오 수 : 정상 2 + 예외 6 = 8개
```

## 7. 품질 기준 / 체크리스트

**구조 기준**
- [ ] Feature 하나가 하나의 기능 책임인가
- [ ] 책임을 한 줄로 설명할 수 있는가
- [ ] In Scope / Out Scope가 명시됐는가
- [ ] 의존 Feature가 표시됐는가

**크기 기준**
- [ ] 시나리오가 2~10개 범위로 예상되는가
- [ ] 한 팀/역할이 담당 가능한 단위인가
- [ ] "~와 ~" 형태의 이중 책임이 없는가

**연결 기준**
- [ ] PRD의 범위 안에 있는가
- [ ] Out of Scope 항목이 Feature로 들어가지 않았는가
- [ ] AC로 완료 여부를 판단할 수 있는 단위인가

| F-06 환설 처리 | 원결제 수단으로 환불 / 예외 승인 후 대체 수단으로 환불 / 배송비 차감 환불 / PG사 환불 API 실패 처리 |

> **이 장이 결정한 것**: 구현 책임 단위(Feature), In/Out Scope, 의존 관계
> **다음 장이 시작하는 것**: 각 Feature의 동작을 시나리오로 구조화

## 이 장의 핵심 메시지

Feature Spec은 구현의 단위를 정의하는 문서다. 이 단위가 너무 크면 AI가 한 번에 처리할 수 없고, 너무 작으면 맥락이 사라진다. "한 번의 배포로 완성 가능하고, Acceptance Criteria로 완료를 판단할 수 있는 단위"가 좋은 Feature다.

Feature 목록은 팀 내 업무 분배와 AI 작업 지시의 기준이 된다. 이것이 없으면 누가 무엇을 만들고 있는지가 불명확해진다.
