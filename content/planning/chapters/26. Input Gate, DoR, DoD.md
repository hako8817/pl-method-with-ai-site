# 26장. Input Gate, DoR, DoD

> 이 장은 세 가지 진입·완료 기준을 함께 다룬다. Input Gate는 산출물을 다음 단계로 넘겨도 되는지를 확인하는 기준이다. DoR(Definition of Ready)은 실제 작업 착수가 가능한 조건이 갖춰졌는지를 본다. DoD(Definition of Done)는 작업이 완료됐다고 판단할 수 있는 기준이다. 세 기준은 산출물 체인의 품질 게이트를 구성한다.

| 게이트 | 확인 시점 | 확인 주체 | 핵심 질문 |
|---|---|---|---|
| **Input Gate** | 산출물을 다음 단계에 넘기기 전 | 전달하는 쪽 (기획자/PM) | "이 산출물을 받아서 다음 작업을 바로 시작할 수 있는가?" |
| **DoR** | 스프린트·과제 착수 직전 | 착수하는 쪽 (개발팀/PM) | "이 과제의 입력 조건이 모두 갖춰져 있는가?" |
| **DoD** | 작업 완료 선언 직전 | 완료하는 쪽 (개발팀/QA) | "이 과제가 완료됐다고 팀 전체가 동의할 수 있는가?" |

세 게이트는 역할이 다르다. Input Gate는 산출물 품질을 관리하고, DoR은 착수 가능성을 검증하며, DoD는 완료 기준을 확정한다. 세 기준이 모두 갖춰져야 "만들었다"와 "제대로 만들었다"의 차이를 체계적으로 관리할 수 있다.

---

## 제1절. Input Gate: 다음 단계 진입 조건

> **이 장에서 다루는 것**
> - Input Gate의 역할과 적용 기준
> - 산출물별 Input Gate 점검 항목
> - AI와 함께 Input Gate를 운영하는 실무 패턴

> 이 장은 Input Gate를 다룬다. 시작 준비 기준(DoR)은 26장 제2절, 완료 기준(DoD)은 26장 제3절에서 다룬다.

> **전제 지식**: 25장(산출물 체인 설계) — Input Gate는 산출물 체인의 각 연결 지점에서 다음 단계로 진입 가능한지를 판단하는 기준이다.

## 이 장의 목적

이 장은 산출물이 존재한다는 것과 다음 단계로 넘겨도 된다는 것이 다르다는 점을 설명한다. Input Gate는 문서가 준비됐는지를 다음 단계 진입 전에 확인하는 기준이다.

이 장을 읽고 나면 다음을 할 수 있어야 한다.

- Input Gate가 왜 필요한지 설명할 수 있다.
- 산출물별 Input Gate 점검 항목을 설계할 수 있다.
- AI 초안이 Input Gate를 통과할 수 있는 수준인지 판단할 수 있다.

---

## 1. 이 산출물이 왜 존재하는가

실무에서는 문서를 만들었다는 사실 자체가 안도감을 준다. PRD가 있고, 정책서가 있고, BPMN과 DMN이 있다고 하면 겉으로는 충분해 보인다. 하지만 실제로는 큰 차이가 있다.

- 문서가 있음: 파일은 존재한다.
- 문서가 준비됨: 다음 단계가 이 문서를 신뢰하고 사용할 수 있다.

예를 들어:

- PRD에 Out of Scope가 없고 성공 기준이 불분명하면 Ready가 아니다.
- 정책서에 예외 규칙과 DMN 후보가 없으면 Ready가 아니다.
- BPMN에 예외 흐름과 판단 분기 지점이 없으면 Ready가 아니다.
- 사양서에 테스트 포인트가 없으면 Ready가 아니다.

산출물 체인이 실패하는 이유는 문서가 없어서가 아니라, 준비되지 않은 문서를 다음 단계로 넘기기 때문인 경우가 많다.

## 3. Input Gate는 무엇을 확인해야 하는가

Input Gate는 문서마다 다르지만 공통적으로 세 가지를 본다.

### 3-1. 최소 필수 항목이 채워졌는가

| 산출물 | 최소 항목 |
|---|---|
| RIB | 문제 정의, 범위, 제약, 이해관계자 |
| PRD | 문제 정의, 범위, 핵심 시나리오, 성공 기준 |
| 정책서 | 기본 규칙, 예외 규칙, 참조 기준 |
| BPMN | 참여자, 정상 흐름, 예외 흐름 |
| DMN | 입력값, 규칙, 결과값 |
| 사양서 | 상태, 입력 조건, 메시지, 예외 처리 |
| 테스트케이스 | 전제 조건, 입력/행동, 기대 결과 |

### 3-2. 상위 기준 문서와 연결되어 있는가

문서가 혼자 떠 있지 않고 앞 단계 문서와 연결되어 있는지 본다.

### 3-3. 다음 단계가 실제로 사용할 수 있는 수준인가

다음 단계 담당자가 이 문서만 보고도 착수 가능한 수준이어야 한다.

즉 Input Gate는 **필수 항목 + 연결 + 사용 가능성**을 본다.

---

## 4. 왜 AI 시대에 더 중요해졌는가

AI 시대에는 문서 초안이 매우 빨리 만들어진다. 그래서 세 가지 위험이 커진다.

- **초안이 너무 빨리 다음 단계로 넘어간다**: 겉보기 완성도가 높아 보여도 핵심 항목이 빠져 있을 수 있다.
- **그럴듯함이 품질처럼 보인다**: AI가 쓴 문장은 매끄럽지만 판단 기준이 없을 수 있다.
- **약한 문서가 연쇄적으로 확대된다**: PRD가 약하면 정책서, BPMN, 사양서, 테스트케이스도 동시에 흔들린다.

AI 시대일수록 "문서가 빨리 나왔다"보다 "이 문서를 지금 넘겨도 되는가"를 더 엄격하게 물어야 한다.

## 5. 산출물별 Input Gate 적용 기준

| 단계 전환 | Input Gate 점검 기준 |
|---|---|
| RIB → PRD | 문제 정의와 범위 초안이 있는가 |
| PRD → 정책/설계 | 범위, 시나리오, 성공 기준이 정리됐는가 |
| 정책서 → BPMN/DMN | 기본 규칙과 예외 규칙, DMN 후보가 있는가 |
| 사양서 → 개발/QA | 상태·메시지·예외 처리·테스트 포인트가 있는가 |
| TC → 릴리즈 | 정상·예외·경계 케이스가 포함됐는가 |

## 6. 이커머스 주문·반품·환불 케이스에 적용하면

| 게이트 | 점검 기준 |
|---|---|
| PRD Gate | 주문·결제·반품 범위와 핵심 시나리오가 정리됐는가 |
| 정책서 Gate | 반품 허용 기간·판매자 귀책·배송비 부담·환불 조건 규칙과 예외가 정리됐는가 |
| BPMN Gate | 구매자·판매자·운영자 개입 흐름과 반품 승인 예외 흐름이 보이는가 |
| DMN Gate | 반품 허용/거부 판단·판매자 귀책 판단이 조건 조합으로 구조화됐는가 |
| 사양서 Gate | 주문·반품 상태, 오류 메시지, API 응답이 구현 가능 수준인가 |
| 테스트 Gate | 반품 정책·환불 조건 리스크 케이스가 검증 범위에 포함됐는가 |

## 7. AI와 함께 Input Gate를 운영하는 실무 패턴

### AI에게 맡기기 좋은 일

- 필수 항목 누락 점검
- 참조 문서 연결 누락 탐지
- 테스트 포인트 누락 질문 생성

### 사람이 직접 보증해야 하는 일

- 실제 통과/반려 여부 결정
- 범위·정책·운영 리스크 판단
- 승인 여부 확정

AI는 점검을 도울 수 있지만, 다음 단계로 넘길 책임은 사람이 져야 한다.

---

## 8. 품질 기준 / 체크리스트

- 문서가 존재하는가가 아니라 사용 가능한가를 보고 있는가
- 앞 단계 문서와 연결되는가
- 다음 단계 담당자가 이 문서로 착수 가능한가
- AI 초안이라도 사람의 통과 판단이 남는가

## 제2절. DoR: 시작 준비 기준

> **이 장에서 다루는 것**
> - DoR의 역할과 Input Gate와의 차이
> - 산출물별 DoR 체크리스트
> - AI와 함께 DoR을 운영하는 실무 패턴

> 다음 단계 진입 조건(Input Gate)은 26장 제1절, 완료 기준(DoD)은 26장 제3절에서 다룬다.

> **전제 지식**: 26장 제1절(Input Gate) — DoR은 Input Gate를 통과한 문서가 실제 작업 착수에 필요한 조건을 갖췄는지를 판단하는 기준이다.

## 이 장의 목적

이 장은 DoR(Definition of Ready)이 무엇인지, Input Gate와 어떻게 다른지, 그리고 산출물별로 어떻게 적용하는지를 설명한다. DoR은 "이 문서를 받았다"가 아니라 "이 문서로 지금 작업을 시작할 수 있다"를 확인하는 기준이다.

이 장을 읽고 나면 다음을 할 수 있어야 한다.

- DoR이 Input Gate와 어떻게 다른지 설명할 수 있다.
- 산출물별 DoR 항목을 설계할 수 있다.
- 팀 운영 리듬에서 DoR을 어떤 시점에 적용하는지 판단할 수 있다.

---

## 1. 이 산출물이 왜 존재하는가

Input Gate는 문서를 다음 단계로 넘겨도 되는지를 본다. DoR은 한 단계 더 들어간다. 실제로 작업을 시작할 수 있는 조건이 갖춰졌는지를 본다.

차이를 예로 들면:

- Input Gate: PRD가 다음 단계로 넘어갈 수준인가
- DoR: 개발팀이 이 Feature를 백로그에 올리고 작업을 시작할 수 있는가

즉 Input Gate가 "전달 가능한가"를 보고, DoR은 "착수 가능한가"를 본다. 두 기준이 모두 있어야 산출물 체인이 흔들리지 않는다.

## 2. 무엇을 입력으로 받고 무엇을 넘기는가

### DoR이 받는 입력

| 입력 소스 | 내용 |
|---|---|
| Input Gate를 통과한 산출물 | 전달 가능 수준이 확인된 문서 |
| 팀 합의 착수 조건 | 조직 내 DoR 항목 목록 |
| 이전 단계 산출물 연결 | 상위 문서 참조 확인 |

### DoR이 넘겨주는 출력

| 출력 | 내용 |
|---|---|
| 착수 가능 판정 | 작업 시작 가능 여부 |
| 미충족 항목 목록 | 보완이 필요한 조건과 담당자 |
| 착수 시점 기록 | DoR 통과 일자 — 이후 추적 기준 |

---

## 3. DoR은 무엇을 확인해야 하는가

DoR은 완벽함이 아니라 **다음 작업이 시작될 수 있을 만큼 준비됐는가**를 본다.

### 3-1. 산출물별 DoR 항목

#### RIB DoR

- 문제 정의가 있다
- In Scope / Out of Scope 초안이 있다
- 이해관계자가 정리되어 있다
- 확인 필요 사항이 보인다

#### PRD DoR

- 문제 정의가 명확하다
- In Scope / Out of Scope가 있다
- 핵심 시나리오가 있다
- 성공 기준이 있다
- 관련 RIB가 연결되어 있다

#### 정책서 DoR

- 적용 범위가 명확하다
- 기본 규칙이 정리돼 있다
- 예외 규칙이 있다
- BPMN 후보 / DMN 후보가 보인다

#### BPMN DoR

- 참여자와 역할이 구분돼 있다
- 정상 흐름이 있다
- 주요 예외 흐름이 있다
- DMN으로 분리할 판단 지점이 보인다

#### DMN DoR

- 판단명이 있다
- 입력값이 정의돼 있다
- 결과값이 정의돼 있다
- 기본 규칙과 예외 규칙이 반영돼 있다

#### 사양서 DoR

- 참조 문서가 연결돼 있다
- 상태/전이 조건이 있다
- 메시지와 예외 처리 기준이 있다
- 테스트 포인트가 있다

---

## 4. 왜 AI 시대에 더 중요해졌는가

AI로 초안이 빠르게 만들어지면 착수 조건 확인 없이 바로 다음 단계로 넘어가는 일이 많아진다. DoR이 없으면 개발팀이 불완전한 정보로 착수했다가 중간에 다시 기획으로 돌아오는 비용이 생긴다.

DoR은 이 비용을 착수 전에 차단하는 기준이다.

---

## 5. 팀 운영에서 언제 적용하는가

### 5-1. 산출물 단계별 적용 시점

| 적용 시점 | 내용 |
|---|---|
| Feature 백로그 등록 전 | 개발팀이 이 Feature를 작업할 수 있는 상태인가 |
| BPMN/DMN 상세 작업 착수 전 | 기준 정책서가 준비됐는가 |
| 사양서 작성 착수 전 | BPMN/DMN이 충분히 구조화됐는가 |
| 테스트케이스 작성 착수 전 | 사양서와 AC가 테스트 포인트를 제공하는가 |

### 5-2. 2주 스프린트 기준 DoR 적용 사이클

실제 스프린트에서 DoR은 Sprint Planning 직전에 집중적으로 적용된다. 아래는 2주 스프린트 기준 전형적인 DoR 적용 흐름이다.

| 시점 | 활동 | DoR 적용 내용 |
|---|---|---|
| Sprint N-1 마지막 주 | 백로그 정제(Backlog Refinement) | 다음 스프린트 후보 Feature의 DoR 점검. PRD·정책서·AC 준비 상태 확인 |
| Sprint N 시작 전날 | Sprint Planning 준비 | PM이 DoR 최종 점검. 미통과 항목은 이번 Sprint에서 제외 |
| Sprint N Day 1 | Sprint Planning | DoR 통과 항목만 Sprint Backlog에 포함. 미통과 이유 팀 공유 |
| Sprint 중 (긴급 추가 시) | Scope 변경 판단 | 긴급 추가 항목도 DoR 점검 통과 후 포함 여부 결정 |

### 5-3. 기획 단계별 DoR 적용 흐름

스프린트 단위가 아닌 기획 진행 단계에서 DoR은 아래 순서로 적용된다.

1. **RIB 작성 완료 → PRD 착수 DoR 점검**: 문제 정의와 요청 배경이 합의됐는가
2. **PRD 완료 → 정책서·Feature Spec 착수 DoR 점검**: 성공 기준, Out of Scope, 핵심 정책이 있는가
3. **정책서 완료 → BPMN/DMN 착수 DoR 점검**: 예외 규칙과 DMN 후보가 식별됐는가
4. **BPMN/DMN 완료 → 사양서 착수 DoR 점검**: 흐름과 판단 분기가 구조화됐는가
5. **사양서 완료 → 개발 착수 DoR 점검**: 테스트 포인트와 에러 케이스가 사양서에 있는가

각 단계의 DoR 통과 여부는 회의 직후가 아닌 **산출물 리뷰 종료 후 PM이 명시적으로 기록**한다. 구두 합의로 넘어가면 이후 "이미 확인한 것"인지 "아직 확인 안 한 것"인지 추적할 수 없다.

## 제3절. DoD: 완료 기준

> **이 장에서 다루는 것**
> - DoD의 역할과 DoR과의 차이
> - 산출물별 DoD 체크리스트
> - AI와 함께 DoD를 운영하는 실무 패턴

> 다음 단계 진입 조건(Input Gate)은 26장 제1절, 시작 준비 기준(DoR)은 26장 제2절에서 다룬다.

> **전제 지식**: 26장 제2절(DoR) — DoD는 시작된 작업이 완료됐다고 판단할 수 있는 기준이다. DoR이 착수 조건이라면 DoD는 종료 조건이다.

## 이 장의 목적

이 장은 DoD(Definition of Done)가 무엇인지, DoR과 어떻게 다른지, 그리고 산출물별로 어떻게 적용하는지를 설명한다. DoD는 "작업이 끝난 것 같다"가 아니라 "이 기준을 충족했을 때 완료로 본다"를 팀이 사전에 합의하는 기준이다.

이 장을 읽고 나면 다음을 할 수 있어야 한다.

- DoD가 DoR과 어떻게 다른지 설명할 수 있다.
- 산출물별 DoD 항목을 설계할 수 있다.
- 릴리즈 판단에서 DoD를 어떻게 적용하는지 설명할 수 있다.

---

## 1. 이 산출물이 왜 존재하는가

완료의 기준이 없으면 팀마다 완료를 다르게 본다. 개발팀은 코드가 머지됐을 때, QA는 테스트가 통과됐을 때, 기획팀은 문서가 업데이트됐을 때를 완료로 볼 수 있다.

DoD는 이 차이를 사전에 정의한다. 무엇이 달성됐을 때 이 산출물 또는 기능이 완료됐다고 볼 수 있는지를 팀이 함께 합의한 기준이다.

AI 시대에는 문서 초안이 빠르게 만들어지기 때문에 "만들었다"와 "완료됐다"의 차이가 더 쉽게 흐려진다. DoD는 이 흐림을 방지한다.

## 3. DoD는 무엇을 확인해야 하는가

### 3-1. 산출물별 DoD 항목

#### PRD DoD

- 핵심 이해관계자가 범위에 합의했다
- 성공 기준이 리뷰되었다
- 후속 산출물 필요성이 식별되었다

#### 정책서 DoD

- 기본 규칙과 예외 규칙이 분리됐다
- 상위 정책과 충돌 여부가 검토됐다
- BPMN 후보 / DMN 후보가 식별됐다

#### BPMN DoD

- 정상/예외 흐름이 모두 표시됐다
- 역할과 시스템 경계가 보인다
- 상태 전환 시점이 드러난다

#### DMN DoD

- 입력 정의가 용어집/상태 모델과 일치한다
- 규칙 충돌과 우선순위가 검토됐다
- 테스트케이스로 바로 연결 가능한 수준이다

#### 사양서 DoD

- 구현 조건이 모호하지 않다
- 메시지와 상태, 인터페이스가 연결돼 있다
- 개발과 QA가 같은 기준으로 볼 수 있다

#### 테스트케이스 DoD

- 정상/예외/경계 케이스가 포함된다
- 요구사항과 연결된다
- 주요 정책 리스크를 검증한다

#### 기능(Feature) DoD

- AC(Acceptance Criteria)가 모두 통과됐다
- 관련 TC 실행 결과가 RTM에 반영됐다
- 운영 반영에 필요한 문서가 갱신됐다

## 4. 팀 운영에서 언제 적용하는가

### 4-1. 단계별 적용 시점

| 적용 시점 | 내용 |
|---|---|
| 문서 승인 시 | 산출물 DoD 기준으로 최종 리뷰 |
| 개발 완료 판정 시 | 기능 DoD 기준으로 Done 확인 |
| 릴리즈 직전 | 전체 DoD 달성 여부 점검 |
| 스프린트 종료 시 | 미완 항목 식별 및 이관 판단 |

### 4-2. 2주 스프린트 기준 DoD 적용 사이클

DoD는 Sprint 후반부와 Sprint Review에서 집중적으로 적용된다. 아래는 전형적인 2주 스프린트 기준 DoD 적용 흐름이다.

| 시점 | 활동 | DoD 적용 내용 |
|---|---|---|
| Sprint N Day 8~9 | 개발 완료 직후 | 기능별 AC 통과 여부, TC 실행 결과 확인. Done 판정 가능한 항목 식별 |
| Sprint N Day 10 | Sprint Review 전 | PM이 DoD 기준으로 릴리즈 가능 항목과 미완 항목 구분 |
| Sprint N Day 10 | Sprint Review | Done 항목만 데모 대상으로 포함. 미완 항목 이관 사유 공유 |
| Sprint N 종료 후 | Retrospective | DoD 기준 달성률 점검. 반복적으로 미달 항목이 있으면 기준 재조정 검토 |
| 릴리즈 직전 | 릴리즈 DoD 점검 | 모든 Feature DoD 통과 확인, RTM 갱신, Changelog 등록, 운영 반영 준비 |

### 4-3. DoD 미달 항목 처리 기준

Sprint 종료 시점에 DoD를 충족하지 못한 항목은 다음 기준으로 처리한다.

| 상황 | 처리 방식 |
|---|---|
| AC는 통과했으나 TC 실행 미완 | 다음 Sprint 초반에 TC 실행 완료 후 RTM 갱신 |
| AC 일부 미통과 | Done 판정 보류. 다음 Sprint 최우선 작업으로 이관 |
| 문서 갱신 누락 (사양서·정책서 등) | 릴리즈 전 완료 조건으로 별도 추적 |
| 범위 외 이슈 발견 | Decision Log에 기록, 별도 Feature로 등록 |

"거의 됐다"는 Done이 아니다. DoD는 팀이 사전에 합의한 기준이 모두 충족됐을 때만 통과한다.
