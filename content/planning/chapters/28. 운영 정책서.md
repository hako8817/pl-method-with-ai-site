# 28장. 운영 정책서

> **전제 지식**: 11장(PRD), 21장(사양서) — OPD의 장애 대응·변경 관리 기준은 PRD에서 정한 SLA와 사양서의 API/상태 정의에서 출발한다. 두 산출물의 내용을 알아야 OPD 항목을 구체화할 수 있다.

## 이 장의 목적

이 장은 서비스 출시 이후 안정적인 운영을 위한 정책과 절차를 정의하는 **운영 정책서(OPD: Operations Policy Document)**를 다룬다.

기획자에게 운영 정책서는 낯선 문서다. "운영은 개발팀이나 인프라팀이 관리하는 것 아닌가?" 하지만 운영 정책서에 담기는 내용의 상당 부분은 기획 단계에서 이미 결정되거나 결정되어야 한다.

어떤 상태에서 서비스를 일시 중단할 수 있는가. 운영자가 어떤 경우에 데이터를 직접 수정할 수 있는가. 장애 발생 시 어떤 기준으로 롤백할 것인가. 이것은 기술 결정이 아니라 정책 결정이다.

이 장을 읽고 나면 독자는 다음을 할 수 있어야 한다.

- OPD가 왜 기획 산출물 체인의 마지막 단계에 위치하는지 설명할 수 있다.
- OPD의 주요 구성 항목(모니터링·장애 대응·변경 관리·SLA)을 이해한다.
- AI와 함께 OPD 초안을 만들고 PM이 무엇을 확정해야 하는지 판단할 수 있다.
- OPD가 다음 RIB(운영 환류)로 어떻게 이어지는지 이해한다.

---

## 1. 이 산출물이 왜 존재하는가

출시가 끝이 아니다. 서비스는 출시 이후 운영 단계에서 가장 많은 판단과 결정이 필요하다. 그런데 이 판단의 기준이 없으면 다음 문제가 반복된다.

- 장애 발생 시 롤백할 것인지 핫픽스를 배포할 것인지 기준이 없어 판단이 늦어진다.
- 운영팀이 직접 DB를 수정해도 되는지에 대한 기준이 없어 임의로 결정된다.
- SLA 기준을 누가 모니터링하는지 정해져 있지 않아 장애를 늦게 감지한다.
- 운영 중 발생한 정책 예외가 어디에도 기록되지 않아 다음 기획에 반영되지 않는다.

OPD는 이 판단들의 기준을 사전에 정의한다. 또한 OPD는 **운영에서 발견된 이슈가 다시 RIB로 환류되는 고리**를 만드는 역할도 한다. 캔버스 도식에서 `OPD → RIB` 피드백 루프가 표시된 이유다.

## 2. 무엇을 입력으로 받고 무엇을 넘기는가

**입력:**

| 입력 소스 | 내용 |
|----------|------|
| NFR | SLA 기준(가용성·성능·RTO/RPO) |
| SAD | 인프라 구조, 배포 방식 |
| 정책서 | 운영자 권한, 데이터 처리 정책 |
| 권한 정책 매트릭스 | 운영자 접근 범위 |
| 테스트 계획서 | 출시 전 체크리스트, 롤백 조건 |

**출력:**

| 다음 대상 | OPD에서 넘겨주는 것 |
|----------|-------------------|
| **운영팀** | 장애 대응 절차, 에스컬레이션 기준 |
| **RIB (다음 과제)** | 운영 이슈·VOC·정책 예외 → 다음 기획 입력 |
| **Decision Log** | 운영 중 발생한 정책 변경·예외 처리 결정 기록 |

## 3. OPD 구조

### 3-1. 모니터링 기준

| 항목 | 기준 | 담당 |
|------|------|------|
| 서버 CPU/메모리 | 80% 이상 5분 지속 → 알림 | 인프라팀 |
| API 응답 시간 | P95 3초 초과 → 알림 | 인프라팀 |
| 에러율 | 5xx 오류 1% 초과 → 즉시 알림 | 인프라팀 + PO |
| 반품 처리 오류율 | 자동 판단 실패 5% 초과 → 운영팀 알림 | 운영팀 |
| SLA | 가용성 99.9% 미달 → 에스컬레이션 | PO |

### 3-2. 장애 대응 절차

| 단계 | 행동 | 기준 시간 |
|------|------|-----------|
| 감지 | 알림 수신, 영향 범위 1차 파악 | 5분 이내 |
| 판단 | 롤백 vs 핫픽스 vs 서비스 중단 결정 | 15분 이내 |
| 조치 | 선택한 방법 실행 | 상황에 따라 |
| 공지 | 사용자·내부 이해관계자 상황 공유 | 30분 이내 |
| 사후 분석 | 원인 분석, 재발 방지 계획 | 72시간 이내 |

**롤백 결정 기준:**

| 상황 | 결정 |
|------|------|
| Critical 버그 + 롤백 가능 | 즉시 롤백 |
| Critical 버그 + 롤백 불가 | 서비스 일시 중단 + 핫픽스 |
| High 버그 | PO 판단 후 핫픽스 또는 다음 배포 |
| Medium 이하 | 다음 정기 배포에 포함 |

### 3-3. 운영자 권한 행사 기준

운영자가 직접 데이터를 조회·수정할 수 있는 조건을 명시한다.

| 행위 | 허용 조건 | 기록 의무 |
|------|-----------|-----------|
| 반품 신청 데이터 조회 | CS 문의 처리 목적 | 조회 이유 로그 |
| 반품 예외 처리 (정책 외) | PO 승인 후 | 처리 이력 기록 |
| 주문·반품 상태 수동 수정 | PO 승인 후 | Decision Log 기록 |
| DB 직접 수정 | 원칙적 금지 / 긴급 장애 시 CTO 승인 | 변경 내용 전체 기록 |

### 3-4. 배포 관리 정책

| 항목 | 기준 |
|------|------|
| 배포 주기 | 정기 배포: 격주 수요일 / 긴급 배포: 승인 후 즉시 |
| 배포 시간 | 피크 타임(9~22시) 외 |
| 무중단 배포 | Blue-Green 또는 Rolling Update |
| 배포 전 체크리스트 | 스테이징 QA 통과, PO 최종 승인, 롤백 계획 준비 |
| 점검 공지 | 사전 24시간 공지 (계획 점검 시) |

### 3-5. SLA 관리

| 항목 | 기준 | 미달 시 |
|------|------|---------|
| 월간 가용성 | 99.9% (월 약 43분 허용 다운타임) | PO + 경영진 보고 |
| 장애 복구 | RTO 1시간 이내 | 에스컬레이션 |
| 데이터 복구 | RPO 4시간 이내 | 긴급 대응팀 소집 |

### 3-6. 운영 이슈 환류 (RIB 연결)

OPD의 핵심 기능 중 하나는 운영 중 발생한 문제를 다음 기획으로 연결하는 것이다.

| 환류 유형 | 예시 | 입력 대상 |
|-----------|------|-----------|
| 반복 운영 문의 | CS가 수동으로 반복 처리하는 케이스 | 다음 기능 개선 RIB |
| 정책 예외 누적 | 공식 정책으로 수용해야 할 반복 예외 | 정책서 개정 |
| 성능 이슈 | 모니터링에서 반복 감지되는 병목 | NFR 재정의 |
| 보안 이슈 | 취약점 발견 | 보안 정책 강화 |

## 4. AI와 함께 만드는 법

### 단계 1: 입력 준비

AI에게 다음을 제공한다.
- NFR의 SLA·RTO/RPO 기준
- 정책서의 운영자 권한 관련 규칙
- 배포 환경 정보(클라우드, 배포 방식)

### 단계 2: AI 초안 생성

프롬프트 예시:
```
아래 기준으로 운영 정책서(OPD) 초안을 작성해줘.

SLA: 99.9% 가용성, RTO 1시간, RPO 4시간
배포: AWS Blue-Green, 격주 정기 배포
모니터링: CloudWatch 기반 (주문 생성·결제·배송 상태 추적)
운영자 권한: CS 팀은 주문/반품 조회·상태 수정 허용, DB 직접 수정은 긴급 장애만 승인
주요 정책: 반품 허용 기간 7일 (배송완료 기준), 판매자 귀책 판단 기준, 환불 조건

주요 항목: 모니터링 기준(주문·결제·배송·반품 지표), 
           장애 대응 절차(주문 실패·결제 오류·배송 지연 시나리오), 
           롤백 기준(결제 오류·반품 정책 버그 등), 
           배포 정책, 운영자 권한 행사 기준, SLA 관리,
           반복 이슈 환류(예: 반품 거부율 높은 상품 유형 → 정책 검토)
```

### 단계 3: PM 확정 기준

| 항목 | 이유 |
|------|------|
| 롤백 결정 기준 | 비즈니스 영향도 판단은 PO가 해야 함 |
| 운영자 권한 범위 | 컴플라이언스·보안 정책과 연동 |
| SLA 기준 | 계약 또는 내부 약정과 일치해야 함 |
| 환류 기준 | 어떤 운영 이슈를 다음 기획에 올릴지 PO 판단 |

## 5. 품질 기준 / 체크리스트

| 항목 | 확인 기준 |
|------|-----------|
| SLA 정의 | 가용성·RTO·RPO가 NFR과 일치하는가 |
| 장애 대응 | 감지→판단→조치→공지→사후분석 단계가 정의됐는가 |
| 롤백 기준 | 상황별 롤백 vs 핫픽스 결정 기준이 명확한가 |
| 운영자 권한 | 허용 행위와 금지 행위, 기록 의무가 명시됐는가 |
| 배포 정책 | 정기·긴급 배포 기준과 체크리스트가 있는가 |
| 환류 구조 | 운영 이슈가 다음 기획으로 연결되는 경로가 있는가 |
| 승인 상태 | Draft / Review / Approved 상태가 표시됐는가 |

---

## 6. 다음 단계 연결 규칙

- **RIB (다음 과제)**: 반복 운영 이슈, VOC 패턴, 정책 예외 누적 → 다음 기획의 출발점
- **Decision Log**: 운영 중 정책 예외·변경 결정 기록
- **RTM**: 운영 이슈가 어떤 요구사항과 연결되는지 추적
- **정책서 개정**: 운영 예외가 공식 정책으로 수용될 때 정책서 업데이트

---

## 7. 이 장의 핵심 메시지

> 출시는 시작이다. 운영 정책서는 출시 이후의 판단 기준을 미리 정의해서 운영을 예측 가능하게 만들고, 운영에서 배운 것을 다음 기획으로 연결한다.

OPD는 운영팀의 문서가 아니다. PM이 정의한 정책·권한·SLA가 운영 단계에서 어떻게 유지되는지를 명시하는 기획 산출물이다. 그리고 OPD의 환류 구조는 산출물 체인이 단선으로 끝나지 않고 순환하도록 만드는 고리다.

---

## 8. 다음 장으로의 연결

OPD까지 완성되면 산출물 체인의 모든 주요 산출물이 갖춰진다. 이제 이 체인을 전체 조망으로 다시 보고, 실제 과제에서 어떻게 선택적으로 운영할 것인지를 설계할 차례다.

### OPD에서 산출물 체인 설계로 이동하는 항목

| OPD 항목 | 이동 형태 | 산출물 체인 설계에서의 역할 |
|---|---|---|
| 운영 이슈 패턴 | 반복 발생 이슈 유형 목록 | 체인 개선 포인트 식별 |
| SLA 미달 항목 | 미충족 지표 목록 | 다음 사이클 RIB 입력 (환류) |
| 장애 원인 분류 | 설계·구현·운영 원인 구분 | 체인 어느 단계가 약한지 진단 기준 |
| 배포 정책 | 배포 빈도·방식 | 체인 운영 리듬 설계 기준 |
| 롤백 기준 | 롤백 트리거 조건 | 체인 변경 관리 원칙 |

### 체인 전환 기준 (OPD → 산출물 체인 설계)

| 확인 항목 | 기준 |
|---|---|
| 전체 체인 산출물 존재 | RIB → OPD까지 모든 핵심 산출물이 최소 Draft 이상으로 존재하는가 |
| 운영 이슈 환류 준비 | OPD의 이슈 패턴이 다음 사이클 RIB로 넘어갈 항목이 식별되어 있는가 |
| SLA 달성 여부 판단 | 출시 후 SLA 기준을 충족하고 있는가 |

- **이 장이 결정한 것**: 운영 기준, 장애 대응 절차, SLA, OPD→RIB 환류 구조
- **다음 장이 시작하는 것**: RIB에서 OPD까지의 전체 체인을 조망하고 과제별 산출물 세트를 설계하는 방법
