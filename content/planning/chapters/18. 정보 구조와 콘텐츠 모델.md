# 18장. 정보 구조와 콘텐츠 모델

> 이 장은 서비스 안의 정보를 사용자 관점에서 계층과 관계로 정리하는 정보 구조도(IA)와, 각 콘텐츠 유형의 속성·관계·제약을 정의하는 콘텐츠 모델을 다룬다. IA는 메뉴·페이지·콘텐츠의 위계를 정리하고, 콘텐츠 모델은 각 콘텐츠 요소가 어떤 구조와 규칙을 가지는지를 정의한다.

> **전제 지식**: 16장(프로젝트 정책서와 권한 정책), 17장(BPMN과 DMN) — 정보 구조와 콘텐츠 모델은 정책서의 규칙과 BPMN의 프로세스 흐름에서 생성·변경되는 데이터가 어떤 구조로 표현되어야 하는지를 정의한다. 두 산출물의 내용을 먼저 알아야 IA와 콘텐츠 모델의 범위를 설계할 수 있다.

## 이 장의 목적

이 장은 서비스 안의 정보를 사용자 관점에서 구조화하는 두 산출물을 다룬다. 정보 구조도(IA)는 사용자가 어디서 무엇을 보는지를 정리하고, 콘텐츠 모델은 그 정보가 어떤 구조로 되어 있는지를 기획 기준으로 정의한다. 두 산출물은 ERD, 사양서, API 명세서의 직접 입력이 된다.

이 장을 읽고 나면 독자는 다음을 할 수 있어야 한다.

- IA와 콘텐츠 모델이 왜 각각 필요한지, ERD와 어떻게 다른지 설명할 수 있다.
- 두 산출물이 어떻게 연결되는지, 각각의 입력과 출력이 무엇인지 파악한다.
- AI와 함께 초안을 만들고 PM이 무엇을 검토해야 하는지 판단할 수 있다.
- IA와 콘텐츠 모델이 사양서·API 명세서·ERD 설계에 어떻게 연결되는지 이해한다.

---

## 1. 이 산출물이 왜 존재하는가

정책서와 BPMN, DMN이 확정되면 "무엇을 어떻게 처리한다"는 규칙은 갖춰진다. 그러나 그 규칙이 실제로 작동하려면 두 가지가 더 필요하다. 첫째, 서비스 안의 정보가 사용자 관점에서 어디에 어떻게 놓여 있는가(IA). 둘째, 각 콘텐츠 유형이 어떤 속성과 관계를 가지는가(콘텐츠 모델).

예를 들어 반품 처리 과제를 기준으로 생각해보면, BPMN에는 "반품 신청 → 판매자 확인 → 수거 → 환불"이라는 흐름이 있다. 그러나 이것만으로는 다음 질문에 답하기 어렵다.

- 반품 신청 화면에서 구매자가 볼 수 있는 정보는 무엇이고, 어느 계층에 위치하는가
- "반품 신청" 콘텐츠는 어떤 속성을 가지며, 주문·상품·배송과 어떤 관계를 맺는가
- "반품 사유" 속성의 입력 형식과 필수 여부는 무엇인가

이 질문에 답하는 것이 IA와 콘텐츠 모델의 역할이다. 두 산출물이 없으면 디자인·개발·QA가 각자 다른 기준으로 화면과 데이터를 설계한다.

---

## 2. 무엇을 입력으로 받고 무엇을 넘기는가

**입력:**
- 승인된 PRD (기능 범위, 주요 엔티티)
- 승인된 정책서 (데이터 보존 규칙, 상태 전이 규칙)
- DMN (상태별 판단 기준, 조건 분기)
- BPMN (프로세스 흐름, 각 단계에서 생성·변경되는 데이터)

**출력:**
- 정보 구조도(IA): 서비스 내 정보의 계층과 관계를 사용자 관점에서 정리한 구조
- 콘텐츠 모델: 각 콘텐츠 유형의 속성·관계·제약을 기획 기준으로 정의한 문서

> ERD(개체-관계 다이어그램)와 상태 모델은 19장에서 다룬다. IA·콘텐츠 모델이 기획 관점의 구조 정의라면, ERD는 그것을 데이터베이스 설계로 전환하는 산출물이다.

이 두 산출물은 **사양서·API 명세서·ERD**의 직접 입력이 된다.

---

## 3. 두 산출물의 구조와 역할

### 3-1. 정보 구조도 (IA: Information Architecture)

IA는 서비스 안의 정보를 **사용자 관점**에서 계층과 관계로 정리한 산출물이다. 개발자가 DB 설계를 위해 보는 것이 아니라, 어떤 정보가 어디에 있고 어떻게 연결되는지를 기획과 디자인이 공유하는 데 사용한다.

| 항목 | 내용 |
|------|------|
| 목적 | 서비스 내 정보의 위계와 관계를 사용자 관점에서 정의 |
| 형식 | 트리 구조, 사이트맵, 카드 정렬 결과 |
| 주요 내용 | 메뉴 계층, 콘텐츠 분류, 내비게이션 구조 |
| 기준 문서 | PRD의 기능 목록, 시나리오 |


IA는 기획과 디자인이 공유하는 출발점이다. Figma의 사이트맵이나 트리 구조 형식으로 작성하며, 각 노드에는 페이지 이름, 계층 위치, 주요 콘텐츠 유형을 포함한다.

---

### 3-2. 콘텐츠 모델 (Content Model)

콘텐츠 모델은 서비스 안의 각 콘텐츠 유형이 어떤 속성을 가지고, 다른 유형과 어떤 관계를 맺으며, 어떤 제약 조건 아래 존재하는지를 정의하는 문서다.

IA가 "어디에 무엇이 있는가"를 정의한다면, 콘텐츠 모델은 "그 무엇이 어떤 구조로 되어 있는가"를 정의한다.

| 항목 | 내용 |
|------|------|
| 목적 | 콘텐츠 유형별 속성·관계·제약 정의 |
| 형식 | 테이블, YAML, JSON Schema, Notion 데이터베이스 |
| 주요 내용 | 콘텐츠 유형 목록, 속성(필드), 유형 간 관계, 필수/선택 규칙 |
| 기준 문서 | PRD 기능 목록, IA, 정책서 |

**이커머스 플랫폼 예시 1: 반품 신청(Return) 콘텐츠 모델**

| 속성명 | 유형 | 필수 | 설명 |
|--------|------|------|------|
| return_id | string | 필수 | 반품 신청 고유 식별자 |
| order_id | reference | 필수 | 원주문 콘텐츠 유형 참조 |
| buyer_id | reference | 필수 | 구매자 콘텐츠 유형 참조 |
| reason_code | enum | 필수 | 반품 사유 코드 (단순변심/불량/오배송/기타) |
| reason_detail | text | 선택 | 사유 상세 설명 (최대 500자) |
| photos | array | 선택 | 증빙 사진 (최대 5장, 불량·오배송 시 권장) |
| status | enum | 필수 | 신청접수/판매자확인중/수거중/검수완료/환불완료/거부 |
| applied_at | datetime | 필수 | 반품 신청 일시 (P-02 기한 계산 기준) |
| resolved_at | datetime | 선택 | 처리 완료 일시 |
| exception_approved | boolean | 필수 | 운영 예외 승인 여부 (기본값: false) |

**이커머스 플랫폼 예시 2: 주문(Order) 콘텐츠 모델 (발췌)**

| 속성명 | 유형 | 필수 | 설명 |
|--------|------|------|------|
| order_id | string | 필수 | 주문 고유 식별자 |
| buyer_id | reference | 필수 | 구매자 콘텐츠 유형 참조 |
| status | enum | 필수 | 결제완료/배송준비/배송중/배송완료/구매확정/취소/반품중 |
| confirmed_at | datetime | 선택 | 구매확정 일시 (이후 반품 불가, P-03 기준) |
| returns | array | 선택 | 연결된 반품 신청 목록 (1:N 관계) |

> **콘텐츠 모델과 ERD의 차이**: 콘텐츠 모델은 기획과 디자인이 공유하는 설계 기준이고, ERD는 그것을 데이터베이스 구조로 옮긴 것이다. `applied_at`처럼 정책 조항(P-02)과 직접 연결된 속성이 콘텐츠 모델에 명시되면, ERD 설계자가 해당 컬럼의 목적을 오해할 가능성이 줄어든다.

## 4. AI와 함께 만드는 법

### IA 작성 시

PRD의 기능 목록과 핵심 시나리오를 입력으로 제공한다.

프롬프트 예시:
```
다음 기능 목록과 시나리오를 기반으로 이커머스 플랫폼의 정보 구조도(IA)를 작성해줘.
기능: 홈, 상품 목록, 상품 상세, 장바구니, 주문/결제, 주문 내역, 반품 신청,
     반품 내역, 마이페이지, 판매자 어드민(상품 관리·반품 처리), 운영자 어드민(반품 예외 처리)
각 메뉴의 계층 구조와 주요 콘텐츠를 포함해줘.
```

AI가 생성한 IA에서 PM이 확인할 것:
- 모든 핵심 시나리오의 진입점이 IA에 포함됐는가
- 사용자 흐름이 끊기는 구간은 없는가
- 깊이가 3단계를 초과하는 경로가 있다면 단순화할 수 있는가

### 콘텐츠 모델 작성 시

PRD의 주요 엔티티 목록과 정책서의 제약 조건을 입력으로 제공한다.

프롬프트 예시:
```
다음 정책과 시나리오를 기반으로 반품 신청(Return) 콘텐츠 모델을 정의해줘.

[정책 요약]
- P-02: 배송 완료 후 7일 이내만 반품 신청 가능 (applied_at 기준)
- P-03: 구매확정 이후 반품 불가
- P-04: 판매자 귀책 시 배송비 판매자 부담
- 운영 예외 승인(exception_approved)이 true면 P-02·P-03 예외 허용

[시나리오]
- 구매자 반품 신청 → 판매자 수락/거부 → 수거 → 검수 → 환불

출력: 속성명, 유형, 필수 여부, 설명 (정책 연결 명시 포함)
```

## 5. 품질 기준 / 체크리스트

| 항목 | 확인 기준 |
|------|-----------|
| IA 완전성 | PRD의 모든 기능 진입점이 IA에 포함됐는가 |
| IA 일관성 | 동일한 콘텐츠가 여러 경로에서 다른 이름으로 표현되지 않는가 |
| 콘텐츠 모델 커버리지 | PRD에 언급된 모든 콘텐츠 유형이 정의됐는가 |
| 속성 완전성 | 필수/선택 속성이 명시됐는가 |
| 관계 정의 | 콘텐츠 유형 간 관계(1:N, M:N)가 기술됐는가 |
| ERD 정합성 | 콘텐츠 모델 속성이 ERD 설계와 충돌하지 않는가 |
| 미정 항목 표시 | 확정되지 않은 속성과 관계가 명확히 표시됐는가 |

## 7. 이 장의 핵심 메시지

IA는 사용자가 서비스를 탐색하는 지도다. 콘텐츠 모델은 그 지도 위 각 장소에 무엇이 있는지를 정의한다. 두 산출물이 없으면 디자인, 개발, QA가 각자 다른 지도를 들고 작업한다.

콘텐츠 모델은 ERD 이전에 작성하는 기획 문서다. DB 설계가 아니라 "우리 서비스의 콘텐츠는 이런 구조다"라는 합의의 기록이다. 이 합의가 있어야 ERD, 사양서, API 명세가 일관된 방향으로 만들어진다.

## 8. 다음 장으로의 연결

정보 구조와 콘텐츠 모델이 확정되면 다음 질문은 "이 콘텐츠를 어떤 데이터 구조로 저장할 것인가"다. 19장은 ERD와 데이터 사전을 통해 콘텐츠 모델의 기획 기준을 실제 데이터베이스 설계로 전환하는 방법을 다룬다.
