# 9장. 문제 정의서와 범위 정의서

> **전제 지식**: 8장(RIB) — RIB는 비즈니스 문제와 요청 배경을 담는다. 문제 정의서는 RIB에서 식별된 문제를 해결 가능한 형태로 구조화하고, 범위 정의서는 그 해결 범위를 명확히 한다. RIB의 맥락을 먼저 알아야 "무엇을 해결할 것인가"의 출발점을 이해할 수 있다.

## 이 장의 목적

많은 프로젝트가 "앱 만들어줘"로 시작한다. 바이브 코딩 환경에서는 이 한 문장으로 실제로 무언가가 만들어지기도 한다. 문제는 만들어진 것이 원하던 것인지 판단할 기준이 없다는 데 있다.

문제 정의서와 범위 정의서는 그 기준을 만드는 문서다. 이 두 문서가 없으면 검토 때마다 "이게 맞나?"라는 질문이 반복된다. 있으면 "우리가 정의한 문제를 해결했는가", "우리가 정한 범위 안에 있는가"로 물음이 바뀐다.

이 장은 두 문서의 역할과 구조, 작성 기준을 실무 관점에서 설명한다.

---

## 1. 두 문서가 왜 독립적으로 필요한가

문제 정의와 범위 정의는 PRD나 기능 목록에 녹아 들어가는 경우가 많다. PRD 앞부분에 배경과 목표가 기술되고, 범위가 포함된다.

이 방식의 문제는 두 문서의 역할이 다르다는 데 있다. 문제 정의서는 "왜"에 답하는 문서다. 범위 정의서는 "무엇을 하고 무엇을 하지 않는가"에 답하는 문서다. 이 둘이 한 문서에 섞이면 두 역할 모두 불명확해진다.

더 실용적인 이유도 있다. AI에게 작업을 지시할 때 두 문서를 별도로 넘길 수 있다. 문제 맥락을 먼저 제공하고 이후 범위를 별도로 지정하면 AI의 출력 품질이 달라진다. 하나의 긴 문서보다 구조화된 짧은 문서 두 개가 더 효과적이다.

---

## 2. 문제 정의서

### 역할

문제 정의서는 "우리가 무엇을 해결하려 하는가"를 명확히 하는 문서다. 이 문서의 독자는 팀 전체와 AI다. 팀이 같은 문제를 바라볼 수 있게 하고, AI가 솔루션을 생성할 때 방향을 잃지 않도록 한다.

문제 정의서가 없으면 팀은 솔루션에 대해 논의하지만 실제로는 서로 다른 문제를 푼다. 문제 정의서가 있으면 "이 기능이 우리 문제를 해결하는가"라는 질문이 가능해진다.

### 구조

| 항목 | 설명 |
|------|------|
| 문제 상황 | 현재 어떤 상황에서 어떤 불편이나 비효율이 발생하는가 |
| 영향 대상 | 누가 이 문제를 겪는가 (사용자·팀·비즈니스) |
| 현재 해결 방식 | 지금은 어떻게 해결하고 있는가 (또는 해결하지 못하고 있는가) |
| 해결하지 않으면 | 이 문제를 해결하지 않을 경우 어떤 결과가 생기는가 |
| 해결 목표 | 어떤 상태가 되면 이 문제를 해결한 것인가 |
| 성공 기준 | 위 목표가 달성됐음을 어떻게 확인할 수 있는가 |

### 작성 기준

문제 정의서에서 가장 중요한 항목은 **해결 목표**와 **성공 기준**이다. 이 두 항목이 명확하지 않으면 나머지 항목이 있어도 문서의 역할을 하지 못한다.

흔한 실수는 "더 나은 사용자 경험을 제공한다"처럼 측정할 수 없는 목표를 쓰는 것이다. 좋은 목표는 관찰 가능하고 판단할 수 있어야 한다. "첫 구매 완료까지 걸리는 클릭 수를 현재 7단계에서 4단계 이내로 줄인다"처럼 구체적이어야 한다.

또 하나의 흔한 실수는 솔루션을 문제 정의 안에 포함하는 것이다. "기존 수기 입력 방식을 자동화한다"는 솔루션이지 문제가 아니다. "수기 입력으로 인해 데이터 오류가 발생하고 처리 시간이 평균 20분 소요된다"가 문제다.

### 샘플 (이커머스 플랫폼)

```markdown
## 문제 정의서

**문제 상황**: 반품 신청 이후 환불 처리까지 운영팀이 개별 케이스마다 수동으로 개입하고 있다. 판단 기준이 없어 처리 결과가 담당자마다 다르고, 구매자 환불 대기 시간도 케이스별로 크게 차이가 난다.

**영향 대상**: 구매자(환불 지연 경험), 운영팀(수동 처리 과부하), 판매자(귀책 기준 불명확)

**현재 해결 방식**: 고객센터 담당자가 반품 신청 건을 개별 확인 후 재량으로 승인·거부. 명문화된 판단 기준 없음.

**해결하지 않으면**: 운영 비용이 계속 증가하고, 동일 상황에서 구매자마다 다른 처리 결과가 나와 신뢰도가 하락한다.

**해결 목표**: 반품 허용 여부, 배송비 부담 주체, 환불 수단을 정책으로 확정하고 시스템이 자동 판단하도록 한다.

**성공 기준**: 운영팀 수동 개입 비율이 현재 약 30%에서 5% 이하로 감소한다.
```

## 3. 범위 정의서

### 역할

범위 정의서는 "무엇을 만들고 무엇을 만들지 않는가"를 명확히 하는 문서다. 이 문서의 핵심은 포함 범위만큼 **제외 범위**를 명시하는 것이다.

범위를 명확히 하지 않으면 프로젝트 도중에 "이것도 해주세요"가 반복된다. AI에게 작업을 요청할 때도 마찬가지다. 범위를 명시하지 않으면 AI는 관련된 기능을 자의적으로 추가하거나 제외한다. 기획자가 의도한 범위와 결과물이 달라지는 주요 원인 중 하나다.

### 구조

| 항목 | 설명 |
|------|------|
| 포함 범위 | 이번 프로젝트에서 만들 것 (기능·화면·서비스 단위) |
| 제외 범위 | 이번 프로젝트에서 만들지 않을 것 (의도적 제외) |
| MVP 기준 | 최소한 이것이 있어야 출시 가능한 조건 |
| 1차 이후 검토 항목 | 지금은 제외하지만 이후에 추가할 가능성이 있는 것 |
| 전제 조건 | 이 범위가 성립하기 위해 전제되어야 하는 것 |

### 작성 기준

제외 범위는 "아직 생각하지 않은 것"이 아니라 "의도적으로 이번에 하지 않기로 결정한 것"이어야 한다. 이 구분이 명확해야 이후 범위 변경 요청이 왔을 때 근거를 가질 수 있다.

MVP 기준은 "이것 없으면 출시 안 된다"는 기준이다. 팀이 MVP와 완성본을 혼동하면 범위가 계속 커진다. MVP 기준을 명시하면 "지금 하지 않아도 되는 것"과 "지금 반드시 해야 하는 것"의 경계가 생긴다.

### 샘플 (이커머스 플랫폼 — 반품·환불 처리)

```markdown
## 범위 정의서

**포함 범위**
- 반품 신청 화면 (사유 선택, 사진 첨부, 수거 주소 확인)
- 판매자 반품 수락·거부 화면 (귀책 선택, 처리 결과 입력)
- 반품 배송사 수거 처리 연동 (수거 요청, 수거 완료 상태 반영)
- 환불 처리 (원결제 수단 자동 환불, 처리 결과 구매자 알림)
- 운영자 예외 승인 화면 (정책 외 케이스 수동 처리)

**제외 범위**
- 해외 배송 반품 (정책 미확정, 별도 과제로 분리)
- 디지털 상품(다운로드 완료) 반품 예외 처리 (1차 이후 검토)
- 부분 반품 (전체 반품만 이번 범위에 포함)
- CS 채널을 통한 상품 이상 신고 (고객센터 시스템과 별도 연동 필요)

**MVP 기준**
반품 신청 → 판매자 처리 → 수거 완료 → 환불 처리 정상 흐름이 에러 없이 완료될 것.
운영자 수동 개입 없이 정책 기준에 따른 자동 판단이 동작할 것.

**1차 이후 검토 항목**
- 부분 반품 처리
- 디지털 상품 예외 정책 적용

**전제 조건**
- 결제 시스템 환불 API가 연동 완료 상태여야 함
- 배송사 수거 API는 1개 배송사(CJ대한통운) 기준으로만 이번 범위에 포함
- 반품 정책(허용 기간·귀책 기준·배송비 부담)은 정책서 Approved 상태여야 착수 가능
```

## 4. 두 문서를 AI에게 전달하는 방법

문제 정의서와 범위 정의서는 AI에게 작업을 요청할 때 컨텍스트로 제공하는 문서다. 효과적인 전달 순서는 다음과 같다.

1. **문제 정의서 먼저**: "우리가 해결하려는 문제는 이것이다"를 AI에게 인식시킨다. AI가 솔루션을 제안할 때 방향을 잃지 않도록 한다.
2. **범위 정의서 다음**: "이번에 만들 것은 이것이고, 만들지 않을 것은 이것이다"를 명시한다. AI가 범위를 임의로 확장하거나 축소하지 않도록 한다.
3. **이후 구체적인 지시**: 이 두 문서를 컨텍스트로 제공한 뒤 구체적인 기능 명세나 코드 생성을 요청한다.

두 문서를 제공하지 않고 바로 "장바구니 기능 만들어줘"로 시작하면 AI는 장바구니가 어떤 문제를 해결해야 하는지, 어디까지가 범위인지 모른 채 결과를 만든다.

---

## 5. 이 장의 핵심 메시지

문제 정의서와 범위 정의서는 화려한 기능 명세서보다 먼저 완성되어야 한다. 이 두 문서가 없으면 기능 명세서는 "무엇을 위한 기능인지"가 불분명한 목록이 된다.

AI 협업에서 이 두 문서의 역할은 더 크다. 사람은 암묵적인 맥락을 이해하지만 AI는 그렇지 않다. 문제와 범위를 명시적으로 제공하는 것이 AI 협업의 출발점이다.

문제와 범위를 정의했다면, 다음 질문은 "어떤 가정 위에서 이 프로젝트를 진행하는가"이다. 10장은 가정과 제약사항을 체계적으로 정리하는 방법, 그리고 그것이 우선순위 결정에 어떻게 연결되는지를 다룬다.
