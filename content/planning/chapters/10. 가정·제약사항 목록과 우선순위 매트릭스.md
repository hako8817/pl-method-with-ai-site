# 10장. 가정·제약사항 목록과 우선순위 매트릭스

> **전제 지식**: 9장(문제 정의서와 범위 정의서) — 가정과 제약사항은 문제 정의서와 범위 정의서에서 정한 "무엇을 해결하고 무엇을 만드는가" 위에 세워진다. 두 문서의 내용을 먼저 알아야 어떤 가정이 성립하는지, 어떤 제약이 경계를 결정하는지 이해할 수 있다.

## 이 장의 목적

9장에서 우리는 무엇을 해결할 것인지(문제 정의), 무엇을 만들 것인지(범위 정의)를 다뤘다. 그러나 이 두 문서만으로는 충분하지 않다. 기획은 항상 가정 위에서 진행된다. 그 가정이 틀렸을 때 무슨 일이 생기는지 미리 파악하지 않으면 프로젝트는 예측하지 못한 방향으로 흔들린다.

이 장은 두 가지를 다룬다. 첫째, 기획이 전제로 삼는 가정과 제약사항을 명시적으로 기록하는 방법. 둘째, 무엇을 먼저 만들지 판단하는 우선순위 매트릭스의 구조와 사용법.

---

## 1. 가정·제약사항 목록

### 왜 필요한가

모든 기획에는 전제가 있다. 대부분의 기획자는 이 전제를 암묵적으로 안다. "결제 연동은 PG사가 담당하니까 우리는 그냥 쓰면 된다", "디자인 시스템은 이미 있다", "모바일 앱은 이번에 안 한다" 같은 전제들이다.

문제는 이 전제가 팀 안에서 공유되지 않을 때 생긴다. 기획자는 당연히 알고 있다고 생각하지만 개발자나 AI는 그 전제를 모른 채 작업을 진행한다. 결제 모듈을 직접 구현하거나 새 디자인 시스템을 만들거나 모바일 반응형까지 추가하는 결과로 이어진다.

AI 협업에서 이 문제는 더 자주 발생한다. AI는 전제를 추론하지 않는다. 명시되지 않은 것은 없는 것이다.

### 구조

| 항목 | 유형 | 내용 |
|------|------|------|
| 가정 | 사실이라고 전제하는 것 | 현재 확인되지 않았지만 사실이라고 보고 진행하는 조건 |
| 제약사항 | 변경 불가한 조건 | 기술, 예산, 일정, 법률 등 협상 불가한 조건 |
| 의존성 | 외부 의존 항목 | 외부 시스템, 팀, 데이터에 의존하는 항목 |
| 리스크 | 가정이 틀렸을 때의 영향 | 가정이 어긋날 경우 프로젝트에 미치는 영향 |

### 가정과 제약의 차이

가정은 "그렇다고 믿고 진행하는 것"이다. 확인이 필요하지만 지금 당장 확인할 수 없어서 가정으로 두는 것이다. 나중에 틀린 것으로 밝혀지면 범위나 계획이 바뀐다.

제약사항은 "변경할 수 없는 조건"이다. 예산 상한, 법적 요건, 기술 스택, 배포 환경 등이 해당한다. 기획은 이 조건 안에서 이루어져야 한다.

### 작성 기준

가정은 구체적으로 써야 한다. "사용자 수가 많지 않을 것이다"는 가정이 아니다. "초기 6개월 내 동시 접속자 수는 100명을 초과하지 않는다고 가정한다"가 가정이다.

리스크 항목은 가정이 틀렸을 경우 어떤 영향이 생기는지 함께 적는다. "PG사 연동이 예정보다 2주 늦어질 경우 결제 기능이 포함된 MVP 일정이 조정된다"처럼 실제 영향을 구체화한다.

### 샘플 (이커머스 플랫폼 주문·결제·반품 시스템)

```markdown
## 가정·제약사항 목록

### 가정
- 결제 연동은 외부 PG사(토스페이먼츠)가 담당하며, API 응답시간은 평균 3초 이내일 것으로 가정한다.
- 배송 API는 기존 배송사 연동 인터페이스를 그대로 사용하며, 중간에 변경될 가능성은 낮다고 가정한다.
- 판매자 귀책 반품 판단 기준은 이번 릴리즈에서 정책팀과 합의되어 확정될 것이다.
- 초기 일일 주문량은 최대 1,000건을 넘지 않을 것으로 예상한다.

### 제약사항
- 기술 스택: Node.js + PostgreSQL (변경 불가)
- 일정: 주문·반품·환불 핵심 기능은 12주 이내 출시 필수
- 예산: 클라우드 인프라 월 200달러 이내
- PG사 변경 불가 (기존 계약 유지)
- 배송사 API는 이미 구축된 레거시 시스템 (마이그레이션 불가)

### 의존성
- 결제 PG사 API 문서 (토스페이먼츠에서 제공)
- 배송사 API 명세 (물류팀에서 3주차 이전 제공 필요)
- 반품 정책 기준 수립 (정책팀 협의)

### 리스크
- PG사 API 응답 시간이 3초 초과할 경우: 결제 타임아웃 처리 로직 추가 필요
- 배송 API 연동 지연 시: 수동 배송 추적 기능으로 대체 운영
- 판매자 귀책 판단 기준 확정 지연 시: 운영팀 매뉴얼 검증으로 1주 추가 소요
```

## 2. 우선순위 매트릭스

### 왜 필요한가

범위를 정의하면 "무엇을 만들 것인가"가 정해진다. 그러나 "무엇을 먼저 만들 것인가"는 별도의 판단이 필요하다.

우선순위 매트릭스 없이 진행하면 두 가지 문제가 생긴다. 하나는 팀 내에서 각자가 다른 순서로 작업하는 것이다. 다른 하나는 AI에게 작업을 요청할 때 순서가 없어 의존성 없는 기능부터 만들거나 핵심 흐름보다 주변 기능이 먼저 완성되는 것이다.

### 구조

우선순위 매트릭스는 두 축으로 구성된다.

**가로축 (영향도)**: 이 기능이 문제 해결 목표에 얼마나 직접적으로 기여하는가. 높음/중간/낮음으로 분류.

**세로축 (구현 난이도)**: 이 기능을 구현하는 데 얼마나 많은 노력이 필요한가. 높음/중간/낮음으로 분류.

4사분면 해석:

| 구분 | 영향도 높음 | 영향도 낮음 |
|------|-------------|-------------|
| **난이도 낮음** | 즉시 실행 (Quick Win) | 보류 또는 제거 |
| **난이도 높음** | 우선 계획 수립 | 1차 범위에서 제외 |

### 우선순위 판단 기준

매트릭스의 가장 중요한 기준은 **영향도가 "사용자 가치" 또는 "문제 해결 직결 여부"**라는 점이다. "이 기능이 없으면 핵심 사용자 흐름이 완성되지 않는다"면 영향도 높음이다. "있으면 좋지만 없어도 핵심 흐름은 동작한다"면 영향도 낮음이다.

팀 내에서 "이건 꼭 필요해"라는 의견 충돌이 생길 때 문제 정의서의 해결 목표와 비교하면 판단 기준이 명확해진다. "이 기능이 우리가 정의한 문제를 직접 해결하는가"로 물어보는 것이다.

### AI 협업에서의 활용

AI에게 개발 순서를 요청할 때 우선순위 매트릭스를 함께 제공하면 효과적이다. "다음 기능 목록을 우선순위 매트릭스 순서대로 구현해줘"가 아니라 매트릭스 자체를 컨텍스트로 제공하고 "1순위 Quick Win 항목부터 구현하는 순서를 설계해줘"처럼 요청한다.

### 샘플 (쇼핑몰 플랫폼)

```markdown
## 우선순위 매트릭스

| 기능 | 영향도 | 난이도 | 우선순위 | 비고 |
|------|--------|--------|----------|------|
| 홈 화면 상품 목록 | 높음 | 낮음 | 1 (Quick Win) | MVP 핵심 |
| 상품 상세 화면 | 높음 | 낮음 | 1 (Quick Win) | MVP 핵심 |
| 장바구니 기능 | 높음 | 중간 | 2 (우선 계획) | MVP 핵심 |
| 주문 완료 화면 | 높음 | 낮음 | 1 (Quick Win) | MVP 핵심 |
| 카테고리 필터 | 중간 | 낮음 | 3 (보류) | 2차 스프린트 |
| 상품 검색 | 중간 | 높음 | 4 (제외) | 1차 범위 외 |
| 리뷰 기능 | 낮음 | 높음 | 4 (제외) | 1차 범위 외 |
```

## 3. 두 문서를 함께 사용하는 방법

가정·제약사항 목록과 우선순위 매트릭스는 함께 활용될 때 효과가 커진다.

가정이 바뀌면 우선순위가 바뀐다. "PG사 API가 지연된다"는 가정이 현실이 되면 결제 관련 기능의 우선순위가 바뀐다. 가정·제약사항 목록을 업데이트하면 우선순위 매트릭스를 재검토하는 트리거가 된다.

AI에게 이 두 문서를 함께 제공하면 변경된 가정에 따라 작업 순서나 구현 방향을 조정하는 판단에 AI를 더 효과적으로 활용할 수 있다.

---

## 4. 이 장의 핵심 메시지

가정·제약사항은 문서로 써야 관리된다. 암묵적인 전제는 팀 안에서도 AI와의 협업에서도 오해의 원인이 된다.

우선순위 매트릭스는 "무엇을 먼저 만들 것인가"를 팀과 AI가 같은 기준으로 판단할 수 있게 하는 도구다. 이 판단 기준이 없으면 프로젝트는 각자의 기준으로 진행된다.

이 두 문서는 PRD만큼 중요하다. PRD가 없으면 무엇을 만들어야 하는지 모른다. 가정 목록이 없으면 어떤 전제 위에서 만드는지 모른다. 우선순위 매트릭스가 없으면 무엇을 먼저 만들어야 하는지 모른다.

---

## 5. 다음 장으로의 연결

가정과 제약사항, 우선순위 매트릭스까지 정리되면 프로젝트의 전제와 방향이 고정된다. 이 상태에서 다음 단계는 "무엇을 왜 만드는가"를 팀 전체가 같은 기준으로 공유하는 허브 문서를 만드는 것이다.

11장에서는 PRD(Product Requirements Document)가 방향 문서이자 허브 문서로서 어떤 역할을 하는지, 어떻게 작성하고 다음 산출물과 어떻게 연결되는지를 다룬다.
