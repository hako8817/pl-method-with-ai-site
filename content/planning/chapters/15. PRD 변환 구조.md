# 15장. PRD 변환 구조: 기획 문서를 구현 입력으로 바꾸기

> **전제 지식**: 11장(PRD), 13장(Feature Spec), 14장(Scenario와 AC) — 이 장은 PRD가 어떻게 하위 산출물로 변환되는지를 다룬다. PRD의 구조와 Feature Spec, Scenario/AC가 어떤 역할을 하는지 알아야 변환 체계의 논리를 이해할 수 있다.

## 이 장의 목적

이 장은 PRD가 단독으로 완결되는 문서가 아니라 뒤 산출물들의 입력 구조로 변환되어야 한다는 관점을 다룬다. PRD를 잘 쓰는 것과 PRD가 다음 문서로 이어지도록 변환 가능한 구조로 쓰는 것은 다르다. AI와 협업하는 환경에서 이 차이는 더 크게 드러난다.

이 장을 읽고 나면 다음을 이해해야 한다.

- PRD 변환 구조가 무엇이고 왜 필요한지
- PRD의 어떤 부분이 어떤 산출물로 이어지는지
- AI가 PRD를 다음 단계 산출물로 변환할 때 어떤 구조가 갖춰져야 하는지
- 변환이 안 되는 PRD의 공통적인 문제

---

## 1. PRD는 변환되기 위해 쓰인다

PRD는 제품 방향을 설명하는 문서다. 그러나 실무에서 PRD의 진짜 역할은 뒤 산출물들을 만들기 위한 기준 입력을 제공하는 것이다.

PRD가 갖춰지면 다음 작업들이 가능해진다.

- Feature Spec: PRD의 범위에서 기능 단위를 분리
- 정책서: PRD의 규칙 언급을 정책 조항으로 구체화
- BPMN: PRD의 시나리오 흐름을 프로세스 다이어그램으로 전환
- DMN: PRD의 판단 조건을 의사결정 테이블로 구조화
- 사양서: PRD의 기능 설명을 상태·입력·출력·예외 단위로 분해

이 변환이 잘 되려면 PRD 자체가 변환 가능한 구조로 쓰여야 한다.

---

## 2. 변환되지 않는 PRD의 공통 문제

실무에서 PRD가 다음 단계로 이어지지 못하는 이유는 대부분 세 가지다.

**문장이 너무 서술적이다**: "구매자가 편리하게 주문할 수 있어야 한다"처럼 기준이 없는 서술은 기능 분리도, 정책 추출도, 테스트 기준 설정도 어렵다.

**범위가 불분명하다**: In Scope와 Out of Scope가 명확하지 않으면 Feature Spec 작성 시 어디까지 써야 하는지 판단할 수 없다.

**정책과 기능이 섞여 있다**: "구매확정 이후 반품이 불가하며 이 경우 안내 메시지를 노출한다"처럼 정책 조항과 UI 동작이 한 문장에 섞이면 분리가 어렵다.

---

## 3. 변환 가능한 PRD의 구조 요소

변환이 잘 되는 PRD는 다음 구조 요소를 갖춘다.

**목표와 성공 기준이 분리됨**: 이 기능을 왜 만드는지(목표)와 무엇이 달성되면 성공인지(지표·기준)가 따로 있다.

**범위가 명시적으로 정의됨**: In Scope, Out of Scope, 향후 검토 사항이 구분된다.

**시나리오가 흐름으로 서술됨**: "사용자가 X를 하면 Y가 발생한다"처럼 행위자·동작·결과로 서술된 시나리오는 BPMN과 Scenario 작성의 직접 입력이 된다.

**판단 조건이 명시됨**: "A 조건이면 B, C 조건이면 D"처럼 분기 조건이 명확하면 DMN 변환의 원재료가 된다.

**비기능 요구사항이 분리됨**: 성능, 보안, 가용성 요구는 NFR 문서로 이어지므로 PRD 본문과 섞이지 않아야 한다.

---

## 4. PRD → 산출물 변환 대응표

| PRD 구성 요소 | 변환되는 산출물 |
|---|---|
| 목표 / 성공 기준 | OKR, 릴리즈 기준 |
| In Scope 기능 목록 | Feature Spec 목록 |
| 시나리오 (정상/예외) | Scenario, BPMN |
| 판단 조건 / 분기 | DMN decision table |
| 규칙·제약 언급 | 정책서 조항 |
| 상태·행동·메시지 | 사양서 항목 |
| 비기능 요구사항 | NFR |

---

## 5. AI와 함께 PRD를 변환하는 패턴

PRD가 변환 가능한 구조로 쓰여 있으면 AI를 활용한 다음 단계 산출물 작성이 훨씬 빠르고 정확해진다.

**Feature 분리**: PRD의 In Scope 항목을 입력으로 주고 "이 범위를 Feature 단위로 분리해줘"라고 지시하면 Feature Spec 초안이 나온다.

**정책 추출**: PRD의 시나리오와 예외 처리 섹션을 입력으로 주면 정책서 초안의 기초가 만들어진다.

**BPMN 변환**: 시나리오를 BPMN 흐름 초안으로 변환하는 작업은 AI가 특히 잘한다. 단, 시나리오가 행위자와 흐름으로 구조화되어 있어야 한다.

**DMN 변환**: 판단 조건이 명시된 부분을 입력으로 주면 AI가 decision table 초안을 만든다.

어떤 경우든 AI의 변환 결과는 Draft다. 사람이 검토하고 승인해야 공식 산출물이 된다.

---

## 6. PRD 자동 변환 프롬프트 시퀀스

패턴을 알아도 프롬프트를 어떻게 써야 할지 막히는 경우가 많다. 아래는 PRD 1개를 입력으로 받아 Feature 분해 → 정책 추출 → BPMN 초안 → DMN 초안까지 순서대로 실행할 수 있는 프롬프트 세트다. 각 단계의 출력이 다음 단계의 입력이 된다.

---

### Step 1. PRD → Feature 분해

```
당신은 PRD를 Feature 단위로 분해하는 시스템 분석가입니다.

아래 PRD를 분석하여 Feature 목록을 작성해주세요.

[규칙]
- Feature는 독립적으로 개발·배포 가능한 최소 기능 단위입니다.
- Feature명은 명사형으로 씁니다. 예: "반품 신청 처리", "환불 자동화"
- 각 Feature에 대해 다음 항목을 작성합니다.
  - Feature명
  - 한 줄 설명
  - 근거가 되는 PRD 섹션 또는 항목 (추적용)
  - 우선순위 (P0 / P1 / P2)
- In Scope에 없는 내용은 포함하지 않습니다.
- 기능 설명이 아닌 구현 방법은 쓰지 않습니다.

[입력: PRD]
{{PRD 전문 또는 In Scope 섹션을 여기에 붙여넣기}}

[출력 형식]
| Feature명 | 설명 | 근거 PRD 섹션 | 우선순위 |
|-----------|------|--------------|---------|
```

**이 단계 이후 확인할 것**: Feature 목록이 PRD In Scope 범위 안에 있는지, 하나의 Feature에 두 개 이상의 독립 기능이 섞이지 않았는지 검토한다.

---

### Step 2. PRD → 정책 추출

```
당신은 PRD에서 정책 조항을 추출하는 분석가입니다.

아래 PRD에서 정책, 규칙, 제약, 예외 조건을 추출하여 정책서 초안을 작성해주세요.

[규칙]
- 정책 조항은 "주체 + 조건 + 행동 또는 결과" 형식으로 씁니다.
- 판단 기준이 있는 분기 조건과 예외 처리를 포함합니다.
- 구현 방법(how)이 아닌 규칙(what, when)만 추출합니다.
- UI 동작 설명이나 레이아웃 관련 내용은 제외합니다.
- 조항 번호는 P-001부터 순서대로 붙입니다.

[입력: PRD]
{{PRD 전문을 여기에 붙여넣기}}

[출력 형식]
## [정책 카테고리명]
### P-001 [정책 제목]
- 조건:
- 적용 대상:
- 결과:
- 예외:
```

**이 단계 이후 확인할 것**: 추출된 조항이 실제로 PRD에서 명시적으로 언급된 것인지, AI가 추론으로 추가한 내용이 섞이지 않았는지 검토한다.

---

### Step 3. PRD 시나리오 → BPMN 초안

```
당신은 업무 프로세스를 BPMN 구조로 변환하는 분석가입니다.

아래 시나리오를 BPMN 텍스트 구조로 변환해주세요.

[규칙]
- BPMN 요소를 텍스트로 표현합니다: 시작 이벤트, 종료 이벤트, 태스크, 게이트웨이, 풀, 레인
- 행위자(풀 또는 레인)를 반드시 명시합니다.
- 각 게이트웨이에는 분기 조건을 붙입니다.
- 코드가 아닌 구조 기술서 형식으로 작성합니다.
- 정상 흐름과 예외 흐름을 구분하여 서술합니다.

[입력: 시나리오]
{{PRD의 시나리오 섹션 또는 use case를 여기에 붙여넣기}}

[출력 형식]
풀: [시스템명]
  레인: [행위자1] / [행위자2]

[시작 이벤트] → [태스크: ...] → [게이트웨이: 조건?]
  ├─ Yes: [태스크: ...] → ...
  └─ No: [태스크: ...] → ...
→ [종료 이벤트]
```

**이 단계 이후 확인할 것**: 모든 분기에 종료 이벤트가 있는지, 행위자 구분이 실제 시스템 구조와 맞는지, 시나리오에 없는 흐름이 임의로 추가되지 않았는지 검토한다.

---

### Step 4. PRD 판단 조건 → DMN 초안

```
당신은 의사결정 규칙을 DMN decision table로 구조화하는 분석가입니다.

아래 판단 조건을 DMN decision table로 변환해주세요.

[규칙]
- 입력(Input)과 출력(Output) 변수를 먼저 식별하고 명시합니다.
- 각 행은 하나의 규칙(Rule)입니다.
- 조건은 가능한 한 명확한 값 또는 범위로 씁니다.
- 모든 경우를 커버했는지 확인하고, 누락된 조합이 있으면 명시합니다.
- 충돌하는 규칙이 있으면 별도로 표시합니다.

[입력: 판단 조건]
{{PRD의 조건 및 분기 섹션을 여기에 붙여넣기}}

[출력 형식]
입력 변수: [변수명1], [변수명2]
출력 변수: [결과 변수명]

| 규칙 | [입력 변수1] | [입력 변수2] | [출력 변수] |
|------|-------------|-------------|------------|
| R1   | 조건A       | 조건X       | 결과1      |
| R2   | 조건B       | 조건Y       | 결과2      |

누락 조합: [확인 결과 기술]
충돌 규칙: [확인 결과 기술]
```

**이 단계 이후 확인할 것**: 입력 변수 조합이 실제 시스템 상태와 일치하는지, 출력 결과가 정책 조항(Step 2)과 충돌하지 않는지 대조한다.

---

### 시퀀스 실행 흐름 요약

```
[PRD 전문]
    │
    ├─ Step 1 → Feature 목록 (Feature Spec 작성의 입력)
    ├─ Step 2 → 정책 조항 초안 (정책서 작성의 입력)
    ├─ Step 3 → BPMN 텍스트 구조 (다이어그램 도구 입력 또는 리뷰용)
    └─ Step 4 → DMN decision table (의사결정 로직 정의의 입력)
```

각 단계는 독립 실행도 가능하다. Step 1~4 전체를 한 번에 실행할 필요는 없으며, PRD 완성도에 따라 가능한 단계부터 순서대로 진행하면 된다. Step 1의 Feature 목록이 확정된 뒤 Step 3을 실행하면 BPMN의 태스크 경계가 더 명확해진다.

## 7. 이커머스 반품 처리 케이스에 적용하면

PRD에 "배송 완료 후 7일 이내 반품을 신청할 수 있으며, 판매자 귀책 반품 시 배송비는 판매자가 부담한다"가 있다면 다음처럼 이어진다.

- Feature Spec: 반품 신청 및 처리 Feature
- 정책서: 반품 기간, 판매자 귀책 판정 기준, 배송비 부담 규정
- BPMN: 반품 신청 → 기한 확인 → 귀책 판단 → 수거 / 거부 흐름
- DMN: 주문 상태 × 경과일 × 반품 사유 → 허용/조건부/거부 분기표
- 사양서: 반품 상태값·반품 사유 분류·환불 수단·배송비 계산 방식

PRD 한 줄이 여러 산출물의 기초가 되는 구조다.

---

## 8. 체크리스트

- [ ] PRD의 목표와 성공 기준이 분리되어 있는가
- [ ] In Scope와 Out of Scope가 명시되어 있는가
- [ ] 시나리오가 행위자·동작·결과 구조로 서술되어 있는가
- [ ] 판단 조건이 명시적으로 표현되어 있는가
- [ ] 비기능 요구사항이 본문과 분리되어 있는가
- [ ] 이 PRD를 보고 Feature Spec 항목 목록을 뽑을 수 있는가

---

## 9. 정리

PRD는 잘 쓰는 것만으로 충분하지 않다. 다음 산출물로 변환되기 위한 구조를 갖춰야 한다. 변환 가능한 PRD는 목표·범위·시나리오·판단 조건·비기능 요구사항이 분리된 구조를 가지며 Feature Spec, 정책서, BPMN, DMN, 사양서 작성의 기초 입력이 된다.

PRD가 변환 가능한 구조를 갖추면, 이 장에서 제시한 4단계 프롬프트 시퀀스로 Feature 분해 → 정책 추출 → BPMN 초안 → DMN 초안을 순서대로 실행할 수 있다. AI 협업은 속도뿐 아니라 품질에서도 차이를 만든다.
